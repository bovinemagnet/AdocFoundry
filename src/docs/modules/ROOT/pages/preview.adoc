= The preview
Paul Snow
:revnumber: 0.0.0
:description: The native rendered preview: following the page, scroll sync, click-to-source, links, includes, diagrams and its current limits.

The preview shows the page you are editing as it will read, without leaving the application.
It is drawn natively and needs no browser, Node.js, Ruby or Java.
Every action described here is an engine command, so it also appears in the command palette.
See xref:keyboard-shortcuts.adoc[Keyboard shortcuts] for the bindings.

== Showing and hiding the preview

Toggle Preview (`view.toggle_preview`) shows or hides the preview.
The PDF is a way of showing an open preview, so closing the preview while the PDF shows turns the PDF off.
It closes in the place it had before the PDF was turned on, docked or in its own window.
When it opens again, it shows the rendered page there.
This applies to Toggle Preview, the close button and the Preview button alike.
It is bound to kbd:[Cmd+K] then kbd:[V] on macOS and kbd:[Ctrl+K] then kbd:[V] on Linux and Windows.
This is a chord: hold the modifier for kbd:[K] only, release it, then press kbd:[V] on its own.

The preview is a pane docked to the right of the editor.
Its toolbar shows the title of the page being previewed and these buttons:

[cols="1,4"]
|===
|Button |What it does

|Pin or Unpin
|Keeps the preview on its current page, or lets it follow the active page again.

|Sync on or Sync off
|Turns scroll sync on or off.

|Detach or Dock
|Moves the preview into its own window, or back beside the editor.

|Close (×)
|Close Preview hides the preview, docked or in its own window, as Toggle Preview does.
It is in the header of the PDF pages too.
|===

== Following the active page

By default the preview follows the active page: open another tab, follow a link or go back, and the preview shows that page.
Each page's scroll position is remembered, so returning to a page puts you back where you were.

Pin Preview (`preview.pin`) keeps the preview on one page while you edit others.
This is useful for watching a page that includes the file you are editing.
Pin again to unpin.

== PDF preview

The preview pane can show the preview target as PDF pages instead of the rendered page.
The target is the pinned page, else the active one.
Toggle PDF Preview (`view.toggle_pdf_preview`) switches it on and off.
It is in the View menu and the command palette, and has no default key binding.
The preview's header also has a PDF button; while the PDF is shown it reads Page, to switch back.
Turning the PDF preview on also shows the preview if it was hidden.
Turning it off puts the preview back as it was before the PDF was turned on.
If turning the PDF on opened the preview, turning it off closes the preview again.
If the rendered page was showing, it shows again.
This is remembered across a restart.

Toggle PDF Preview Window (`view.toggle_pdf_window`) shows the PDF in its own window.
Run again, it turns the PDF off and puts the preview back as it was before.
Closing that window does the same.
It is in the View menu and the command palette, and has no default key binding.

The title bar has three buttons, Preview, PDF and PDF Window, each highlighted while that view is showing.
Preview shows the rendered page.
Clicked while highlighted, it closes the preview.
Clicked while the PDF shows, it switches back to the rendered page, docked.
If the PDF had opened the preview, the preview opens again as the rendered page.
Otherwise it shows the preview.
PDF shows the PDF docked beside the editor, moving it out of its own window if it is there.
PDF Window shows the PDF in its own window.
Clicked while highlighted, either of these buttons turns the PDF off.

The pages are typeset as Export Page to PDF typesets the page, with the same theme and fonts.
The theme is the page's `pdf-theme`, else `[pdf] theme`, found in `pdf-themesdir` or `[pdf] themes_dir`.
Standards such as PDF/A and PDF/UA are not applied, because they change nothing that is visible.
Unsaved edits are included.

After typing, the pages follow once the page settles, which is the preview's 100 ms pause.
They are typeset on a background worker, so the editor never waits.
An ordinary page takes about a tenth of a second more; the typesetting of the four-page reference article takes about 25 ms in a release build.

=== Zoom

The pages open fitted to the pane's width (Fit Width) and follow the pane as it is resized.
A toolbar above the pages has, from left to right:

* Zoom Out (−).
* The zoom as a percentage.
* Zoom In (+).
* Width, for Fit Width.
* Page, for Fit to Window: the largest page whole in the pane, which also follows its size.
* 100%, for Actual Size: one point of the page to one screen pixel.

Zoom In and Zoom Out step through 50%, 67%, 75%, 90%, 100%, 110%, 125%, 150%, 175%, 200%, 300% and 400%.
Below 50%, Zoom Out goes on down to 10%, a step of 1.25 times each.

The keys are the same as for images.
kbd:[Cmd+=] (or kbd:[Cmd++]) zooms in and kbd:[Cmd+-] zooms out.
kbd:[Cmd+0] is Actual Size and kbd:[Cmd+9] is Fit to Window.
On Linux and Windows use kbd:[Ctrl] in place of kbd:[Cmd].
They work anywhere in the workspace window while the PDF preview is shown, the editor included, and in the preview's own window once you click in it.
Fit Width has no key.
Zoom In, Zoom Out, Actual Size, Fit to Window and Fit Width are in the View menu and the command palette while the PDF preview is shown or an image is the active tab.

Holding kbd:[Cmd] (kbd:[Ctrl] on Windows and Linux) while scrolling zooms about the pointer.
A trackpad pinch zooms on Linux; macOS does not deliver pinch gestures to the application yet.
Zooming keeps the point under the pointer where it is, or the point at the centre of the pane for keys and buttons.

The zoom is kept while you edit and the pages are typeset again, for as long as the window is open.
It is not saved between sessions.

Each page is first drawn at 2048 pixels on its longer side.
This is sharp up to about 240% on a standard display and about 120% on a Retina or other 2× display.
Above that, the pages in and near the view are drawn again, sharper, a moment after the zoom or the scrolling stops.
That redrawing is limited to 16 million pixels a page.
This is about 580% of an A4 page on a standard display and about 290% on a 2× display, so very high zooms on a 2× display are a little soft.

Clicking a line goes to its source at any zoom.

Clicking a line of text on a page puts the caret at the start of the paragraph, heading or other block that line came from.
When the line came from an included file, that file opens, as it does when you click a block in the rendered preview.
Lines that come from the template, such as headers, footers and the generated parts of the title page, have no source.
A click on one of them goes to the nearest line above it that has one.

When the page cannot be typeset, for example because the theme is missing, the pane says why instead of showing pages.
Pinning, detaching and docking work as they do for the rendered preview.
Scroll sync does not apply to the PDF pages.
See xref:pdf-export.adoc[Exporting to PDF] for the theme and font rules.

== Detaching the preview

Detach Preview (`view.detach_preview`) opens the preview in its own window, which you can put on a second screen.
Closing that window docks the preview again.
The docked and detached views always show the same page.

== Scroll sync

Scroll sync works in both directions.

* Moving the caret in the source scrolls the preview to the block that contains it.
* Scrolling the preview moves the source to the topmost visible block.

Toggle Preview Scroll Sync (`view.toggle_scroll_sync`) turns both directions off and on.

== Click to source

Clicking a block in the preview places the caret at that block's source.
When the content came from a partial, the partial opens in a tab at the right line, so you edit the file that holds the text.

== Links

Clicking a link in the preview does the following.

[cols="2,4"]
|===
|Link |Result

|An `xref:` that resolves
|Navigates to the target page. The move is recorded in back and forward history.

|An `xref:` that does not resolve
|It is drawn with a wavy underline in the danger colour. Clicking it shows "This reference does not resolve."

|An external link
|Opens in the browser.

|A link to a file
|Opens in the system's default application.
|===

A missing image shows a placeholder that reads "Missing image: " followed by its target.

== When it updates

The preview re-renders 100 ms after the last edit to the page or to any file it includes.
It reads open buffers, so unsaved edits show immediately.
A render that a later edit has overtaken is discarded, so old text never flashes back.

Includes resolve through the Antora catalog.
That covers `partial$` and `example$` targets, and qualified ids such as `include::developer:example$flow.mmd[]` and `include::other:partial$x.adoc[]`.
Images and attachments are found in a module's `images` and `attachments` directories, and also in the older `assets/images` and `assets/attachments`.
When both hold a file with the same name, the standard directory wins.
See xref:antora-support.adoc[Antora support].

== Section numbers

With `:sectnums:`, sections are numbered as Asciidoctor numbers them, in the preview, the HTML from the command line and PDF export alike.
Special sections, such as a `[preface]`, `[glossary]` or `[bibliography]`, and the sections inside them are not numbered and do not count towards the chapters.
An `[appendix]` is lettered `Appendix A:`, with its sections `A.1.`; `appendix-caption` changes the word.
`sectnumlevels` (3 unless set) limits the levels that show a number; deeper sections are counted but show none, and the table of contents agrees.
Blocks are labelled from `figure-caption`, `table-caption`, `example-caption` and `listing-caption`; unsetting one removes the label and the number, and setting one changes the word.
See xref:pdf-export.adoc[Exporting to PDF] for the details.

== Source blocks

A source block with a language is highlighted with the same tree-sitter grammars as the editor.
The languages are those listed in xref:using-the-editor.adoc#the-editor[the editor description].

== Diagrams

Diagram blocks are rendered in the preview.
Every diagram renders on your computer.
Mermaid runs inside AdocFoundry, and Graphviz, PlantUML and D2 use the tools installed on your `PATH`, or at the paths set in `[tools]`.
Nothing is sent to an online rendering service.

[cols="2,2,3"]
|===
|Block style |Renderer |Needs

|`mermaid`
|In process
|Nothing. There is no browser, Node.js or Java.

|`graphviz`, `dot`
|`dot -Tsvg`
|Graphviz, on the `PATH` or set as `[tools] dot`.

|`plantuml`, `uml`
|`plantuml`
|PlantUML, on the `PATH` or set as `[tools] plantuml`.

|`d2`
|`d2`
|D2, on the `PATH` or set as `[tools] d2`.
|===

While a diagram renders, the preview shows its source.
If the tool is missing or fails, the source stays and the reason is shown with it.
The preview updates when a diagram finishes, so the page never waits on one.

Rendered diagrams are cached by a checksum of their source and options in `<workspace>/.cache/adocfoundry/diagrams/`.
A diagram drawn by Graphviz, PlantUML or D2 is also keyed by the program that drew it and the page's folder, so a different or upgraded tool draws it afresh.
The `.cache` folder is skipped by workspace discovery by default.

TIP: On macOS an application started from the Dock does not see your shell's `PATH`, so a Homebrew tool is often not found.
Set the absolute path in the `[tools]` table of your user settings file, for example `dot = "/opt/homebrew/bin/dot"`.
The `plantuml` and `d2` keys work the same way.
These keys are read from the user settings file only; a workspace settings file that sets them gets a warning and is ignored.
If a configured path does not exist, the diagram shows its source with the reason, for example "graphviz diagrams need `/opt/homebrew/bin/dot`, which does not exist".
If the setting is empty and the tool is not on the `PATH`, the reason is "... which was not found on the PATH".
Changing these settings takes effect when settings reload, and diagrams that failed are tried again.
A tool that was not found is looked for again a second later, so one installed while the application runs is used the next time the page is previewed.
Graphviz, PlantUML and D2 run in the page's folder, so a relative `!include` or `image=` path in a diagram resolves against the page, as it does with asciidoctor-diagram.

A Graphviz, PlantUML or D2 process that runs longer than 30 seconds is stopped, and the diagram shows its source with the reason, for example "`dot` did not finish within 30 seconds and was stopped".
A Mermaid diagram, which renders in process, is stopped at the same limit, and the diagram shows its source with the reason "`Mermaid` did not finish within 30 seconds and was stopped".
Set `diagram_timeout` in the `[tools]` table of your user settings file to change the limit; it is a positive number of seconds, and it is read from the user settings file only.
A tool that writes more than 32 MB to standard output or standard error is stopped too, and the diagram shows "<program> wrote more than 33554432 bytes and was stopped".
At most four diagrams render at once, and the rest wait in a queue, so a page with fifty diagrams does not start fifty processes.
The preview, the visual editor and PDF export share this limit.
If a diagram renderer crashes, the diagram shows its source with the reason "the diagram renderer crashed: ..." followed by what the crash reported.

A diagram that failed is not tried again each time the preview is rebuilt, only when its source or options change.
To try every failed diagram again, after installing a tool, fixing a file a diagram includes, or when a tool timed out on a busy machine, choose *View › Retry Failed Diagrams* (`preview.retry_diagrams`, also in the command palette).
It also looks for the diagram tools again, so a tool installed or upgraded since is used.
The application remembers the reasons for at most 256 failed diagrams beyond those of the pages it is showing; older ones are forgotten when a page is next parsed, and tried again when shown.
The rest of the page, the preview and exports carry on.
See xref:settings.adoc[Settings] for the keys.

== STEM

A block formula is typeset and drawn as an image on a white card, black on white in either theme.
While it renders, the source shows.
If it fails, a short message shows with the source.
An inline formula (`stem:[…]`, `asciimath:[…]` or `latexmath:[…]`) is drawn as its typeset image in the line of text.
It is sized to the text beside it and sits on that text's baseline.
A formula taller than one and a half lines is drawn smaller, so the line keeps its height.
Hovering over it shows its source in a tooltip.
In the dark theme an inline formula is drawn black on a small white backing, as block formulas are.
In the light theme it has no backing.
Until an inline formula has rendered, or when it cannot be converted, it shows as its source in a code style.
In the visual editor, a typeset inline formula is one step for the caret, like other macros, and copying it copies its source.
To edit the formula itself, change its source.
Formulas are cached like diagrams.
See xref:pdf-export.adoc#stem[Exporting to PDF] for the notation rules.

== Known limits

* The preview is read-only.
To edit the rendered page, use the visual editor; see xref:visual-editing.adoc[Visual editing].
* The preview has no settings of its own.
It follows the editor theme.
* The preview is a native approximation of Asciidoctor's output, not a copy of it.
The project's fidelity harness compares the two over a corpus of pages; see xref:developer:testing.adoc#render-tests[Testing].

== Exporting to HTML

Export Page to HTML… (`export.html_page`) writes the active page as a standalone HTML file.
It is in the File menu and the command palette, and has no default key binding.
It opens a save dialog, suggesting the page's name with an `.html` extension, in the page's folder.

The file is what `adocfoundry-cli render` writes for the page: the preview's view tree as Asciidoctor-shaped HTML.
The difference is that local images, diagrams and formula images are embedded in the file as `data:` URIs instead of `file://` addresses, so it opens in another folder, on another machine, or as an attachment to a message.
Remote images (`http` and `https` addresses) stay links.
A local file that cannot be read, or that is not an image (PNG, JPEG, GIF, SVG, WebP, BMP, ICO or AVIF), keeps its `file://` address.

The export reads the open buffer, so unsaved edits are included.
It waits until the render is current and every diagram has rendered, then writes the file in the background, so the application stays responsive.
When it finishes, a notification says "Exported page.html" and has an Open button that opens the file with the system, normally in the browser.
If it fails, the notification says "HTML export failed:" followed by the reason, and names the file.
Closing the page before the file is written reports that it was closed.

Unlike PDF export, it needs no typesetter.

With `:icons: font`, admonitions and inline icons are written as Asciidoctor writes them: `<i class="fa icon-note" title="Note"></i>` in the admonition's icon cell, and `<span class="icon"><i class="fa fa-heart"></i></span>` for `icon:heart[]`.
A Font Awesome stylesheet, such as an Antora site's, draws them.
The file links no icon font, so it shows each admonition's label in its icon's place, and inline icons are not drawn.
A block with an `icon` attribute keeps its text label.
The native preview is unchanged.

== Rendering from the command line

`adocfoundry-cli render` writes a page as the preview renders it.
See xref:command-line.adoc#render[Command line].
