= Language server
Paul Snow
:revnumber: 0.0.0
:description: adoc-ls, the Language Server Protocol server built from the AdocFoundry engine, and the Zed extension that uses it.

`adoc-ls` is a language server that speaks the Language Server Protocol over standard input and output.
It runs on the AdocFoundry engine, so it gives the same answers as the desktop editor and the Problems panel.

[source,sh]
----
adoc-ls --stdio
adoc-ls --version
----

The binary name, `--stdio` and the three command ids that existing clients hold in code actions are unchanged.
Its capabilities are a superset of before.

== How it works

The server keeps an engine instead of its own state.

* Workspace folders from `initialize` are opened in the engine. The server answers `initialize` once indexing finishes, after at most 120 seconds.
* `didOpen` opens the client's buffer in the engine. The file need not exist. The buffer is the client's from then on: a change to the file on disk never replaces it (the editor reloads its buffer and sends the change, if it does), and the engine keeps no undo history for it.
* Each incremental change becomes one edit to the engine document.
* `didClose` closes the engine document, which reverts to the file on disk.
* If the user settings file or the workspace's `.adocfoundry.toml` does not parse, or the workspace cannot be opened, the server says so with a `window/showMessage` warning naming the file, after answering `initialize`. A user settings file that does not parse gives the default settings.

The server lets the engine catch up whenever the connection has been quiet for 50 ms.
It also does so between messages once something the engine keeps is due, or a worker or the file watcher has sent it something, and publishes what changed.
The diagnostics of a typed change are published once the engine has diagnosed the new text, after typing pauses, never the previous text's diagnostics under the new version.

== Features

* Diagnostics, as described in xref:diagnostics.adoc[Diagnostics]. They are the engine's, with the same codes and severities as the Problems panel. The server publishes them for the changed page and for every other open page whose diagnostics changed.
* Go to definition for xref, include and image targets and attributes.
* Hover.
* Completion, triggered by `:`, `$`, `#`, `/`, `<` and `{`.
* Document symbols and workspace symbols.
* Find references (`textDocument/references`).
* Rename an anchor (`textDocument/rename`).
* Update links when a file is renamed (`workspace/willRenameFiles`).
* Spelling hints and quick fixes, described below.
* Code actions and commands, described below. Code actions honour the kinds the client asks for (`context.only`): the spelling fixes are quick fixes, and the preview actions have the empty kind.

Hover, definition, completion and symbols behave as before.

=== Find references

On a page, find references lists the xrefs that link to it, including links through its `page-aliases`.
It also lists the include directives that include it.
Those may be relative, written through a declared attribute, or Antora resource ids such as `partial$x.adoc`.

On an anchor (`[[id]]` or `[#id]`), or on a reference to one, it lists every reference to that anchor.

=== Rename

Rename on an anchor id renames the anchor and every reference to it.
Anywhere else the server refuses with an error.
To rename a page, rename its file.

The server registers `workspace/willRenameFiles` for `+**/*.{adoc,asciidoc,ad}+` files.
It returns the edits to the xrefs, nav entries and includes that name the file, and the client moves the file.
Includes written through an attribute are left as written.
The edits are worked out from the text as typed, typing not yet indexed included.
When the edits cannot be worked out, for example because a file that names the page changed on disk and has not been read again yet, the server answers with an error naming the reason, so the client does not move the file and leave its links behind.

== Commands

`adoc.renderPreview`, `adoc.renderLivePreview` and `adoc.stopLivePreview` render an HTML preview, once or re-rendered on save, and stop the live preview.
They render through Asciidoctor whenever `tools.asciidoctor` is set in the user settings file or `asciidoctor` is on `PATH`.
Otherwise they render through the engine's view tree, with diagrams and, in builds with Typst, typeset STEM.
See xref:settings.adoc[the settings].
A render through Asciidoctor is stopped after 60 seconds.
The system browser is started apart from the server's standard input and output, which carry the protocol, and the server does not wait for it.

`adoc.checkWorkspace` publishes the diagnostics of every file with problems, open or not.
A later check clears the problems of a file that is not open once they are fixed.
It returns `{ files, problems }`.

`adoc.exportPdf` exports a page to PDF, or with `component: true` its component version as a book.
It takes `{ uri, component?, output, theme?, standards? }` and reports with `window/showMessage`.
A page the client does not have open is opened only for the export and closed afterwards.
It is advertised only when the server is built with Typst.

`adoc.spelling.addToWorkspace` and `adoc.spelling.addToUser` add a word to the workspace dictionary (`.adocfoundry-words.txt`) or the user dictionary (`spelling-words.txt` beside the user settings file).
Each takes `[uri, start, end]`, the page and the byte offsets of the word.
A range that is no longer a misspelt word, because the page changed since the action was listed, is refused with an error and nothing is added.

== Spelling

The server publishes misspelt words as Hint diagnostics with the code `adoc.spelling`.
Each has a quick fix, "Change to '<word>'" for every suggestion, and fixes that run the two commands above.
Misspellings are not in the Problems panel or in `adocfoundry-cli check`.
See xref:using-the-editor.adoc#spelling[Spelling] for what is checked and for the dictionaries.

== Settings

The server reads the same files as the application: the user settings file and the workspace's `.adocfoundry.toml`.
If either file does not parse, the server warns, as described in <<_how_it_works,How it works>>.
Git is off unless the user settings file sets `[git] enabled = true`.
`editor.auto_save` has no effect in the server, which never saves a file; the editor saves.

== Builds

The default build is lean, with no Typst and no Git.
On macOS arm64 it is 32.4 MB and 237 crates.
Build with `--features typst,git` to add PDF export, typeset STEM and Git.
That build is 88.0 MB and 535 crates.

[source,sh]
----
cargo install --git https://github.com/bovinemagnet/AdocFoundry adoc-ls
cargo install --git https://github.com/bovinemagnet/AdocFoundry adoc-ls --features typst,git
----

`cargo xtask layers` checks that the default build compiles neither Typst nor Git.

== Zed

The Zed extension "AsciiDoc and Antora" (ID `asciidoc-antora`, https://github.com/bovinemagnet/zed-asciidoc-antora[zed-asciidoc-antora]) provides AsciiDoc highlighting and starts `adoc-ls`.
It uses an `adoc-ls` on your `PATH` when there is one.
Otherwise it downloads `adoc-ls` from the latest AdocFoundry release and keeps it up to date.
The release archives cover Linux, macOS and Windows on x86-64 and AArch64.
If the latest release cannot be fetched, the extension falls back to its most recent earlier download.

The release archives are built with Typst and Git.
The downloaded server therefore has PDF export, typeset STEM and Git, unlike the default build described in <<_builds,Builds>>.

Zed's `lsp.adoc-ls.binary` setting can name another binary instead.
To run your own build, install it on your `PATH` as described in <<_builds,Builds>>.

The server began life inside `zed-asciidoc`.
It now ships from AdocFoundry, and `zed-asciidoc` is only the thin extension.

== Other editors

Any editor that can start a stdio language server for `.adoc` files can use `adoc-ls`.
Point it at the `adoc-ls` binary with the `--stdio` argument.

== Consistency with the command line

A test runs `adocfoundry-cli check` and `adoc-ls` over the same fixtures and asserts that they report the same diagnostics.
See xref:command-line.adoc[Command line] and xref:developer:testing.adoc[Testing].
