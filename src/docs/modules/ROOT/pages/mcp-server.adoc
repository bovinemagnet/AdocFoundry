= MCP server
Paul Snow
:revnumber: 0.0.0
:description: adoc-mcp, a Model Context Protocol server that lets assistants read, check and, if allowed, edit an Antora documentation workspace.

`adoc-mcp` is a Model Context Protocol (MCP) server.
It speaks MCP over standard input and output, or over MCP's Streamable HTTP transport on this machine.
It runs on the AdocFoundry engine, so an MCP client such as an assistant gets the same answers as the desktop editor, the xref:command-line.adoc[command line] and the xref:language-server.adoc[language server].

[source,sh]
----
adoc-mcp <root>… [--allow-write] [--http <addr>]
adoc-mcp --version
----

== Running it

Give it one or more roots.
A root is a directory.
A relative root is taken from the current directory.

The server indexes the workspace before it serves anything.
Settings come from the user settings file and each workspace's `.adocfoundry.toml`, as in the application.
See xref:settings.adoc[Settings].

By default the server only reads.
The write tools are offered only with `--allow-write`.

The server also keeps every file it reads on a tool's behalf inside the roots, not only the paths a tool is given.
This covers the files a page includes (nested includes, and includes through a symbolic link that leads outside the roots), the images, theme and fonts of a PDF export, and any other file the export asks for.
A refused include is left out of the page.
A refused image is shown as its alt text, and the export reports a warning such as "image is outside the workspace roots".
A refused PDF theme, or a theme that `extends` one, fails the export with an error saying the file is outside the workspace roots.

Graphviz, PlantUML and D2 diagrams are not rendered, because those tools can read files themselves.
Mermaid diagrams still render, as they are drawn inside the server.
The application, `adocfoundry-cli` and `adoc-ls` are not restricted in this way.

== Configuring a client

Most MCP clients take a list of servers as JSON.
Add AdocFoundry like this:

[source,json]
----
{
  "mcpServers": {
    "adocfoundry": { "command": "adoc-mcp", "args": ["/path/to/docs"] }
  }
}
----

To allow writing, add the flag:

[source,json]
----
"args": ["/path/to/docs", "--allow-write"]
----

[#http]
== Serving over HTTP

A client that connects to a running server, rather than starting one, uses the HTTP transport.
Start the server with `--http` and a loopback address:

[source,sh]
----
ADOC_MCP_TOKEN=choose-a-secret adoc-mcp /path/to/docs --http 127.0.0.1:8765
----

The server prints the address it listens on, such as `adoc-mcp: listening on \http://127.0.0.1:8765/mcp`.
Port `0` picks any free port.

The transport serves this machine only:

* The address must be a loopback address: `127.0.0.1`, `[::1]` or `localhost`. Any other address is refused at start-up.
* Every request must carry `Authorization: Bearer <token>`. A request without it, or with the wrong token, gets `401 Unauthorized`.
* The `Host` header must name a loopback host, so a web page cannot reach the server through DNS rebinding.

The token is the value of `ADOC_MCP_TOKEN`.
If that is unset or empty, the server makes a random token and prints it once, as `adoc-mcp: token <token>`.

The tools, the write flag and the path limits are the same as over standard input and output.
Every client shares one engine.
Ctrl-C or `SIGTERM` stops the server.

Clients take the server's URL and the token's header:

[source,json]
----
{
  "mcpServers": {
    "adocfoundry": {
      "url": "http://127.0.0.1:8765/mcp",
      "headers": { "Authorization": "Bearer choose-a-secret" }
    }
  }
}
----

== Read-only tools

These tools are always offered.

[cols="2,3,4"]
|===
|Tool |Arguments |Result

|`list_components`
|None.
|Each component version: name, version, title, display version, start page and nav files.

|`get_nav`
|`component`, `version?`
|The navigation trees. With no `version`, the component's latest version is used. Each entry has its title, resource id and page path.

|`read_page`
|`path` or `resource_id`, `from?`
|The page's text, title, attributes and includes. Each include has its target and the file it resolves to. If the engine holds unsaved edits, the text is the engine's buffer. A `resource_id` is `version@component:module:family$path`. `from` names the page that a partial id is read from.

|`resolve`
|`target`, `from`
|What an xref, include or image target resolves to from a page, or that it does not. The target is a macro as written, such as `include::partial$x.adoc[]`, or a bare xref target.

|`check`
|`scope?`, `fail_on?`, `cursor?`, `limit?`
|The workspace's diagnostics, the same array that `adocfoundry-cli check --format json` prints, and `failed`. `failed` is true when any diagnostic meets `fail_on`, which is `error` (the default) or `warning`. It is judged over every diagnostic, not only the page. The answer is paged: see <<paging>>.

|`symbols`
|`query`, `cursor?`, `limit?`
|Workspace symbols, paged: see <<paging>>.

|`search`
|`query`, `regex?`, `case_sensitive?`, `whole_word?`, `scope?`
|Matches, each with its path, line and line text.

|`render_page`
|`path`, `format?`
|The page as the engine renders it: plain text (`text`, the default) or HTML (`html`).

|`git_status`
|None.
|Each root's branch and changed AsciiDoc files, as `adocfoundry-cli git-status --format json` gives them.

|`link_graph`
|`scope?`, `path?`, `depth?`, `partials?`, `nav?`, `orphans?`, `unresolved?`
|The link graph, as `adocfoundry-cli graph` prints it in JSON. `scope` is `workspace` (the default), `page` or `path`; a `page` scope needs `path`, absolute or relative to the first root, and follows links both ways to `depth` (1 to 3, default 1). A `path` scope needs `path`, where the path starts, and `to`, where it ends, and follows links only in their direction unless `directed` (a boolean, default true) is false; it answers with the same JSON as `adocfoundry-cli graph --path`, including its `path` array, or `{ "path": null }` when there is none, and `format: svg` draws just the path. See xref:graph-view.adoc#_the_path_between_two_pages[The path between two pages]. `partials`, `nav` and `orphans` default to true and `unresolved` to false. Nodes and edges are each cut at 500. When one is cut, the answer carries `truncated` saying how many were shown, and `incomplete: true`. `format` is `json` (the default) or `svg`, and `dark` (a boolean, default false) draws the SVG for a dark background. With `svg` the answer is `{ "svg": "<svg …>" }`, the image described in xref:graph-view.adoc#_export_the_graph[Export the graph]; an SVG over 200,000 bytes is refused with a message suggesting `scope: page`. See xref:graph-view.adoc[The link graph].
|===

[#discovery]
== Finding your way around

These read-only tools help a client discover a workspace before it reads or edits.
All four answer with `schema_version: 1` and `workspace_revision`.
Ranges are byte offsets, `{ "start", "end" }`: the first byte, and just past the last.

[cols="2,3,4"]
|===
|Tool |Arguments |Result

|`list_pages`
|`root?`, `component?`, `version?`, `module?`, `family?`, `cursor?`, `limit?`
|Antora resources, in resource-id order: component, version, module, family, path. The list is paged, with at most 500 items: see <<paging>>. `next_cursor` resumes it while the workspace revision stands. `version` is `~` for the versionless version, or a version name such as `3.0`. Without it every version is listed, and the versionless and numbered versions are never mixed up. `version` and `module` need a `component`, otherwise the call is refused with `invalid_argument` rather than guessing. `family` is `page` (the default), `partial`, `example`, `image`, `attachment` or `any`. `root` limits the list to files beneath a folder. An unknown component or version is `not_found`. Each item gives `resource_id`, `component`, `version` (null for the versionless one), `module`, `family`, `relative_path`, `path` (relative to the first root), `title` and `in_navigation`. `in_navigation` is true when a navigation file listed in the page's own component version's `antora.yml` lists the page. It is null for anything but a page.

|`get_outline`
|`path` or `resource_id`, `from?`, `headings?`, `anchors?`
|A page's title with its sections nested by level. `headings` and `anchors` default to true. `from` names the page that a partial id is read from. Each node has `kind` (`document` or `section`), `title`, `level`, `id`, `range`, `title_range` and `children`. The `id` is the one a reference reaches the section by: its anchor, else the id Antora generates from its title. For a navigation file (`kind: navigation`) the outline is its entries instead. An entry has `kind` `page` when it links and `category` otherwise, and a `target`, the xref target. `anchors` lists the anchors the page declares, each with `id`, `range` and `conditional`. `conditional` is true when the anchor is declared inside `ifdef`, `ifndef` or `ifeval`, so it may not be in the build.

|`get_page_context`
|`path` or `resource_id`, `from?`, `navigation?`, `includes?`, `incoming?`, `attributes?`, `text?`
|What surrounds a page. The first four booleans default to true. `text` defaults to false, and without it the page's text is not sent. The answer has `identity`, `title`, `navigation`, `includes`, `incoming` and `attributes`. `identity` gives the component, version, module, family, relative path and `page-aliases`, and is null for a file outside every component. `navigation` gives `in_navigation` and `places`: each navigation file that lists the page, with the entry's title, the titles above it and those beneath. Each of `includes` gives the `target` as written, its `range`, `resolved`, `resolves_to` and `resource_id`. `incoming` counts the `xref`, `nav` and `include` references that reach the page; `find_references` lists them. See <<attributes>> for `attributes`.

|`find_references`
|`path` or `resource_id`, `from?`, `anchor?`, `kinds?`, `cursor?`, `limit?`
|The exact references that reach a page, paged like `check`, with `total`: see <<paging>>. These are xrefs in pages and partials (`xref`), entries of navigation files (`nav`) and include directives (`include`). With `anchor`, the references to that anchor of the page are listed instead (`anchor`): `+<<id>>+`, `+xref:#id[]+` and `+xref:page.adoc#id[]+` from anywhere. `kinds` is a list of `xref`, `include`, `nav` and `anchor`. Each item gives `kind`, `path` (the file it is written in), `resource_id`, `range`, `line`, `column`, `target` as written and `confidence`. `line` and `column` are one-based, and the column counts bytes. `confidence` is `resolved`, because every reference listed was resolved to the page. The references come from the index, resolved one by one, and never from the link graph's merged edges. A dynamic target that cannot be resolved is not listed. A path and a resource id together are refused as ambiguous.
|===

A listing reads only the resources it returns.
A page of results from a workspace of 20,000 pages takes a couple of milliseconds.

[#attributes]
=== Attributes in a page's context

`attributes.declared` lists the attributes declared for the page, both in the page and in its component version's `antora.yml` (`asciidoc.attributes`).
Each has:

* `name`.
* `value`, as written.
* `unset`, true for `:name!:`.
* `dynamic`, true when the value refers to another attribute, such as `+{product}+ Suite`.
* `source`, which is `page` or `component`.
* `defined_in`, where it is declared.
* `range`, for an attribute declared in the page.

`effective_values` is `unknown`.
The value a build sees also depends on the playbook, the command line, soft and hard sets, and the order of declarations.
These are not yet traced (issue #99), so no effective value is given or invented.

[#quality-audit]
== Auditing quality

`quality_audit` is a read-only tool.
It audits the documentation's quality exactly as `adocfoundry-cli audit --format json` does.
See xref:command-line.adoc[the command line] and xref:quality-audit.adoc[The quality audit].

The policy is the workspace's own `.adocfoundry.toml` `[quality]` table, read from the first root as the command line reads it.
The user's settings file is never read, so every client and CI see the same result.

[cols="2,3,4"]
|===
|Tool |Arguments |Result

|`quality_audit`
|`component?`, `version?`, `rules?`, `severity?`, `include_excluded?`, `require_complete?`, `fail_on?`, `cursor?`, `limit?`
|The audit report, with its findings paged: see <<paging>>.
|===

The arguments are:

`component` and `version`::
The scope. `version` is a version name such as `3.0` and needs a `component`. Without it every version of the component is audited. `~` is refused, as an audit's scope cannot select the versionless version alone.

`rules`::
List only findings with these codes. A code is a rule id such as `quality.page.missing-title`, or a diagnostic code such as `adoc.unresolved-xref-file`. The counts stay the whole report's.

`severity`::
List only findings at least this severe: `info`, `warning` or `error`.

`include_excluded`::
Also list the findings the policy excludes, with their reasons. It is false by default, though `counts.excluded` is always given.

`require_complete` and `fail_on`::
Override the policy, as `--require-complete` and `--fail-on` do.

`cursor` and `limit`::
Page the findings.

The answer is the audit report.
It has its own `schema_version`, the scope, the rules and their severities, the providers and their states, `completeness` with any gaps, `counts`, the navigation `coverage`, `skips` and `findings`.
The findings are paged, at most 500 a page.
`findings_total` is how many the filters take, and `next_cursor` resumes the list.
Each finding has a `region` (one-based lines and character columns) besides its byte range.

Every page carries the whole report's completeness, counts and coverage.
A client that reads only one page still sees whether the audit is partial.

The tool adds these fields:

* `verdict`, which is `pass`, `fail` or `untrustworthy`, as the policy judges the report.
* `exit_code`, what the command line would exit with: 0, 1 or 2. It is also 2 when the `[quality]` settings are invalid, which `policy_problems` lists.
* `outcome`, which is `pass` only for a complete audit. It is `pass_partial` when nothing failed in what was audited but not everything was, for example when an enabled optional provider cannot run in this build. A partial report is never taken for a plain pass. The other outcomes are `fail` and `untrustworthy`.
* `workspace_revision`.

A skipped dynamic construct, such as a navigation file with an `include::`, is counted and listed under `skips`.
It never makes the audit partial by itself.

The tool runs no optional provider, such as Vale or external links, and makes no network request.
A cursor belongs to its arguments and policy, so changing a filter or an override starts again.
Use `check` for diagnostics alone.

[#impact]
== Analysing impact

`analyse_impact` is a read-only tool.
It gives the documentation impact analysis exactly as `adocfoundry-cli impact` reports it.
See xref:command-line.adoc#impact[the command line], which documents the impact kinds, statuses and completeness gaps in full.

[cols="2,3,4"]
|===
|Tool |Arguments |Result

|`analyse_impact`
|`source`, `component?`, `version?`, `include_provenance?`, `max_depth?`, `cursor?`, `limit?`
|The impact report, with its impacts filtered and paged: see <<paging>>.
|===

The arguments are:

`source`::
Required. It names what changed, as exactly one of these:
+
* `{ "type": "git_refs", "base": "<ref>", "head": "<ref>" }` compares two local revisions. They are read from Git objects alone. Nothing is fetched or checked out, and the working tree is never read.
* `{ "type": "working_tree" }` compares `HEAD` with the working tree, including the server's unsaved buffers.
* `{ "type": "paths", "paths": ["..."] }` takes the files named, against the working tree, with no base revision. Each path must be inside the roots.

`component` and `version`::
List only impacts in that component or version. `version` needs a `component`. `~` is the versionless version. The counts and completeness stay the whole report's.

`include_provenance`::
True by default. With false, impacts leave out `via` and `source`, for a shorter answer.

`max_depth`::
How many includes deep the analysis follows. It is 32 by default.

`cursor` and `limit`::
Page the impacts, at most 500 a page.

The answer is the impact report.
It has its own `schema_version`, the `source`, `completeness` with any gaps, `changes`, `impacts` and `counts`.
`impacts_total` is how many the filters take.
`next_cursor` resumes the list, and `truncated` is present while more follow.
`workspace_revision` is given too.

Every page carries the whole report's completeness and counts.
A client that reads only one page still sees whether the analysis is partial.
A page's prose change never reaches the pages that merely link to it.

The errors are:

* `not_found`, for a ref that does not exist.
* `unavailable`, for a Git source when the workspace is in no Git repository. Use `paths` instead.
* `outside_workspace`, for a path outside the roots.
* `invalid_argument`, for a `version` without a `component`.

The tool never changes the repository, posts comments or makes a network request.

[#publication]
== Checking publication

`validate_publication` is a read-only tool.
It reports whether the documentation is ready to publish.
It is put together from what the engine already checks, and has no rule of its own.

[cols="2,3,4"]
|===
|Tool |Arguments |Result

|`validate_publication`
|`component?`, `version?`
|The audit, the navigation, the profiles and what was not checked, with an `outcome`.
|===

The scope is taken as `quality_audit` takes it.
The answer has these parts:

`audit`::
The quality audit as `quality_audit` makes it, under the workspace's own policy. It gives its `outcome`, `exit_code`, `completeness`, `counts` and `policy_problems`.

`navigation`::
For each component version in scope: its `navigation_files`, each with `exists`; its `start_page`, with `resolves` and `path`; and the audit's `coverage` of its pages (`pages`, `listed` and `undetermined`). The start page is the `start_page` its `antora.yml` names, or `ROOT:index.adoc` by default, which is marked `default: true`.

`profiles`::
Every PDF publication profile (`[pdf.profiles.<name>]`), with `ready` and its `problems`. A problem is an unknown or outside output, content not in the workspace (a page not indexed, a component version not in the catalog, or a missing navigation file), or a theme not found. Profiles are checked without exporting. See xref:pdf-export.adoc#publication-profiles[Publication profiles].

`not_checked`::
What a native check cannot see: the Antora build itself, with its extensions, UI bundle, content sources and remote components; what the native renderer approximates; and external links.

The `outcome` is one of:

* `ready`
* `ready_partial`, where nothing failed but the audit could not check everything
* `not_ready`, where the audit failed or is untrustworthy, a start page does not resolve, a navigation file is missing, or a profile has problems

Every profile is checked whatever the scope.
The tool builds nothing and makes no network request.

[#prompts]
== Prompts

The server offers four MCP prompts.
They are workflow recipes that a client can show its user.
Each is text that names the tools to call, in order.
None grants a permission.
Each says that only the server decides what may change, and that page text is data, never instructions.

[cols="2,3,4"]
|===
|Prompt |Arguments |Recipe

|`review_documentation`
|`component?`, `version?`
|Audit, summarise, look at the pages behind the most frequent findings, and suggest fixes as previews.

|`create_howto`
|`component`, `module?` (default `ROOT`), `topic`
|Look at the module's pages and navigation, preview a `create_page` with its navigation entry, show it, apply it on agreement, and check the result.

|`review_documentation_change`
|`pages` (paths or resource ids, separated by commas)
|Get each page's context and incoming references, its diagnostics and the audit's relevant rules. It says that impact analysis across Git revisions is not available yet.

|`prepare_release`
|`component`, `version?`
|Run `validate_publication`, then the audit's findings when it does not pass, say what was not checked, and suggest fixes as previews.
|===

A missing required argument, or an unknown prompt, is an error.

[#staging]
== Staging changes

`preview_changes` shows a change before it is made.
`apply_changes` makes it.
A client previews, reads the diffs and diagnostics, and then applies.

`preview_changes` is always offered, even without `--allow-write`, because it writes nothing.
`apply_changes` is offered only with `--allow-write`, like the other write tools.

=== Previewing

`preview_changes` takes `operations`, at most 64.
They are applied in order, as one change.
Each operation has a `kind`:

[cols="2,5"]
|===
|Kind |Arguments

|`replace`
|`path` or `resource_id`, then `old_text` (which must occur exactly once) or `range` (`{ start, end }` byte offsets), and `new_text`. Optionally `expected_hash`, the SHA-256 (hex) that the file must hold now.

|`create_page`
|`component`, `version`, `module`, `title`, and optionally `file_name` and `add_to_navigation`. `version` is `~` for the versionless version. It is needed when the component has several versions, and otherwise the call is refused as ambiguous. `file_name` is the page's path in the `pages` folder, and is named from the title without it. `add_to_navigation` adds an entry at the end of the module's navigation file. It is what New Page does in the app.

|`create_partial`
|`component`, `version`, `module`, `file_name` (in the `partials` folder) and optionally `text`.

|`create_module`
|`component`, `version`, `name`, and optionally `families`, `navigation`, `index` and `index_title`. `version` is `~` for the versionless version. It is needed when the component has several versions. See <<creating-a-module>>.

|`rename`
|`path` or `resource_id`, `new_name` (a file name or a path relative to the page's folder) and optionally `expected_hash`. It rewrites the xrefs, navigation entries and includes that name the page, as Rename Page does.
|===

A navigation change is a `replace` on the navigation file, or `add_to_navigation`.

The answer has:

* `preview_id`, 32 hex characters and unguessable.
* `expires_at`, in seconds since 1970 (UTC), and `expires_in_seconds`, which is 15 minutes.
* `workspace_revision`.
* `files`, each changed file.
* `can_apply`, which is false on a server started without `--allow-write`, with a `reason`.

Each of `files` has:

* `kind`, which is `create`, `edit` or `move`.
* `path`, and `to` for a move.
* `resource_id`.
* `before_hash` and `after_hash`, both SHA-256.
* `diff`, whose lines start with `-`, `+` or a space. Lines left out are shown as `@@ n unchanged lines @@`.
* `diagnostics` that the file would have after the change. Each has `severity`, `code`, `message`, `line` and `column`.

The diagnostics are worked out on a copy of the workspace with the whole change made.
The preview writes nothing to disk, changes no buffer and indexes nothing.

A mistaken operation fails the whole preview.
Its message starts `operation n:`, and it carries the usual codes:

* `conflict`, when `old_text` is not in the page or `expected_hash` does not match.
* `invalid_argument`, for an ambiguous version or a file name with `..`.
* `not_found`, for an unknown module.

=== Applying

`apply_changes` takes `preview_id`, an optional `idempotency_key` and `save`, which is true by default.

Immediately before making the change, it checks again that:

* every path is inside the roots. A folder that has become a symbolic link out of them is refused with `outside_workspace`.
* every file still holds the text the preview saw. Otherwise the answer is `stale_preview`. This includes edits made since through the server's own buffers.
* every file to make is still absent. Otherwise the answer is `conflict`.

On any mismatch, nothing of the change is made.
Otherwise the change is made through the engine as one undo step, as the app makes it.

A preview can be applied once.
Afterwards, or once it has expired, or from another session, its id is unknown and answers `stale_preview`.
Applying again with the same `idempotency_key` returns the first answer instead of applying twice.

The answer has `applied`, `saved`, `changed` (the files changed, relative to the first root), `resource_ids` and `workspace_revision`.

=== What is and is not atomic

The checks, and the making of the change in the engine, are all or nothing.
Saving is not atomic across files: each changed page is saved in turn.
New files are written as they are made, as New Page writes them.

If a save fails, `apply_changes` answers `internal_error`.
Its `details` give:

* `applied: true`.
* `saved`, the pages written.
* `failed`, each page and its error.
* `recovery`, a note on what to do.

The unsaved pages keep the change in the server's buffers, where `read_page` shows it.
Once the cause is fixed, `edit_page` with no edits and `save: true` writes one.

=== Sessions and limits

Previews belong to the session that made them.
Over HTTP each session has its own, though all sessions share one engine and so the same buffers.
A change saved or left unsaved by one session is what the others read.

A session keeps at most 16 previews and 4 MiB of staged text.
Older previews are dropped to make room.
Previews expire after 15 minutes, and idempotency keys are kept as long.

Document text is data, never permission.
A page saying that the assistant may write grants nothing.
Only `--allow-write` does.

== Write tools

These tools, and `apply_changes` (see <<staging>>), are offered only with `--allow-write`.
Without it they are not listed.
A client that calls one anyway gets a tool error with the code `permission_denied`, and a message that names `--allow-write`.
Nothing in a page's text, and nothing in a client's request, can change this.

[cols="2,3,4"]
|===
|Tool |Arguments |Result

|`create_page`
|`component`, `version`, `module`, `title`, `file_name?`, `add_to_navigation?`, `expected_nav_hash?`, `save?`
|Makes a page through the engine's `page.new` command, the one the app's New Page invokes, so the page's place, name, navigation entry and undo are the app's. `version` is `~` for the versionless version. It is needed when the component has several versions, and otherwise the call is refused as ambiguous. `file_name` is the page's path in the module's `pages` folder. Without it the name is made from the title. With `add_to_navigation: true` an entry is added at the end of the module's navigation file. `expected_nav_hash` is the SHA-256 the navigation file must hold now, as a preview gave it. Otherwise the answer is `conflict`. With `save` (true by default) the navigation file and the page are written to disk. The page's file is made in any case, as New Page makes it. The page and its entry are one undo step. It applies at once. A page that exists already is a `conflict`. It returns `path`, `resource_id`, `navigation_file`, `changed` and `saved`.

|`create_partial`
|`component`, `version`, `module`, `file_name`, `text?`
|Makes a partial through the engine's `page.new_partial` command, as New Partial does. `file_name` is in the `partials` folder, and may include folders, such as `shared/limits.adoc`. The text, when given, is written as a second undo step and saved. A partial that exists already is a `conflict`. It returns `path`, `resource_id` and `include`. `include` has `from_its_module` (such as `+include::partial$shared/limits.adoc[]+`) and `from_anywhere`, the full resource id (such as `+include::3.0@product:admin:partial$shared/limits.adoc[]+`).

|`create_module`
|`component`, `version`, `name`, `families?`, `navigation?`, `index?`, `index_title?`
|Makes a module through the engine's `module.new` command, the one the app's New Module invokes. `version` is `~` for the versionless version. It is needed when the component has several versions, and otherwise the call is refused as `invalid_argument`. `families` lists the families to make besides `pages`, which is always made. Without it, `partials` and `images` are made. `navigation` (true by default) makes `nav.adoc` and lists it in `antora.yml`. `index` (true by default) makes `pages/index.adoc`, titled `index_title` or the name in title case. A name that exists is a `conflict`, and a bad name is `invalid_argument`. It applies at once, saves `antora.yml`, and is one undo step. It returns `module`, `path`, `made` (every file made), `descriptor` and `index_page` (its resource id).

|`edit_page`
|`path`, `edits`, `save?`
|Applies the edits in order. Each edit is `{ old_text, new_text }` or `{ range: { start, end }, new_text }`, and goes through the engine's `edit.replace_range` command. `old_text` must occur exactly once. If any edit fails, none of that call's edits stay. With `save: true` the page is written to disk. Otherwise the edits stay in the engine's buffer, and `read_page` shows them.

|`rename_page`
|`path`, `new_name`
|Moves the page and rewrites the xrefs, nav entries and includes that name it. Then it saves every file it changed. `new_name` is a file name or a path relative to the page's directory.

|`export_pdf`
|`path` or `component`, `output`, `theme?`, `standards?`
|Exports a page as an article, or a component version as a book. A component is `name` or `version@name`. The standards are `pdf-a-1b`, `pdf-a-1a`, `pdf-a-2a` and `pdf-ua-1`. It returns the output, the page count and any warnings.
|===

See xref:pdf-export.adoc[Exporting to PDF] for themes and standards.

=== Creating pages and partials

`create_page` and `create_partial` apply at once.
Use them when the client has the user's agreement already.
For a change of several files, or one the user should review first, use `preview_changes` with `create_page` or `create_partial` operations.
These stage the same plans.
Then call `apply_changes`.

Neither tool writes a file of its own.
The engine does, through the same commands as the app.

[[creating-a-module]]
`create_module` makes a module in an existing component version, as New Module does.
It applies at once and is not staged.
See xref:using-the-editor.adoc#new-module[Make a new module] for the folders, files and `antora.yml` change.

Making a project (`create_project`) waits for issues #291 to #295.
It is not offered yet.

=== Not offered yet

These are not offered, and the server does not list them:

* `create_project` waits for issues #291 to #295.
* `build_site` waits for the build command of issue #293 and a separate `--allow-build` flag (issue #334). `--allow-write` never implies it. Until then the server refuses `--allow-build` as an unknown option.
* Resource-change subscriptions wait for issue #335.

== Resources

Every page is a resource.
Its URI is a `file://` URI, and its media type is `text/asciidoc`.

`resources/list` is paged.
A page holds at most 500 resources, and the answer carries `nextCursor` while more follow.
Resources are ordered by Antora resource id and then path, with files outside any component first.
A cursor is opaque and follows the rules in <<paging>>.

A resource template, `+antora:{resource_id}+`, reads a page or a partial by its Antora id.

[#structured]
== Structured results

Every tool answers with its JSON as text content, so every client keeps working.
A session that negotiated MCP protocol version 2025-06-18 or later also gets the same JSON as `structuredContent`.
In that session `tools/list` gives each tool an `outputSchema`, which names its top-level fields and the ones always present.
A session on 2025-03-26 or 2024-11-05 gets text only, with no output schemas.

The server negotiates the version that the client asks for, when it supports it.

== Tool annotations

Each tool carries MCP annotations.

* The read-only tools have `readOnlyHint: true` and `openWorldHint: false`.
* `edit_page` and `rename_page` have `readOnlyHint: false` and `destructiveHint: true`.
* `export_pdf` has the same, and `idempotentHint: true`.

Annotations are hints for clients.
They never grant permission.
The server alone decides what runs.

[#paging]
== Pages of results

`check`, `symbols`, `list_pages`, `find_references`, `quality_audit` and `analyse_impact` take `cursor?` and `limit?`.
`limit` is at most 500, which is also the default.
Their answer adds:

* `total`, the number of items in the whole list. `list_pages` gives none, since counting would read every resource. `quality_audit` gives `findings_total` instead, and `analyse_impact` gives `impacts_total`.
* `next_cursor`, which you pass as `cursor` to get the next page. It is null on the last page.
* `workspace_revision`, the workspace revision that the list was made at.

While more pages follow, the answer still has `truncated: { shown, total }`.

A cursor is opaque.
It belongs to the query, meaning the same arguments, and to the workspace revision it was made at.
Once the workspace changes, an old cursor is refused with `invalid_argument` and a message that says it is stale.
A change is a page edited, added or removed, on disk or through the engine.
List again from the start.

The other lists are not paged.
`list_components`, `search` and the nodes and edges of `link_graph` are cut at 500, and carry `incomplete: true` when they are cut.

[#errors]
== Errors

A failed tool call is a tool error, with `isError: true`.
Its text is the message.
Its structured content is:

[source,json]
----
{ "error": { "code": "invalid_argument", "message": "…" } }
----

An error's structured content may also carry `details`, as `apply_changes` gives for a failed save.

The codes are stable.

[cols="2,5"]
|===
|Code |Meaning

|`invalid_argument`
|An argument is missing, malformed or contradictory, or a cursor belongs to another query or to an older workspace revision.

|`not_found`
|The page, component or resource does not exist.

|`outside_workspace`
|A path lies outside every root, or reaches outside through a link.

|`permission_denied`
|A write tool was called without `--allow-write`.

|`conflict`
|Text or a file changed from what the request expected. For example, the `old_text` of `edit_page` is no longer in the page, an `expected_hash` does not match, a file to make now exists, or a save conflicts.

|`stale_preview`
|A preview's files changed since it was made, or its id is unknown, already applied, expired or from another session: see <<staging>>.

|`index_incomplete`
|A whole index of the workspace is still running.

|`unavailable`
|The server is busy, for example too many requests are waiting for the engine.

|`timeout`
|The request took too long.

|`result_too_large`
|The answer is too big, for example an SVG over 200,000 bytes.

|`internal_error`
|An unexpected failure.
|===

`resources/list` and `resources/read` are not tools.
A failure there is a JSON-RPC error, and its `data.code` carries the same code.

== Waiting for the engine

Every client shares one engine, and one request uses it at a time.
A request waits at most 30 seconds for another to finish with it, then answers `timeout`.
At most 16 requests wait at once.
More are answered `unavailable` straight away.
So a stalled request, such as a long PDF export or render, never holds up other clients indefinitely.

Renders, searches, Git status and exports keep their 120-second limit, after which they answer `timeout`.

== Limits and safety

* Every path, absolute or relative to the first root, must lie inside a root. The check is lexical and also follows symbolic links. Otherwise the call is refused with `outside_workspace`.
* The server makes no network requests. With `--http` it listens on a loopback address only, for requests that carry its token.
* Project scripts are never run.
* Lists are paged or cut at 500 items, as described in <<paging>>.
* Texts are cut at 200,000 bytes. The result then carries `truncated: { shown_bytes, total_bytes }`.
* Errors carry a stable code and the engine's message: see <<errors>>.
* A request waits at most 30 seconds for the engine, and at most 16 wait at once: see <<_waiting_for_the_engine>>.
* `validate_publication` and the prompts make no request and run nothing.
* A preview holds at most 64 operations, and expires after 15 minutes. A session keeps at most 16 previews and 4 MiB of staged text: see <<staging>>.

[#workflows]
== Example workflows

=== Adding a page

List the module's pages with `list_pages`.

[source,json]
----
{ "component": "product", "version": "3.0", "module": "ROOT" }
----

Read the outline of the module's navigation file with `get_outline`.
Then call `preview_changes` with a `create_page` operation.

[source,json]
----
{
  "operations": [
    {
      "kind": "create_page",
      "component": "product",
      "version": "3.0",
      "module": "ROOT",
      "title": "Rotating keys",
      "add_to_navigation": true
    }
  ]
}
----

Read the diffs in `files`.
When they are right, call `apply_changes` with the `preview_id`.
This needs `--allow-write`.

[source,json]
----
{ "preview_id": "<the id from the preview>" }
----

=== Reviewing quality before a release

[source,json]
----
{ "component": "product", "version": "3.0" }
----

Send this to `validate_publication`.
If the `outcome` is not `ready`, call `quality_audit` with the same scope, and page through the findings with `cursor`.

[source,json]
----
{ "component": "product", "version": "3.0", "severity": "warning" }
----

Fix what it finds with previews.

=== Checking what a change to a partial touches

Call `find_references` on the partial.

[source,json]
----
{ "resource_id": "product:ROOT:partial$note.adoc" }
----

Then call `get_page_context` on each page that includes it.

Calling `analyse_impact` with `paths` gives the same, with every page the partial renders into.

[source,json]
----
{ "source": { "type": "paths", "paths": ["modules/ROOT/partials/note.adoc"] } }
----
