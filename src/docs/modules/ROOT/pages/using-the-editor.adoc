= Using the editor
Paul Snow
:revnumber: 0.0.0
:description: The workspace, sidebar, editor, link following, search and replace, and page rename.

This page describes the source editor and the workspace around it.
The rendered preview has its own page, xref:preview.adoc[The preview], and editing the rendered page has another, xref:visual-editing.adoc[Visual editing].
Every action described here is an engine command with a stable id, so it also appears in the command palette (kbd:[Cmd+Shift+P] or kbd:[Ctrl+Shift+P]).
See xref:keyboard-shortcuts.adoc[Keyboard shortcuts] for the bindings.

== The workspace

When you open a folder, AdocFoundry discovers every `antora.yml` beneath it and indexes the AsciiDoc files on a background worker.
The window stays usable while indexing runs.
The status bar shows "Indexing…" only while the whole workspace is being indexed or file changes are being applied, not after every keystroke.
Plain AsciiDoc folders work too, with relative-path resolution only.

Folders named in `workspace.ignore` (by default `node_modules`, `.git`, `build`, `target` and `.cache`) are skipped.
See xref:settings.adoc[Settings].

AdocFoundry watches the workspace.
A file changed on disk is re-indexed, and `antora.yml` is re-read when it changes.
A buffer with unsaved edits is never overwritten: you are told that the file changed on disk and your buffer is kept.

== The sidebar

The sidebar has three tabs and an outline.

Navigation::
Each component version's navigation, nested as its `nav.adoc` files list it.
A line such as `product@2.0 · main` heads the panel, naming the active page's component version and branch.
A component that declares no `nav` in `antora.yml` shows its pages by module instead.

Modules::
Every module, with its families (pages, partials, examples, images and attachments) and their resources.

Problems::
Workspace diagnostics grouped by file, with a count in the tab title.
Click one to open the file at that location.
A row too long for the sidebar ends with an ellipsis, and hovering it shows the full text in a tooltip.
This applies to every panel in the sidebar.

Outline::
The sections of the active document.
For a navigation file, the outline is its navigation tree.

[[the-editor]]
== The editor

The editor is a source editor.
The rendered page is shown beside it by the preview; see xref:preview.adoc[The preview].
The Source, Visual and Split buttons beside the tabs switch a page to the visual editor, where you edit the rendered text in place; see xref:visual-editing.adoc[Visual editing].
It provides:

* Syntax highlighting from the AsciiDoc tree-sitter grammars.
The inline grammar is injected into paragraphs, titles, table cells and macro targets.
* Highlighting inside source blocks for Rust, Java, JavaScript, TypeScript, Python, Go, JSON, YAML, TOML, shell, SQL and HTML.
XML and Dockerfile blocks are not highlighted yet.
* Folding of sections, delimited blocks and lists, line numbers and soft wrap.
* Diagnostics as you type.
See xref:diagnostics.adoc[Diagnostics].
* Hover on xref, include and image targets, anchors and `+{attributes}+`.
* Completion after `xref:`, `include::`, `image::`, `{` and `#`.
* Undo and redo that treat a run of typing as one step.
Typed characters within 500 ms of each other coalesce.

Tabs follow the active document, so opening a page by any route (the sidebar, link following, the palette or a rename) shows it in a tab.
With the preview docked, the tab strip scrolls to keep the active page's tab in view, including when a page becomes active by following a link or through the outline.

Each tab has an X button that closes it, asking first if the page has unsaved changes.
Tabs are in the order the pages were opened.
Right-click a tab for a menu that acts on that tab, not necessarily the active one:

* *Close* closes the tab.
* *Close Others* closes every other tab.
* *Close Left* and *Close Right* close the tabs to its left or right.
* *Close Clean* closes every tab without unsaved changes.
* *Close All* closes every tab.

Items that would close nothing are greyed out, such as Close Left on the first tab.
Right-clicking the empty part of the tab bar offers only Close Clean and Close All.
The same commands are in the palette and act on the active tab; see xref:keyboard-shortcuts.adoc[Keyboard shortcuts] for their keys.
When any of the tabs to be closed has unsaved changes, you are asked once, naming them (for example "a.adoc and b.adoc have unsaved changes."): Discard closes them all and Cancel closes none.
Close Clean never asks, since it leaves unsaved tabs open.

The ← and → buttons at the start of the tab bar are Go Back and Go Forward through the places you have followed links to.
Each is greyed out when there is nowhere to go.

[[formatting-text]]
== Formatting text in the source editor

Bold (`Cmd-B` or `Ctrl-B`), Italic (`Cmd-I` or `Ctrl-I`) and Code (`Cmd-E` or `Ctrl-E`) toggle a mark around the selection in the source editor, with the same keys as the visual editor.
Highlight has no key and is in the command palette.
They work in Source mode and on the source side of Split mode.

* The constrained form (`+*bold*+`, `+_italic_+`, `+`code`+` and `+#highlight#+`) is used where it is valid.
Where it cannot be, such as part of a word (`+un**break**able+`), the unconstrained form (`+**+`, `+__+`, `+``+` and `+##+`) is used.
* Spaces at the edges of the selection stay outside the mark.
* If the selection is already marked, with its delimiters just inside or just outside it, the command removes the mark.
Another mark's delimiters do not count, so bolding an italic word gives `+_**word**_+`.
* A selection over several lines marks each line on its own, because a mark never runs across lines, which might be list items or block delimiters.
Blank lines are skipped.
If every line is already marked, all are unmarked; otherwise only the unmarked lines are marked.
* With nothing selected, an empty pair of delimiters is inserted with the caret between them, ready to type.

The marked text stays selected afterwards, so pressing the key again undoes the mark.
Each toggle is one undo step.

== Following links

Cmd-click (Ctrl-click on Linux and Windows), F12 or kbd:[Cmd+Enter] (kbd:[Ctrl+Enter]) on a reference follows it:

* An `xref:` opens the target page and places the caret on the anchor, if there is one.
* An `include::` opens the included file.
* An `+{attribute}+` goes to the place the attribute is defined: the document, an included file, `antora.yml` or the playbook.
* An `image::` or an attachment opens in the system's default application.

If the target cannot be resolved, the diagnostic is shown and nothing is opened.

=== Back and forward

Every followed link is recorded.
Go Back (`Ctrl-minus`) and Go Forward (`Ctrl-Shift-minus`) move through that history, also available from the arrows in the title bar and at the start of the tab bar.
These two bindings use Ctrl on every platform, including macOS.

=== Peek an include

kbd:[Alt+F12] on an `include::` shows the included file read-only, without leaving the current page.
Use Open from the peek to open it in a tab.

== Find and replace

Find in Workspace (kbd:[Cmd+Shift+F] or kbd:[Ctrl+Shift+F]) searches every file in the workspace.
Regular expression, case-sensitive and whole-word options are available.
Results arrive as the search runs, and clicking one opens it.

Replace in Workspace (kbd:[Cmd+Shift+H] or kbd:[Ctrl+Shift+H]) does not change anything immediately.
It shows a preview listing every change; nothing is written until you apply it.
Applying the preview is one undo step across every file it touches.

== Rename a page

Rename Page (kbd:[F2]) renames the active page.
AdocFoundry shows a preview that lists the file move and every xref, navigation and include edit needed to keep links working.
Apply the preview to move the file and rewrite the xrefs, nav entries and includes of the file.
An include written through an attribute is left as written.
The moved page's own references keep naming what they named, and their edits appear in the preview with the others.
In a plain document, xref, include and image targets are relative to the page's folder, so moving the page into `guides/` rewrites `+xref:child.adoc[]+` as `+xref:../child.adoc[]+`.
In an Antora page, xrefs, images and `family$` includes are resource IDs relative to the module, so a move within the module changes nothing, while a move to another module, component or version qualifies them: `+xref:other.adoc[]+` becomes `+xref:ROOT:other.adoc[]+`, and `include::partial$p.adoc[]` becomes `include::ROOT:partial$p.adoc[]`.
IDs written with `./` or `../`, and includes written as plain paths, are relative to the page's folder and are rewritten when it changes.
A reference from the page to itself, such as `+xref:index.adoc#top[]+`, keeps pointing at the page in its new place.
Targets written through an attribute, URLs and pure `#fragment` references are left as written.
One undo moves the page back and restores every edit.

== Themes

The theme follows the system by default.
Toggle Light/Dark Theme (`Cmd-K Cmd-T` or `Ctrl-K Ctrl-T`) switches immediately, and the `editor.theme` setting fixes it to `light`, `dark` or `auto`.

== The read-only second window

Open Read-Only Window (`Cmd-K Cmd-N` or `Ctrl-K Ctrl-N`) opens a second window that shows the active document read-only and follows it as you edit.
It uses the same multi-window path as the detachable preview; see xref:preview.adoc[The preview].

== Settings and the palette

Open Settings (`Cmd-,` or `Ctrl-,`) opens your user settings file, creating it if necessary.
Saving it applies the change.
See xref:settings.adoc[Settings].

The command palette lists every command with its title.
Bold, Italic, Code and Highlight are listed in every mode.
The other commands that apply only to the visual editor, such as the list and block commands and Insert Link, are listed only while the active page is shown in Visual or Split mode.
Commands that need an open page are hidden when none is open, and Antora-only commands are hidden when the workspace has no Antora component.

== The line and column in the status bar

The status bar shows the caret's line and column as `Ln, Col`.
In Visual mode, and in Split mode while the visual side has focus, they follow the visual editor's caret.
Otherwise they follow the source editor's caret.

== The branch in the status bar

Inside a Git repository the status bar shows the current branch, such as `⎇ main`.
It is the branch of the repository that holds the active document, or of the first root when no document is open.
A detached HEAD shows `⎇ detached @ 1a2b3c4` and a repository with no commits shows `⎇ no commits yet`.
Outside a repository nothing is shown.
When the active page belongs to an Antora component, the bar shows its version and the branch together, such as `product@2.0 · main`, or `product@latest` for a component with `version: ~`.
See xref:antora-support.adoc#versions-and-branches[Versions and branches].
When the branch has a remote-tracking branch on the remote named by `git.remote`, the bar adds the number of commits the remote does not have, such as `⎇ main ↑2` or `product@2.0 · main ↑0`.
Nothing is added while the branch has no remote-tracking branch yet.
The branch and the count update after a commit, a push or a branch switch.
Refresh Git Status (`git.refresh`) in the palette discovers the repositories again, and the `git.enabled` setting turns this off; see xref:settings.adoc[Settings].

[[change-markers]]
== Change markers

A 3-pixel bar at the left edge of the source editor, beside the line numbers, marks the lines changed against the last commit (`HEAD`).
Unsaved edits are included.
Green marks added lines and blue marks modified lines.
A small red triangle between two lines marks where lines were deleted.
The markers follow scrolling, soft wrap and folding, and never move the text.
They update shortly after typing pauses.
The visual editor marks changed blocks in the same colours; see xref:visual-editing.adoc#changed-blocks[Changed blocks].
Setting `git.show_markers` to `false` hides the markers in both editors; see xref:settings.adoc[Settings].

=== Reverting a change

Clicking a marker opens a card showing the lines as they were in the last commit.
Its heading reads "Before this change", "Added since the last commit" or "Deleted since the last commit".
*Revert Change* puts those lines back as one undo step, and Undo brings the edit back.
*Copy* copies the old lines.
Clicking elsewhere closes the card.

Revert Change (`git.revert_hunk`) is also in the palette and acts on the change at the caret.
It reports "there is no change here" when the caret is not in a change.
Go to Next Change (`Option-Down` or `Alt-Down`) and Go to Previous Change (`Option-Up` or `Alt-Up`) move the caret from change to change, wrapping round at the ends.
They report "there are no changes" when the page has none.

== The Changes panel

The sidebar has a *Changes* tab when a workspace root is in a Git repository.
A folder outside Git has no Changes tab, and a repository with no changes shows an empty panel.
Show Changes (`git.show_changes`) in the palette switches the sidebar to it.

The panel lists the changed files under the roots that are AsciiDoc pages (`.adoc`, `.asciidoc` or `.ad`) or lie in an Antora family directory (`images`, `attachments`, `examples` or `partials`).
Ignored files are never listed.
Each row has the status letters of `git status --short`, the path relative to the root and, for an open document, the number of changes in brackets:

----
 M modules/ROOT/pages/page.adoc (2)
?? modules/ROOT/images/diagram.svg
----

With more than one repository, the files are grouped under each repository's folder name.
Clicking a row's name opens the file with the caret on its first change.
The name of a deleted file is struck through and opens nothing.

[[staging-and-committing]]
=== Staging and committing

Each row has a checkbox, ticked when the file has changes staged.
Ticking it stages the file as it is in the working tree: new and changed files are added and a deleted file is staged as deleted.
Unticking it unstages the file by putting the `HEAD` version back in the index.
The working tree is not touched.

Above the rows, *Stage All* stages every file the panel lists and is disabled when it lists none.
*Commit…* opens the commit dialog and is disabled when nothing is staged.

The commit dialog has:

* a message field, whose first line is the summary, with a note under it such as "Summary: 41 of 72 characters", shown in the warning colour past 72;
* the files that will be committed;
* *Commit* and *Commit and Push* buttons.

The dialog has no option to amend a commit or to create a branch.
After committing, a notification reads `Committed abc1234`, or `Saved 2 files and committed abc1234` when open documents with unsaved edits were saved first.
The change markers and the Changes panel clear, because `HEAD` has moved.

Commit (`git.commit`) in the palette opens the same dialog.
Stage (`git.stage`) and Unstage (`git.unstage`) in the palette act on the active file, and Stage All Changes (`git.stage_all_adoc`) does what *Stage All* does.

Save and Commit (`git.save_and_commit`, in the Document category) saves the active page, stages it and opens the dialog with the message `docs: update <page title>`.
The page title is the document title, or the file name when the page has none.

A commit needs an author.
The name and address come from `user.name` and `user.email` in the usual Git configuration scopes.
Without them the commit is refused with a message that says how to set them:

[source,sh]
----
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
----

A commit with nothing staged is refused with "nothing is staged to commit".
When `commit.gpgsign` is `true`, the commit is made with the `git` executable so that it is signed with your key.

[[pushing]]
=== Pushing

*Commit and Push* in the dialog, and Push (`git.push`) in the palette, push the current branch to the remote named by `git.remote`, `origin` by default.
Pushing runs the `git` executable, so your credential helper, SSH agent and signing setup work unchanged.
A notification reports the result, such as "Pushed main to origin", or shows the error Git gave.

Push never forces and never sets an upstream.
A branch with no upstream is refused with "branch X has no upstream: run `git push --set-upstream origin X` once".
The executable is `tools.git` when set, else `git` on `PATH`.
Without one, the command says "pushing needs the git executable: install Git or set [tools] git".
Staging and committing do not need the executable, apart from signed commits.

[[blame]]
== Blame

Toggle Blame (`git.show_blame`, in the View category) in the palette shows or hides a blame column at the left of the source editor for the active document.
Each visible line shows the short commit id, the author and how long ago the line last changed, such as `abc1234 Paul Snow, 3 days ago`.
A line changed since the last commit, including by unsaved edits, shows `Not committed`.
The column follows scrolling, soft wrap and folding.

With `git.blame_on_hover` set to `true`, resting the pointer on a line's number for 400 ms shows a tooltip such as `abc1234 · Paul Snow · 3 days ago · Fix the install steps`, or `Not committed`.
The setting is `false` by default; see xref:settings.adoc[Settings].

Blame is worked out once for the file as it is in the last commit, in the background, the first time it is asked for.
It is not worked out again as you type: lines you change are shown as not committed.
It is worked out again after a save, a commit or a branch switch.
Times are shown relative to now, such as "just now", "5 minutes ago", "2 hours ago", "3 days ago", "2 months ago" and "1 year ago".

[[remote-links]]
== Links to a line on the hosting site

Open on Remote (`navigate.open_on_remote`, in the Navigate category) opens the caret's line in the browser, on the site that hosts the repository's remote.
Copy Remote Link (`navigate.copy_remote_link`) copies the address instead and says so.
Both are in the palette and have no default binding.

The remote is `git.remote`, `origin` by default.
The link points at the current branch, or at the commit when HEAD is detached.
Remote URLs in the forms `git@host:org/repo.git`, `ssh://git@host/org/repo.git` and `https://host/org/repo` (with or without `.git`) are all understood.

[cols="1,3"]
|===
|Site |Link

|GitHub
|`\https://github.com/org/repo/blob/main/README.md?plain=1#L12`

|GitLab
|`\https://gitlab.com/group/repo/-/blob/main/page.adoc#L3`

|Bitbucket Cloud
|`\https://bitbucket.org/team/repo/src/main/page.adoc#lines-7`

|Azure DevOps
|`\https://dev.azure.com/org/project/_git/repo?path=/page.adoc&version=GBmain&line=7&...`
|===

The GitHub link carries `?plain=1`, which shows the source so that the line anchor works on rendered files such as AsciiDoc.
Azure DevOps uses `GC` and the commit in place of `GB` and the branch when HEAD is detached.

github.com, gitlab.com, bitbucket.org, dev.azure.com, ssh.dev.azure.com and `*.visualstudio.com` are recognised.
A self-hosted site is named in the `[git.hosts]` table of the user settings file, host name to kind:

[source,toml]
----
[git.hosts]
"git.example.com" = "gitlab"   # github | gitlab | bitbucket | azure
----

The commands refuse, with a message, in three cases:

* The repository has no such remote: "the repository has no remote named origin".
* The branch has not been pushed, so `refs/remotes/origin/<branch>` does not exist: "branch main is not pushed to origin".
A local branch that is ahead of its remote still gets a link.
* The host is not recognised: the message asks you to name its kind under `[git.hosts]`.

== Known limits

* Input-method (IME) composition has not been verified by hand on any platform.
* Frame timing during long typing bursts has not been captured on every platform.
