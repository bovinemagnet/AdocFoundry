= Settings
Paul Snow
:revnumber: 0.0.0
:description: The TOML user and workspace settings files and every key they accept.

Settings are TOML.
There are two layers, and the workspace layer is applied after the user layer.

[cols="1,3"]
|===
|Layer |File

|User
|`adocfoundry/adocfoundry.toml` in the platform configuration directory: `~/.config` on Linux, `~/Library/Application Support` on macOS and `%APPDATA%` on Windows.
Open Settings File creates it if it is missing.

|Workspace
|`.adocfoundry.toml` at the root of the workspace.
|===

Saving either file applies it, whether in AdocFoundry or in another editor while a workspace is open.
Reload Settings re-reads both.

[#settings-window]
== The settings window

Open Settings (`Cmd-,` or `Ctrl-,`) opens a window of the settings most people change, so that you need not edit the file.
Pressed again, it brings the window to the front.
Open Settings File opens `adocfoundry.toml` in a tab instead, creating it if it is missing, and so does the window's Open File button.
Open Settings File has no default keys and is in the menu and the command palette.

The window has a page for each group of settings:

[cols="1,3"]
|===
|Page |Settings

|Editor
|`editor.font_family`, `editor.font_size`, `editor.soft_wrap`, `editor.tab_width`, `editor.preview_tabs`, `editor.auto_save` and `editor.attribute_values`.

|Appearance
|`appearance.mode`, `appearance.light_theme`, `appearance.dark_theme`, `appearance.font_set` and `appearance.font_scale`.

|Workspace
|`workspace.ignore`.

|Tools
|`tools.asciidoctor`, `tools.git`, `tools.dot`, `tools.plantuml`, `tools.d2`, `tools.node`, `tools.diagram_timeout`, `tools.build_timeout` and `tools.commit_timeout`.

|Git
|`git.enabled`, `git.show_markers`, `git.blame_on_hover` and `git.remote`.

|PDF
|`pdf.theme`, `pdf.themes_dir`, `pdf.fonts_dir`, `pdf.site_url` and `pdf.standards`.
|===

Each setting shows its description, and the search box finds a setting by its title, its description or its name in the file.
Settings that are not in the window are still set in the file.

A change is written to the user settings file, and only that value changes: comments, the order of keys and keys the window does not know are kept, and a settings file that is a symbolic link stays one.
Switches and choices are saved at once.
Text and numbers are saved when typing pauses for half a second, on kbd:[Enter], on leaving the field and when the window closes.
A number outside its range is not saved.
Emptying a text field, or using the reset button beside a setting you have changed, takes the setting out of the file, so its default applies.
Changing Mode also removes the older `[editor] theme` setting.

A setting that the workspace's `.adocfoundry.toml` gives is shown with a note saying so, and cannot be changed in the window.
Change it in that file.

The window shows a message, and leaves the file as it was, when:

* there is no user settings file to save to,
* the settings file does not parse, or
* the settings file has unsaved edits in a tab.

A settings tab with no unsaved edits follows the change.
The window also follows changes made in the file.

[#state-folder]
The app also keeps two folders and two files in its state folder, `adocfoundry` under the platform's local state location: `$XDG_STATE_HOME/adocfoundry` on Linux, normally `~/.local/state/adocfoundry`; `~/Library/Application Support/adocfoundry` on macOS; and `%LOCALAPPDATA%\adocfoundry` on Windows.
It is local, never roaming, because the settings file is often synchronised or kept in a dotfiles repository and copies of pages should not travel with it.
The folders are `recovery`, holding copies of unsaved pages until they are saved or closed, and `history`, holding saved versions of pages.
The files are `session.json`, the last session, and `recent-folders.json`, the folders opened recently.
`update-state.toml` and `sidebar-state.json` stay beside the settings file.
See xref:using-the-editor.adoc#crash-recovery[Recovering unsaved changes], xref:using-the-editor.adoc#local-history[Local history] and xref:using-the-editor.adoc#restoring-the-session[Restoring the last session].

[[font-sets]]
== Font sets

A font set gives three roles: Interface (menus, panels, tabs, dialogs and the status bar), Source (the source editor, and code in the preview, the visual editor and reports) and Reading (prose and headings in the preview and the visual editor).
`appearance.font_set` chooses one.
The fonts of `workshop`, `reading-room` and `legible` ship inside the app, so nothing needs installing.

[cols="2,3,3,3"]
|===
|Id |Interface |Source |Reading

|`workshop` (default)
|IBM Plex Sans
|IBM Plex Mono, 13
|IBM Plex Sans, 15

|`reading-room`
|Source Sans 3
|Source Code Pro, 14
|Source Serif 4, 17

|`legible`
|Atkinson Hyperlegible Next
|Atkinson Hyperlegible Mono, 14
|Atkinson Hyperlegible Next, 16

|`current`
|the theme's or the system's interface font
|the theme's or the system's monospace font; JetBrains Mono in the source editor only, if installed
|as Interface
|===

`current` is the fonts the app used before font sets; they do not ship.
A theme's `font.family` and `mono_font.family` apply only under `current`; any other set overrides them.
`editor.font_family` and `editor.font_size`, when a settings file names them, replace the set's source role.
Font sets change the app and never PDF export, which keeps its theme's fonts.

Define a set of your own in the user file:

[source,toml]
----
[appearance]
font_set = "house"

[appearance.font_sets.house]
name = "House"            # defaults to the id
based_on = "reading-room" # a built-in id; workshop when left out
source = "Iosevka"
source_size = 14
reading = "Georgia"
reading_size = 16
----

A role left out comes from `based_on`.
The keys are `name`, `based_on`, `interface`, `source`, `source_size`, `reading` and `reading_size`.
The families must be installed; a missing interface, source or reading family is reported in a notification and falls back to the theme's.
An id a built-in set has, a bad `based_on` or a bad value leaves the set out with a warning.

*Select Font Set...* in the View menu and the command palette is the quick way to choose; see xref:using-the-editor.adoc#themes[Themes].

[#key-bindings]
== Key bindings

`[keymap]` in the user settings file gives a command other keys than its default.
It maps a command id to keys.
A workspace file's `[keymap]` is ignored with a warning, so a repository cannot take over your keys.

[source,toml]
----
[keymap]
"document.close_all" = "cmd-k x"   # a chord: two strokes
"view.toggle_preview" = "cmd-alt-p"
"git.stage" = "ctrl-shift-s"       # a command with no default keys
"document.save_all" = ""           # takes the command's keys away
----

The ids may be written without quotes too, as in `document.close_all = "cmd-k x"`.
Taking the line out gives the command's default back.
The command palette finds a command by id as well as by title; see xref:keyboard-shortcuts.adoc[Keyboard shortcuts] for the ids of the commands that have default keys.

=== Notation

Keys are one stroke or several, separated by spaces.
A stroke is any of the modifiers `cmd`, `ctrl`, `alt` and `shift`, in any order and any case, then a key, all joined by `-`.
`cmd` is Command on macOS and Control on Linux and Windows.
A key is a letter, a digit or a sign, `f1` to `f24`, or one of `enter`, `escape`, `tab`, `space`, `backspace`, `delete`, `insert`, `up`, `down`, `left`, `right`, `home`, `end`, `pageup` and `pagedown`.

=== What happens

The change takes effect when the user settings file is saved, in AdocFoundry or elsewhere while a workspace is open, or when you choose Reload Settings.
No restart is needed.
The command palette shows each command's keys in force.
The menus do too, but only the first stroke of a chord.
The tables in xref:keyboard-shortcuts.adoc[Keyboard shortcuts] list the defaults.

Keys you give a command are taken from the command that has them by default.
Any command that can be run from the palette can be given keys, including those with none by default.
A command of the window that is given keys wins over the editors' own, so `cmd-f` may be given to another command.
Moving Undo or Redo off their keys does not bring back the editor widget's own undo and redo.

Some keys belong to the app and not to a command, and cannot be changed: Command Palette, Toggle Light/Dark Theme, Open Read-Only Window, the zoom keys, and the caret movement and clipboard keys.

=== Warnings

These are warned about and not applied:

* an unknown command id;
* keys that cannot be read;
* a first stroke that types or moves the caret, which is one with no `cmd`, `ctrl` or `alt`, unless it is a function key or is the command's own default;
* the same keys given to two commands, where the first by id keeps them;
* a command that cannot be run from a key.

Keys that begin another command's keys, such as `cmd-k` beside `cmd-k x`, are warned about and applied.
The longer ones may then not work, or the shorter wait a moment for a second stroke.

|`appearance.font_set`

|`appearance.font_sets.<id>`
|table
|none

User file only.

|`appearance.font_scale`
|number
|`1`

[#docx-settings]
== Word export settings

The `[docx]` table sets how the Word documents the engine writes are laid out and styled, and `[docx.profiles.<name>]` saves Word publications under a name.
These settings are what Export Page to Word…, Export Component to Word…, Export DOCX Profile…, `adocfoundry-cli docx` (see xref:command-line.adoc#docx[docx]) and the MCP `export_docx` tool read.
See xref:word-export.adoc[Exporting to Word] for the export itself.

Both settings files may set `[docx]`.
A key the workspace file sets replaces the user file's.
A `[docx.header]` or `[docx.footer]` table replaces that one's lines whole, so a workspace that sets `[docx.footer]` does not keep the user file's even-page footer.
A workspace profile replaces a user profile of the same name.
An unknown key, or a value that cannot be used, warns and leaves the default.

Word export and PDF export are set apart.
Nothing in `[docx]` is read for PDF.
Nothing in `[pdf]` is read for Word except, for the PDF-theme look only, the theme and the folder it is found in (`[pdf] theme` and `themes_dir`); its fonts and standards are never read.

[#docx-looks]
=== Looks

A Word export has a look: a PDF theme, a Word template, or none.
`[docx] look` sets the default, and is `"pdf-theme"`, `"template"` or `"none"`.
The default is `"pdf-theme"`.
A `look` value that cannot be used is warned about and leaves the default.

With `look = "pdf-theme"`, Word follows a PDF theme only when one is named: the page's `pdf-theme` attribute, or `[pdf] theme` written in a settings file.
Unlike PDF export, it never falls back to the bundled `default` theme, so a workspace that names no theme gets the Word export's own look, as before.
The theme is found exactly as PDF export finds it.

With `look = "template"`, `[docx] template` names the template.
A name is found as `<name>.dotx`, else `<name>.docx`, in the PDF themes folder: the page's `pdf-themesdir` attribute, else `[pdf] themes_dir`.
A path ending in `.dotx` or `.docx` is relative to that folder, else to the first workspace root.
`look = "none"` reads no theme and no template.

A theme or template that cannot be found fails the export, and the error names where it was looked for.
`look = "template"` with no `template` set fails too.

A template is read as untrusted input:

* A template larger than 32 MB is refused.
So is one that can hold macros, meaning a macro-enabled `.dotm` saved under any name or any package holding a VBA project, one that is not a readable Word package, and one whose styles or numbering are not well-formed XML.
The export fails and says why.
* A header or footer is left out, with a warning, when it refers to anything other than a picture inside the template or a link, for example a picture linked from a web address.
It is left out too when it holds a field that could read something outside the document, such as `INCLUDEPICTURE`, `INCLUDETEXT` or `DDEAUTO`.
A header or footer is also left out when it uses a link to fetch something, for example a picture whose source is a link, when its markup names a web address or network path directly, or when it shows an SVG picture that refers to anything outside itself.
The fields kept are those that only show the document's own facts: `PAGE`, `NUMPAGES`, `SECTIONPAGES`, `SECTION`, `STYLEREF`, `DATE`, `TIME`, `CREATEDATE`, `SAVEDATE`, `PRINTDATE`, `TITLE`, `SUBJECT`, `AUTHOR`, `KEYWORDS`, `COMMENTS`, `LASTSAVEDBY`, `DOCPROPERTY` and `FILENAME`.
* A template's theme that refers to other parts is left out, with a warning.
* A template's picture bullets in its list numbering are kept.
Numbering that refers to anything outside the template is left out, with a warning, and the export's lists are numbered on their own.
* The template is read only through the same file access as the rest of the export, so the MCP server's confinement to the workspace covers it.

What a look gives today:

* A theme gives the page: its `page_size`, `page_layout` and `page_margin`.
The page's `pdf-page-size`, `pdf-page-layout` and `pdf-page-margin` attributes win over the theme, as they do for PDF.
* A theme gives styles, which a reader can still change in Word:
** The body: the document's defaults and Normal, from `base_font_family`, `base_font_size`, `base_font_color`, `base_line_height` and `base_text_align`.
** Headings 1 to 6: the shared `heading_*` keys, with each level's `heading_h<n>_*` keys over them (font, size, colour, style, `text_transform: uppercase` as capitals, and `margin_top` and `margin_bottom` as space before and after).
** Links: Hyperlink, from `link_font_color` and `link_text_decoration`.
** Code: Source Code and Literal Block (font, size, colour, background and border), and Code Char for code spans (font, colour and background).
** Captions: the `caption_*` keys, with `caption_text_align` (or `caption_align`).
** Quotes: the `quote_*` keys, with the left bar from `quote_border_color` and `quote_border_left_width`.
** Boxes: admonitions (the background, and the column rule as the left bar); sidebars and examples (background and border); and tables (border colour and width, background, header row background, font colour and bold, and stripes on every other body row).
* A theme gives the title page: `title_page_text_align` (else `base_text_align`), the title, subtitle and author styles (`title_page_title_*`, `title_page_subtitle_*` and `title_page_authors_*`), and the logo (`title_page_logo_image` and `title_page_logo_align`).
The page's own `title-logo-image` wins over the theme's logo.
* A theme gives the covers: `cover_front_image` and `cover_back_image`, when the page names none.
The page's `front-cover-image` and `back-cover-image` win.
* A theme gives the headers and footers: its `header_*` and `footer_*` keys become the Word document's headers and footers.
** Recto and verso: odd pages take the `recto` content (`header_recto_left_content`, `header_recto_center_content` and `header_recto_right_content`, and the footer's), and even pages the `verso` content.
As in the PDF, even pages show only their own `verso` content, so a theme without verso content leaves even pages blank.
** A theme with no `header_height` (or `footer_height`) shows no header (or footer), as the PDF does.
** Content: `\{page-number}` and `\{page-count}` are live page fields, and `\{document-title}` is the document's title.
`\{chapter-title}`, `\{section-title}`, `\{section-or-chapter-title}` and `\{part-title}` are Word fields that show the current heading.
Word cannot fall back from one heading to another, so `\{section-or-chapter-title}` shows the section's title.
Any other attribute is the document's value, and a line naming an attribute that is not set is left out, as asciidoctor-pdf leaves it out.
** Pictures: an `image:` macro standing alone is a picture from the theme's folder, as wide as its `pdfwidth` (or `scaledwidth`, `width`) when that is an absolute length, else a line high.
** Marks and references: `*bold*`, `_italic_` and `` `monospace` `` marks are left out, keeping their text, and character references such as `&#169;` are the characters.
** Font and rule: the `header_font_*` and `footer_font_*` keys style Word's Header and Footer styles.
`header_border_color` and `header_border_width` draw a rule under the header, and the footer's draw a rule above it.
** Position: each header and footer sits within the theme's `header_height` (or `footer_height`) at the page's edge, placed by its `vertical_align` and `padding` as in the PDF.
** Column widths (`header_columns`) are not used: Word's left, centre and right tab stops place the three slots.
** A `[docx.header]` or `[docx.footer]` written in the settings replaces the theme's, and so do written `margins.header`, `margins.footer` and `odd_even`.
* A key that Word cannot express is ignored.
* A theme gives fonts, which are embedded in the document, as Word itself embeds them:
** Which: the fonts of the theme's font catalogue (`font_catalog`) that the Word styles use, with all four faces of each family the theme gives (regular, bold, italic and bold italic).
The no-theme look embeds no fonts.
** Where from: the fonts are found as PDF export finds them, in the PDF fonts folder (the page's `pdf-fontsdir` attribute, else `[pdf] fonts_dir`), then the theme's folder, then the bundled fonts.
Only files inside the workspace's folders are read.
** Names: Word and LibreOffice find an embedded font by the family name stored inside the font file, so the document names each family by that name, even when the theme's catalogue calls it something else.
For example, a catalogue entry `Brand Serif` whose file is Noto Serif is named `Noto Serif` in the Word styles.
** Licences: a font is embedded only when its OpenType embedding permission (`fsType`) allows it.
Installable and editable fonts are embedded.
A preview-and-print font is embedded with a warning that Word may open the document read-only.
A restricted font, or one that allows only its bitmaps to be embedded, is named but not embedded, with a warning that names it.
** Not embedded: fonts with CFF (PostScript) outlines, usually `.otf` files, since Word embeds TrueType outlines only; font collections (`.ttc`); and a font file that cannot be found or read.
Each is named in the document, and each gives a warning.
** Size: fonts are embedded whole, not subset, so they add to the document's size.
The bundled default theme's two families add about half a megabyte.
`[docx] embed_fonts = false` names the fonts without embedding them, so a reader's computer shows them only where they are installed.
* A template gives its styles, numbering, theme, fonts, page, and headers and footers.
** Styles: the template's styles are used as it defines them.
Styles the export needs that the template does not have, such as code, admonitions and captions, are added, based on the template's default paragraph style.
A template whose built-in styles have other ids, such as a German one with `Überschrift 1`, is matched by the style's name.
** Numbering: its list numbering is kept, and the export's lists are numbered after it.
** Theme and fonts: its theme, its font table and any fonts it embeds are kept.
`[docx] embed_fonts = false` names the template's fonts without embedding them.
** Page: its last section's page size, orientation and margins are used.
** Headers and footers: those that last section shows are used exactly as they are, with their pictures and links, fields included.
Odd and even pages differ when the template says so.
A header or footer that the template's last section takes from an earlier section is used too.
** Body: nothing of the template's body is used.
** Written settings: `[docx]` settings written in a settings file still win, key by key.
`paper`, `orientation` and `margins.*` replace the template's page.
A written `header` or `footer` replaces the template's header or footer.
`[docx.styles]` changes the template's own style's font, size or colour rather than replacing it.

A `[docx]` key written in either settings file applies over the look.
A key that is not written takes the look's value, else the built-in default.
This holds for `[docx.styles]` too: a written `heading_colour` replaces the theme's heading colour, and the rest stays the theme's.
So `paper`, `orientation` and each `[docx.margins]` side, when written, win over the theme's page, and an export's or profile's own `paper` and `orientation` win over everything.

[#docx-profiles]
=== Word profiles

A Word profile names a Word document you produce again and again, as a PDF profile does.
It is a table `[docx.profiles.<name>]` in either settings file.

[cols="1,4"]
|===
|Key |Meaning

|`page`, `component` or `nav`
|Exactly one of them, as for xref:pdf-export.adoc#publication-profiles[a PDF profile]: a page's path, a component version (`name` or `version@name`), or an array of navigation file paths, relative to the first workspace folder.

|`output`
|Where to write the document, relative to the first workspace folder.
The default is `<name>.docx` there.
It must be a `.docx` file name and inside the workspace folder; a profile whose output would be written outside it is refused when it is run.

|`paper` and `orientation`
|This document's own, in place of the value in `[docx]`.

|`attributes`
|A table of attribute names to strings, numbers or `true`, applied to every page before its own header.

|`theme`
|The name of a PDF theme to take this document's look from, found as <<docx-looks>> describes.

|`template`
|The name of a Word template to use as this document's look.

|`look`
|`"none"`, to give this document the Word export's own look whatever `[docx]` says.
|===

At most one of `theme`, `template` and `look` may be given.
A profile that gives more than one is left out with a warning.
A profile that gives none uses the look `[docx]` sets.

A profile that has none of `page`, `component` and `nav`, or more than one of them, that has an `output` which is not a `.docx` file name, a bad `paper` or `orientation`, or an unknown key is left out with a warning.
A key that only PDF profiles have, such as `standards`, is an unknown key here.
A Word profile may set its own look, as <<docx-looks>> describes, with `theme`, `template` and `look`.

A profile declares its own content in each format, and a PDF profile and a Word profile of the same name are independent.
A book published in both formats therefore repeats its one line of content, and neither profile can change the other.

This example publishes one Antora book as both a PDF and a Word document, with output paths and style settings of their own.

[source,toml]
----
[pdf.profiles.admin-guide]
component = "2.0@admin"
output = "build/admin-guide.pdf"
theme = "acme"

[docx.profiles.admin-guide]
component = "2.0@admin"
output = "build/admin-guide.docx"
orientation = "portrait"

[docx]
paper = "a4"

[docx.styles]
heading_font = "Calibri Light"
heading_colour = "1F3864"

[docx.footer]
left = "{chapter-title}"
right = "{page-number} of {page-count}"
----

The PDF profile's `theme` is not read for Word, which has its own look keys, and the Word profile's `orientation` is not read for PDF.

|===

[#kindle-profiles]
=== Kindle profiles

A profile has exactly one of these.

* `page`, a page.
* `component`, a component version as `version@name` or `name`.
* `nav`, an array of navigation files.

It may also have these keys.

* `format`, as `[kindle] format`.
* `output`, relative to the first root and inside the workspace, with the format's extension.
It is `<name>.<format>` at the root by default.
* `attributes`, which are set for the export.
* `title`, `creator`, `language`, `identifier` and `cover`, as for `[kindle]`.

[source,toml]
----
[kindle]
format = "kfx"
creator = "Paul Snow"

[kindle.profiles.admin-guide]
component = "2.0@guide"
format = "azw3"
output = "build/admin-guide.azw3"
cover = "images/cover.png"
----

[#epub-settings]
== EPUB export settings

The `[epub]` table sets the metadata, cover, stylesheet and date of the EPUB books the engine writes, and `[epub.profiles.<name>]` saves EPUB publications under a name.
These settings are what Export Page to EPUB…, Export Component to EPUB…, Export EPUB Profile…, `adocfoundry-cli epub` and the MCP `export_epub` tool read.
See xref:epub-export.adoc[Exporting to EPUB] for the export itself.
Nothing is read from `[pdf]`, `[docx]` or `[kindle]`, and nothing here changes another format.
An unknown key, or an output that is not a `.epub` file, is reported when the settings are read.

[cols="2,2,2,4"]
|===
|Key |Type |Default |Meaning

|`epub.style`
|string
|`"default"`
|The book's style. Only `"default"` exists.

|`epub.title`, `creator`, `identifier` and `publisher`
|strings
|from the book
|The book's metadata, which replaces what the pages give.

|`epub.language`
|string
|from the book
|A BCP 47 tag such as `"en-GB"`. Without one the export warns and uses English.

|`epub.cover`
|string
|none
|A picture for the cover, relative to the workspace root. The `front-cover-image` attribute wins over it.

|`epub.css`
|string
|none
|A stylesheet of your own, relative to the workspace root. See <<epub-css>>.

|`epub.modified`
|string
|see below
|The book's modification time: a date such as `"2026-11-19"`, taken as midnight UTC, or a UTC time such as `"2026-11-19T10:30:00Z"`, from 1980 to 2107. Without it the `SOURCE_DATE_EPOCH` environment variable is used, and then the time of the export, when exporting again gives other bytes.

|`epub.profiles.<name>`
|table
|none
|A named EPUB publication. See <<epub-profiles>>.
|===

[#epub-css]
=== Your own stylesheet

`css` is linked after the default stylesheet, so it can change how the book looks and never what it holds.
It may not use `@import`, `url(`, `@font-face`, `@namespace`, script expressions or bindings, markup or backslash escapes, and it may be at most 256 KB.
Otherwise the export fails and writes nothing.

[#epub-profiles]
=== EPUB profiles

A profile has exactly one of these.

* `page`, a page.
* `component`, a component version as `version@name` or `name`.
* `nav`, an array of navigation files.

It may also have these keys.

* `output`, an `.epub` file inside the workspace.
It is `<name>.epub` at the root by default.
* `attributes`, which are set for the export.
* `title`, `creator`, `language`, `identifier`, `publisher`, `cover`, `css` and `modified`, as for `[epub]`.

A profile repeats its content: it never names a PDF, Word or Kindle profile.

----

[#docbook-settings]
== DocBook export settings

The `[docbook]` table says where the DocBook documents the engine writes keep their pictures, and `[docbook.profiles.<name>]` saves DocBook publications under a name.
Nothing is read from `[pdf]`, `[docx]`, `[kindle]` or `[epub]`, and nothing here changes another format.
An unknown key, or an `assets` value that is neither `"copy"` nor `"reference"`, is reported when the settings are read.

[cols="2,2,2,4"]
|===
|Key |Type |Default |Meaning

|`docbook.assets`
|string
|`"copy"`
|`"copy"` writes each picture once into the folder beside the document that is named after it (`guide.xml` gives `guide_assets/`), so the two can be moved together. `"reference"` copies nothing and refers to each picture where it is, by a path from the document's folder; such a document is not portable.

|`docbook.profiles.<name>`
|table
|none
|A named DocBook publication. See <<docbook-profiles>>.
|===

The assets folder is always named `<name>_assets`, because the rule for replacing it safely depends on the name.
The export always checks its own document, and the diagnostic level that fails an export is the command line's `--fail-on`, so neither is a setting.

[#docbook-profiles]
=== DocBook profiles

A profile has exactly one of these.

* `page`, a page.
* `component`, a component version as `version@name` or `name`.
* `nav`, an array of navigation files.

It may also have these keys.

* `output`, an `.xml` file inside the first workspace root.
It is `<name>.xml` there by default.
* `attributes`, which are set for the export.
* `assets`, which replaces `[docbook] assets` for this profile.

A profile repeats its content: it never names a PDF, Word, Kindle or EPUB profile.
Any other key, an output that is not an `.xml` file and an unknown `assets` value are refused when the settings are read.

An export's own choice, from the command line, wins over the profile's, which wins over the policy in `[docbook]`, which wins over copying.
The workspace's settings override the user's, key by key, and a profile replaces one of the same name whole.

[source,toml]
----
[docbook]
assets = "copy"

[docbook.profiles.admin-guide]
component = "2.0@guide"
output = "build/admin-guide.xml"
assets = "reference"
----

[#authoring-profiles]
== Authoring profiles

`[authoring.profiles.<name>]` saves a set of attribute values under a name, to read pages with.
It is a table in either settings file.

[source,toml]
----
[authoring.profiles.cloud]
attributes = { cloud = true, edition = "Cloud" }

[authoring.profiles.on-premises]
attributes = { edition = "On-premises" }
----

[cols="1,4"]
|===
|Key |Meaning

|`attributes`
|A table of attribute names to strings, numbers or `true`, which sets an attribute empty, as `:name:` does.
|===

`attributes` is the only key.
A profile with any other key, or a value of another type, is left out with a warning naming `authoring.profiles.<name>`.
A workspace profile replaces a user profile of the same name.
Profiles are listed by name.

The attributes are added after the playbook's, the component version's and those Antora computes for the page.
They are hard set, as the attributes in `antora.yml` are unless they end in `@`: a page's own header cannot change them.
Choose a profile from View › Select Authoring Profile…, or with `--authoring` on the command line.
See xref:preview.adoc#authoring-profiles[Authoring profiles] for what it changes, and xref:command-line.adoc#authoring[Command line] for the options.

== What a workspace file may set

A workspace file may override `editor.*`, `templates.dir`, `sidebar.navigation.default_expansion`, `sidebar.modules.default_expansion`, `sidebar.follow_active`, `workspace.ignore`, `pdf.*`, `docx.*`, `authoring.*`, `graph.*`, `quality.*`, `spelling.enabled` and `spelling.language`.
The two depths override separately.
Both files may set `[quality]`: a rule's severity from the workspace file wins, and the exclusions and the providers of both files apply.
`tools.*` is accepted only in the user file, so a repository cannot point the editor at an executable of its choosing.
`git.*` is also accepted only in the user file, so a repository cannot change how the editor treats it.
`sidebar.remember_expansion` is also accepted only in the user file, because it decides what is saved outside the repository.
`updates.*` is also accepted only in the user file, so a repository cannot make the editor reach the network.
`history.*` is also accepted only in the user file, because history is kept outside the repository.
`spelling.dictionaries` is accepted only in the user file, so a repository cannot point the editor at files of its choosing.
`collaboration.*` is also accepted only in the user file, so a repository cannot make the editor listen for or join a session.
`comments.*` is also accepted only in the user file, so a repository cannot choose the name your comments carry.
`keymap.*` is also accepted only in the user file, so a repository cannot change your keys.

== Warnings

Problems with settings produce warnings and never stop the application:

* An unknown key warns and is ignored.
* A value of the wrong type or range, such as `font_size = -3` or `theme = "purple"`, warns and keeps the default.
* An invalid `default_expansion` (a negative number, a fraction, `true`, an array, or a string other than `"all"`) warns and keeps the value from the layer beneath.
* A key set in the workspace file that is only allowed in the user file warns and is ignored.
* A section that is not a table warns.
* An invalid `[quality]` value, an unknown rule, or an exclusion with an unqualified resource ID, no reason or a duplicate warns and is left out, and makes `adocfoundry-cli audit` exit with 2.

Each warning names the file and the key and is shown once.

A file that is not valid TOML at all (for example a missing closing bracket) does not stop a folder opening.
The folder opens with the other file's settings and the defaults, and a warning names the file, line and column and ends "Its settings are not applied until it is fixed."
Fixing the file on disk applies it, and the warning goes.
A file that stops parsing while the folder is open, or when you choose Reload Settings, is reported as a settings error instead, and the settings already in force are kept.
