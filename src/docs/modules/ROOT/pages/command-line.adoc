= Command line
Paul Snow
:revnumber: 0.0.0
:description: Using adocfoundry-cli to check, search, follow links, render and export to PDF headlessly, including in CI.

`adocfoundry-cli` is a headless front end over the same engine as the desktop application.
It needs no display, which makes it suitable for continuous integration.

[source,text]
----
adocfoundry-cli check <root> [--format text|json] [--fail-on warning|error]
adocfoundry-cli audit <root> [--component [<version>@]<name>] [--format text|json|sarif]
    [--output <file>] [--fail-on none|warning|error] [--require-complete]
adocfoundry-cli impact <root> (--base <ref> --head <ref> | --against HEAD | --changed-file <path>...)
    [--format text|json] [--output <file>] [--max-impacts <n>] [--require-complete]
adocfoundry-cli symbols <root> <query>
adocfoundry-cli follow <file> <byte-offset> [--root <dir>]
adocfoundry-cli render <file> [--root <dir>] [--output <file.html>] [--parser acdc|asciidoc-parser]
adocfoundry-cli pdf <file|component-dir> [--root <dir>] [--component [<version>@]<name>]
    [--theme <name|file.yml>] [--fonts-dir <dir>] [--output <file.pdf>]
    [--standard pdf-a-1b|pdf-a-1a|pdf-a-2a|pdf-ua-1] [--typst <file.typ>]
    [--fail-on none|warning|error]
adocfoundry-cli pdf --profile <name> [<root>] [--output <file.pdf>] [--typst <file.typ>]
    [--fail-on none|warning|error]
adocfoundry-cli git-status <root> [--format text|json]
adocfoundry-cli graph <root> [--page <file> [--depth <n>] | --path <from> <to> [--undirected]] [--format json|dot|svg]
    [--no-partials] [--no-nav] [--unresolved] [--ages] [--dark]
adocfoundry-cli doctor [<root>] [--format text|json]
adocfoundry-cli --version
----

== check

`check` opens the workspace at `<root>`, waits for indexing to finish and prints every diagnostic, sorted by path.

[source,sh]
----
adocfoundry-cli check docs
adocfoundry-cli check docs --format json
adocfoundry-cli check docs --fail-on warning
----

=== Formats

The default `text` format prints one line per diagnostic, with paths relative to the root and `/` separators.

[source,text]
----
path:line:col: severity code message
----

Lines and columns are one-based, and the column counts bytes.
`severity` is `info`, `warning` or `error`.

`--format json` prints an array of objects.

[source,json]
----
[
  {
    "path": "modules/ROOT/pages/index.adoc",
    "range": { "start": 120, "end": 138 },
    "line": 7,
    "column": 3,
    "severity": "warning",
    "code": "adoc.unresolved-xref-file",
    "message": "..."
  }
]
----

`range` holds byte offsets into the file.

=== Exit codes

[cols="1,4"]
|===
|Code |Meaning

|0
|Success: no diagnostic met `--fail-on`.

|1
|At least one diagnostic met `--fail-on`. The default threshold is `error`.

|2
|Usage or runtime error, such as an unknown option, a bad format or a workspace that could not be indexed in time.
|===

The thresholds are `warning` (fails on warnings and errors) and `error`.
Information diagnostics never fail the check.

[[audit]]
== audit

`audit` opens the workspace at `<root>`, waits for indexing to finish and audits the documentation's quality.
It reports every diagnostic `check` reports, with the same codes, severities and messages, and the audit's own rules.
See xref:quality-audit.adoc[] for the policy, exclusions and limitations.

`quality.navigation.unlisted-page`::
A published page that no navigation file of its own component version lists. The start page counts as listed.

`quality.page.missing-title`::
A page with no document title.

`quality.image.missing-alt`::
A block image macro with no alternative text written at all.

See xref:settings.adoc[Settings] for the rules' severities.

[source,sh]
----
adocfoundry-cli audit docs
adocfoundry-cli audit docs --format sarif --output audit.sarif
adocfoundry-cli audit docs --component 2.0@product --require-complete
----

=== Scope and policy

The audit covers the whole workspace by default.
`--component <name>` audits every version of one component, and `--component <version>@<name>` audits one version.
A component or version that is not in the workspace makes the audit unavailable.

The policy is the `[quality]` table of the workspace's own `.adocfoundry.toml`: `fail_on`, `require_complete`, the rule severities and the exclusions.
The user settings file is not read, so CI gets the same result on every machine.
`--fail-on` and `--require-complete` override the file.

=== Formats

`--output <file>` writes the report to the file instead of standard output.
Standard output holds only the report; problems go to standard error.

The default `text` format starts with a line that names the scope and its completeness.

[source,text]
----
Audit of the workspace: complete
Audit of the workspace: partial coverage (1 gap)
----

The counts follow.

[source,text]
----
0 errors, 6 warnings, 1 info; 0 excluded, 2 skipped
----

Then there is one line per finding, with paths relative to the root and `/` separators.

[source,text]
----
path:line:col: severity code message
path: severity code message
----

The second form is for a finding about a whole file, such as an unlisted page.
Lines and columns are one-based, and the column counts characters.

Any gaps come next, then each version's navigation coverage, such as `Navigation of product 3.0: 7 of 8 pages listed`.
The last line is the result: `Result: pass`, `Result: pass, with partial coverage`, `Result: fail` or `Result: not trustworthy, …`.

`--format json` writes the whole report as one JSON document with these fields.

[cols="1,4"]
|===
|Field |Meaning

|`schema_version`
|The version of the report's layout.

|`scope`
|What was audited.

|`revision`
|The revision of the workspace that was audited.

|`roots`
|The folder names of the roots, never full paths.

|`fail_on`
|The threshold in force.

|`require_complete`
|Whether completeness was required.

|`rules`
|The rules and their severities.

|`completeness`
|The `status`, which is `complete`, `partial` or `unavailable`, with its `gaps`.

|`counts`
|The number of findings of each severity, and of those excluded and skipped.

|`coverage`
|Each version's navigation coverage.

|`findings`
|The findings.

|`excluded`
|The findings accepted by an exclusion.

|`skips`
|The constructs a rule could not judge.

|`providers`
|Every optional provider's state, as `{ "provider", "state", "reason" }`. The `reason` appears only for `unavailable`.
|===

A finding has `code`, `severity`, `message` and `location`, and, for an Antora resource, `coordinate`.
`location` holds `root`, the root's place in `roots`; `path`; and `range`, in byte offsets.
Paths are relative to the root, and no absolute path appears in a report.

`--format sarif` writes SARIF 2.1.0 for code-scanning tools.
Each finding is a result with its rule.
An excluded finding is a result with an external suppression that gives the exclusion's reason.
Locations are relative to the root (`uriBaseId` `ROOT0`), with one-based lines and character columns.
Completeness is a property of the run, and each gap is a tool execution notification.
The providers' states are in the run's `properties.providers`.

In the text format, each enabled provider has a `Provider <name>: ran` or `Provider <name>: unavailable` line.

=== Completeness

Completeness is about coverage: whether everything in scope was audited.
A folder that could not be read makes the audit partial (`scope-not-indexed`).
An enabled optional provider that could not run does the same (`provider-unavailable`); see xref:quality-audit.adoc#providers[Optional providers].

A construct a rule cannot judge is a skip, such as a navigation file that includes another file, or a title that may come from an include.
A skip is counted and listed, but it does not make the audit partial.

=== Exit codes

[cols="1,4"]
|===
|Code |Meaning

|0
|Success: no finding met the failure threshold (`fail_on`, `error` by default).

|1
|At least one finding met the failure threshold.

|2
|The audit is unavailable, or it is partial while completeness is required (`--require-complete` or `require_complete = true`), or the `[quality]` settings are invalid, or a usage or runtime error.
|===

The report is always written in full before the command exits, whatever the code.
Excluded findings never fail the audit.
A partial audit passes by default, but says so in its first and last lines.

The thresholds are `none` (fails on nothing), `warning` (fails on warnings and errors) and `error` (fails on errors).
Information findings never fail the audit.

== symbols

`symbols` lists workspace symbols that match `<query>`, one per line, as kind, name and `path:line:col`.

[source,sh]
----
adocfoundry-cli symbols docs installation
----

== follow

`follow` resolves the reference at a byte offset in a file and prints where it leads.
It is used by tests and for scripting.

[source,sh]
----
adocfoundry-cli follow tests/fixtures/xrefs/index.adoc 42
----

For an `xref:`, `include::` or attribute it prints `path:line:col`.
For an image or attachment it prints `external <path>`.
If the offset is not on a followable reference, or the target does not resolve, it prints the reason on standard error and exits with 1.

By default the workspace root is the parent of the nearest `antora.yml`, so that sibling components resolve.
Use `--root <dir>` to choose another.

[[render]]
== render

`render` writes a page as a standalone HTML file, as the xref:preview.adoc[preview] renders it.
Without `--output` the HTML goes to standard output.
It waits for diagrams to finish before writing.
Images are linked by `file://` address; the application's Export Page to HTML… embeds them instead, see xref:preview.adoc#exporting-html[Exporting to HTML].

[source,sh]
----
adocfoundry-cli render docs/modules/ROOT/pages/index.adoc --output index.html
adocfoundry-cli render docs/modules/ROOT/pages/index.adoc --root docs > index.html
----

[cols="2,4"]
|===
|Option |Meaning

|`--root <dir>`
|The workspace root, so that includes, xrefs and images resolve across components. Without it, the root is the parent of the nearest Antora component (the directory above the one holding `antora.yml`), or the file's own directory outside Antora. `.` is accepted.

|`--output <file.html>`
|Write to this file instead of standard output.

|`--parser acdc\|asciidoc-parser`
|Choose the document parser. The default is `acdc`. `asciidoc-parser` is a development comparison, and the application always uses `acdc`.
|===

Images and diagrams are written as absolute `file://` URLs, so the file shows them wherever it is opened on the same machine.
A usage or runtime error exits with 2, as for the other subcommands.

[[pdf]]
== pdf

`pdf` exports a page, or a whole component version, as a PDF.
See xref:pdf-export.adoc[Exporting to PDF] for themes, fonts and what the output contains.

[source,sh]
----
adocfoundry-cli pdf docs/modules/ROOT/pages/index.adoc
adocfoundry-cli pdf docs --output docs.pdf --theme acme-theme.yml
adocfoundry-cli pdf docs --root . --component 2.0@guide --standard pdf-a-2a --standard pdf-ua-1
adocfoundry-cli pdf --profile admin-guide .
----

A file argument exports that page as an article.
By default the PDF is written beside the page with a `.pdf` extension.

A directory that holds an `antora.yml`, or `--component`, exports the component version as a book in navigation order.
By default the PDF is `<name>.pdf` in the current directory.
Without a version, `--component` uses the latest version of the component.

[cols="2,4"]
|===
|Option |Meaning

|`--root <dir>`
|The workspace root, so that includes, xrefs and images resolve across components. Without it, the root is the parent of the component directory, or the parent of the nearest Antora component for a page.

|`--component [<version>@]<name>`
|Export this component version as a book, with coordinates written as Antora writes them.

|`--profile <name>`
|Export the publication profile `[pdf.profiles.<name>]` from the settings. The workspace root is the argument, `--root <dir>`, or else the current directory. `--output`, `--theme`, `--fonts-dir` and `--typst` win over the profile's values, and `--standard` adds to its standards. See xref:pdf-export.adoc#publication-profiles[Publication profiles].

|`--theme <name\|file.yml>`
|A bundled theme, a theme found as `<name>-theme.yml` in the themes directory, or a theme file. It overrides the page's `pdf-theme` and `[pdf] theme`.

|`--fonts-dir <dir>`
|The directory of the theme's fonts, in place of the page's `pdf-fontsdir` and `[pdf] fonts_dir`. The bundled fonts remain available.

|`--output <file.pdf>`
|Where to write the PDF.

|`--standard pdf-a-1b\|pdf-a-1a\|pdf-a-2a\|pdf-ua-1`
|Make the PDF conform to a standard. Repeat the option to ask for more than one. Standards in `[pdf] standards` also apply.

|`--typst <file.typ>`
|Also write the generated Typst source, for inspection.

|`--fail-on none\|warning\|error`
|Exit with 1 when the export reports a diagnostic at least this severe, so CI can refuse a PDF with, for example, a diagram left as its source. The PDF is written all the same. The default, `none`, never fails for a diagnostic.
|===

The command waits for diagrams to render, then prints `<output> (<n> pages)` on standard output.
Warnings, such as an unknown theme key, a missing image or a diagram that could not be rendered (wherever it sits: in a list, a table cell or any other block), print on standard error as `path:line: warning: message`.
An export that fails, or reports a diagnostic that meets `--fail-on`, exits with 1, and a usage error exits with 2.

[[git-status]]
== git-status

`git-status` reports the Git state of the AsciiDoc files under `<root>`.
It finds the repository that holds `<root>` and does not run the `git` executable.

[source,sh]
----
adocfoundry-cli git-status docs
adocfoundry-cli git-status docs --format json
----

The default `text` format prints `branch <head>`, then one line per changed AsciiDoc file in the style of `git status --short`.
The head reads `main`, `detached @ 1a2b3c4` or `no commits yet`.
A file with changes against HEAD ends with the number of changed line runs; a deleted file has no number.

[source,text]
----
branch main
?? docs/new.adoc
 M docs/page.adoc (2 changed)
----

`--format json` prints one object.
`index` and `worktree` are each one of `unmodified`, `added`, `modified`, `deleted`, `renamed`, `untracked`, `ignored` or `conflicted`.

[source,json]
----
{
  "head": "main",
  "files": [
    { "path": "docs/new.adoc", "index": "unmodified", "worktree": "untracked", "hunks": 0 },
    { "path": "docs/page.adoc", "index": "unmodified", "worktree": "modified", "hunks": 2 }
  ]
}
----

If `<root>` is not in a Git repository the command fails with an error and exits with 2.
The other subcommands do not look at Git.

[[impact]]
== impact

`impact` reports what a change to the documentation may affect, and why.
It reads the workspace under `<root>` and takes exactly one source of the change.
Git stays off unless the source is a pair of revisions.

[source,sh]
----
adocfoundry-cli impact docs --base main --head HEAD
adocfoundry-cli impact docs --against HEAD --format json --output impact.json
adocfoundry-cli impact docs --changed-file modules/ROOT/pages/install.adoc
----

=== Sources

[cols="2,4"]
|===
|Option |Meaning

|`--base <ref> --head <ref>`
|Two local Git revisions: branches, tags, `HEAD~1` or commit ids. Both sides are read from the revisions' own files in Git. The working tree is never read, nothing is checked out or fetched, and the repository is not changed.

|`--against HEAD`
|`HEAD` against the working tree, which is the files on disk. The command line has no unsaved buffers.

|`--changed-file <path>`
|The paths named, relative to the root or absolute, against the working tree. Repeat the option for more paths. No base revision and no Git are needed. A path that exists is modified. A path that does not exist was removed, and then the report is partial (`no-base-revision`), since what used it cannot be known.
|===

Giving more than one source is an error.

=== Kinds of impact

[cols="2,4"]
|===
|Kind |Meaning

|Rendered content that may change (`render`)
|The changed page, and every page that includes the changed file, through nested partials.

|References to review (`reference_integrity`)
|Xrefs to a page that was moved or removed, and references to an anchor that was removed. An xref to a moved page is `broken` when the referring page still writes it, `resolved by alias` when the moved page's `page-aliases` covers it, and `resolved by change` when the reference no longer names it. A removed anchor is shown with its `#id`. A change to a page's prose never reaches the pages that merely link to it.

|Navigation (`navigation`)
|A changed navigation file or `antora.yml`, as the pages its component version's navigation lists before and after (`listed`, `unlisted`), and navigation entries that name a moved or removed page. It is reported for that component version only.

|Publications (`publication`)
|Each `[pdf.profiles]` profile whose selection holds an affected page. The impact is `potential` when the profile names content the revision does not have.
|===

Each impact has these facts:

* its confidence, `confirmed` or `potential`;
* the changed file it comes from;
* which revision's evidence shows it: `base`, `head` or `both`;
* the dependency path (`via`);
* the span of the reference that links them.

=== Output

The text format is the default.
It starts with `Impact of <what was compared>: complete|partial|unavailable`.
Next come what is not covered and the changed files.
The impacts follow, grouped by kind, each with `via a → b → c` and `at <file> bytes <start>–<end>`.
A note ends the report when the list was cut.

With `--format json` the output is the report.
It holds these fields:

* `schema_version`;
* `source`, whose `kind` is `git-refs` (with the `base` and `head` specs and commits), `working-tree` or `paths`;
* `completeness`, with a `status` and `gaps`;
* `changes`;
* `impacts`;
* `counts` per kind, before any cut;
* `truncated` (`shown` and `total`), present when more than `--max-impacts` impacts were found.

`--max-impacts <n>` limits the impacts listed.
The default is 1,000.
Paths are relative to the root and never absolute.
The output is deterministic, so the same refs give the same report.
`--output <file>` writes the report to a file.
Standard output holds only the report, and messages go to standard error.

=== Completeness

A gap has a stable reason.

[cols="2,4"]
|===
|Reason |Meaning

|`no-base-revision`
|A path was removed and there is no base revision to say what used it.

|`asset-consumers-not-analysed`
|A changed image or attachment. Its users are not traced yet.

|`not-in-catalog`
|A changed file is in no component version the workspace holds.

|`outside-every-root`
|A changed file is outside every root of the workspace.

|`revision-descriptor-unreadable`
|An `antora.yml` in a revision could not be read.
|===

=== Exit codes

[cols="1,4"]
|===
|Code |Meaning

|0
|The analysis finished, however many impacts it found. Many consumers is never a failure.

|2
|The source is invalid: an unknown ref, a folder in no Git repository for a ref comparison, a path outside the root, or more than one source. Also, with `--require-complete`, the report is partial or unavailable.
|===

=== Limits

* Images and attachments are not traced yet.
* Dynamic includes, such as `+include::{attr}/x.adoc[]+`, whose target the index cannot resolve are not followed.
* Components in other repositories are not analysed (the `not-in-catalog` gap).

=== Using it in CI

This job produces the report as an artifact on pull requests.

[source,yaml]
----
name: Documentation impact
on: pull_request
permissions:
  contents: read
jobs:
  impact:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0
      - name: Install adocfoundry-cli
        run: cargo install --git https://github.com/bovinemagnet/AdocFoundry adocfoundry-cli
      - name: Analyse the change
        run: |
          adocfoundry-cli impact docs --base "origin/${{ github.base_ref }}" --head HEAD --format json --output impact.json
          adocfoundry-cli impact docs --base "origin/${{ github.base_ref }}" --head HEAD --output impact.txt
      - uses: actions/upload-artifact@v7
        with:
          name: documentation-impact
          path: impact.*
----

`fetch-depth: 0` makes the base branch's commits available locally, because the command never fetches.
The job grants no write permission and posts nothing.
Posting a pull request comment is left to a separate, opt-in step.

[[new-module]]
== new-module

`new-module` makes a module in an existing Antora component version, as File › New Module… does in the app.
`<component-root>` is the folder that holds `antora.yml`.

[source,sh]
----
adocfoundry-cli new-module docs admin
adocfoundry-cli new-module docs admin-guide --families pages,partials,images,examples --index-title "Administration"
adocfoundry-cli new-module docs reference --no-nav
----

[cols="2,4"]
|===
|Option |Meaning

|`--families <list>`
|The families to make, separated by commas: `pages`, `partials`, `images`, `examples` and `attachments`. `pages` is always made. The default is `pages,partials,images`.

|`--no-nav`
|Does not make `nav.adoc` or list it in `antora.yml`.

|`--index-title <title>`
|The title of the index page. The default is the name in title case.
|===

The name uses lower-case letters, digits, `.`, `_` and `-`, and starts with a letter or digit, or it is `ROOT` when the component version has no `ROOT` module.
Each empty family folder holds a `.gitkeep` file.
The command prints each file it made, then the descriptor line it added.

[source,text]
----
made modules/admin/pages/index.adoc
made modules/admin/nav.adoc
listed modules/admin/nav.adoc in antora.yml
----

A name that is refused, such as one the component version has already, prints a message and exits with 2.
Nothing is written then.
See xref:using-the-editor.adoc#new-module[Make a new module] for what is made.

[[new-project]]
== new-project

`new-project` makes an Antora component in a folder, through the engine's `project.new` command.
The folder must exist and be empty, though a folder that holds only `.git` or `.DS_Store` counts as empty.
With `--subfolder`, the component goes in a new subfolder of a folder that is not empty, such as a code repository.

[source,sh]
----
adocfoundry-cli new-project site --name demo
adocfoundry-cli new-project site --name demo --title "Demo Guide" --version 1.0 --no-git --no-readme --no-playbook
adocfoundry-cli new-project my-repo --name handbook --subfolder docs
adocfoundry-cli new-project site --name demo --template product-docs
adocfoundry-cli new-project notes --template single-page
----

[cols="2,4"]
|===
|Option |Meaning

|`--template <id\|folder>`
|The template: a built-in or listed id (`minimal` by default), or a template's folder. See xref:using-the-editor.adoc#project-templates[Project templates].

|`--name <name>`
|The component's name. It is required, except for a template that uses no name, such as `single-page`.

|`--title <title>`
|The component's title. The default is the name in title case.

|`--version <version>`
|The component's version. Without it, or with `~`, the component is unversioned.

|`--subfolder <dir>`
|Makes the component in this new subfolder of `<folder>`. It must not exist already.

|`--no-git`
|Does not initialise a Git repository. By default one is initialised.

|`--no-readme`
|Does not make `README.adoc`.

|`--no-playbook`
|Does not make `antora-playbook.yml`, `package.json` or `.adocfoundry.toml`. By default they are made.
|===

The name uses lower-case letters, digits, `.`, `_` and `-`, and starts with a letter or digit.
It cannot be `ROOT`.
The version has no spaces and no `/`.
The command makes `antora.yml`, the `ROOT` module as `new-module` makes one, a `.gitignore`, a `README.adoc`, and the local playbook files `antora-playbook.yml`, `package.json` and, when the folder has none, `.adocfoundry.toml`.
It prints each file it made relative to `<folder>`, sorted, then `initialised a Git repository` when it made one.
The Git repository is made only when the folder is not already inside one, and nothing is staged or committed.

[source,text]
----
$ adocfoundry-cli new-project site --name demo --no-git
made .adocfoundry.toml
made .gitignore
made README.adoc
made antora-playbook.yml
made antora.yml
made modules/ROOT/images/.gitkeep
made modules/ROOT/nav.adoc
made modules/ROOT/pages/index.adoc
made modules/ROOT/partials/.gitkeep
made package.json
----

`adocfoundry-cli check site` then reports nothing.
A folder that is refused, such as one that is not empty or is inside a component, prints the reason on stderr and exits with 2.
Nothing is written then.
For a folder inside a component, use <<new-module>>.

[[graph]]
== graph

`graph` prints the link graph of the workspace under `<root>`, or of one page's neighbourhood.
It reads the same graph as the xref:graph-view.adoc[graph window].
Git stays off, unless you give `--ages`.

[source,sh]
----
adocfoundry-cli graph docs
adocfoundry-cli graph docs --page docs/modules/ROOT/pages/index.adoc --depth 2
adocfoundry-cli graph docs --format dot --no-partials | dot -Tsvg -o graph.svg
adocfoundry-cli graph docs --format svg > graph.svg
adocfoundry-cli graph docs --path docs/modules/ROOT/pages/index.adoc docs/modules/ROOT/pages/install.adoc
adocfoundry-cli graph docs --path docs/modules/ROOT/pages/index.adoc docs/modules/ROOT/pages/install.adoc --undirected --format svg > path.svg
----

[cols="2,4"]
|===
|Option |Meaning

|`--page <file>`
|Print only the pages within reach of this page, in both directions. A page that is not indexed is an error.

|`--depth <n>`
|How many links to follow from `--page`, 1 to 3. It needs `--page`; without it the command exits with 2.

|`--path <from> <to>`
|Print the graph along the shortest path from `<from>` to `<to>`, each a page's path or id as in the JSON.
It cannot be combined with `--page`.
The filter options apply, and links are followed only in their direction.
When there is no path, the command prints "no path from … to …" to standard error and exits with 1.
See xref:graph-view.adoc#_the_path_between_two_pages[The path between two pages].

|`--undirected`
|Follow links in both directions when finding the path.
It needs `--path`.

|`--format json\|dot\|svg`
|`json` (the default), Graphviz `dot`, or `svg`.
`svg` lays the graph out and draws it as the xref:graph-view.adoc#_export_the_graph[exported image], with colours following `[graph] colour_by`.
It works with `--page`, `--depth`, `--path` and the filter options.
With `--path`, `dot` and `svg` draw just the path.

|`--dark`
|Draws the SVG for a dark background.
It applies only to `--format svg`.

|`--ages`
|Turns Git on, reads the repository's history and adds `last_changed` to each node in the JSON.
Without it the command never reads Git.

|`--no-partials`
|Leave out partials.

|`--no-nav`
|Leave out navigation files and their edges.

|`--unresolved`
|Include the targets of links that do not resolve as nodes.
|===

The JSON has the graph's `revision`, its `nodes` and its `edges`.
Ids are paths relative to `<root>`, written with `/`; an unresolved target's id is its text.
`kind` is `page`, `partial`, `nav` or `unresolved`.
`coordinate` is `version@component:module:family`, with `~` for an unversioned component, and is left out outside Antora.
An edge's `kind` is `xref`, `include` or `nav`, and `count` is the number of links it stands for.
With `--ages`, a node also has `last_changed`: when its page last changed, in seconds since the Unix epoch, or `"uncommitted"` for a page with changes not committed.
A node with no age has none.
See xref:graph-view.adoc#graph-page-age[How long ago pages changed].

With `--path`, the JSON is the usual `nodes` and `edges` plus a `path` array, in order.
Each step has an `id`, a `title`, `links` (the kinds of link from the step before, empty for the first step) and `backwards` (true when the step was reached against a link's direction).

[source,json]
----
{
  "revision": 3,
  "nodes": [
    { "id": "modules/ROOT/pages/index.adoc", "title": "Home", "kind": "page",
      "coordinate": "~@docs:ROOT:page", "links_out": 2, "links_in": 1 }
  ],
  "edges": [
    { "from": "modules/ROOT/nav.adoc", "to": "modules/ROOT/pages/index.adoc", "kind": "nav", "count": 1 }
  ]
}
----

In `dot`, navigation files are boxes, partials are dashed and unresolved targets are dotted.
Include edges are dashed, navigation edges are dotted, and a count over 1 is the edge's label.

[[doctor]]
== doctor

`doctor` prints a report of the program, the system, the PDF setup, the tools it can find and the settings in force.
Paste it into an issue when reporting a problem.

[source,sh]
----
adocfoundry-cli doctor
adocfoundry-cli doctor docs
adocfoundry-cli doctor docs --format json
----

The report reads the user settings file the application reads, `adocfoundry/adocfoundry.toml` in the platform's configuration directory.
With `<root>`, it also reads that workspace's `.adocfoundry.toml`.
It holds no page content.
The command always exits with 0, even when it reports a missing tool or font.

[source,text]
----
AdocFoundry diagnostics

Program
  Version:  adocfoundry-cli 0.9.0
  Engine:   adoc-engine 0.9.0
  Build:    release
  Features: typst, git

System
  OS:           macOS 26.6.2
  Architecture: aarch64

PDF
  Theme:           default (bundled)
  Fonts directory: none (the bundled fonts only)
  Font families:   Noto Serif, M+ 1mn
  Fonts:           all found

Tools
  asciidoctor: /opt/homebrew/bin/asciidoctor (Asciidoctor 2.0.26 [https://asciidoctor.org])
  dot:         /opt/homebrew/bin/dot (dot - graphviz version 16.1.0 (20260904.0139))
  plantuml:    not found on PATH
  d2:          not found on PATH
  git:         /usr/bin/git (git version 2.54.0)

Settings
  User settings:      /Users/you/Library/Application Support/adocfoundry/adocfoundry.toml (not found)
  Workspace settings: docs/.adocfoundry.toml (not found)
  Workspace root:     docs
  Git:                on
  Warnings:           none
----

The sections, in order, are as follows.

Program::
The version of the program and of the engine, whether the build is `debug` or `release`, and the features it was built with (`typst` and `git`).

System::
The operating system and its version, and the architecture.

PDF::
The theme, resolved through `[pdf] themes_dir`, which reads `default (bundled)` or the theme file's path; the `[pdf] fonts_dir`, or `none (the bundled fonts only)`; and the font families the theme names.
Either `Fonts: all found` follows, or one `Missing` line for each font that is not found, such as `font X for Y not found`.
Any warnings from loading the theme appear as `Theme warning` lines.

Tools::
`asciidoctor`, `dot` (Graphviz), `plantuml`, `d2` and `git`.
Each shows its path and the first line of its version output.
A tool that is missing shows why: `not found on PATH`, or, for a setting that points nowhere, `not found: [tools] asciidoctor is X, which is not a file`.
A tool that does not answer within 15 seconds is reported as not answering.
`[tools] asciidoctor`, `[tools] git`, `[tools] dot`, `[tools] plantuml` and `[tools] d2` are honoured.

Settings::
The paths of the user and workspace settings files, each marked `(not found)` when missing, the workspace roots, whether Git is on or off, and each settings warning, or `Warnings: none`.

`--format json` prints one object of sections, each a title and its labelled lines.

[source,json]
----
{
  "sections": [
    {
      "title": "Program",
      "lines": [
        { "label": "Version", "value": "adocfoundry-cli 0.9.0" }
      ]
    }
  ]
}
----

The desktop application shows the same report, with its display details added.
See xref:using-the-editor.adoc#reporting-a-problem[Reporting a problem].

== Using it in CI

[source,yaml]
----
- name: Check the documentation
  run: adocfoundry-cli check docs --fail-on warning
----

[source,yaml]
----
- name: Audit the documentation
  run: adocfoundry-cli audit docs --require-complete --format sarif --output audit.sarif
- name: Upload the audit
  if: always()
  uses: github/codeql-action/upload-sarif@v3
  with:
    sarif_file: audit.sarif
----

Strict mode (`--require-complete`) is recommended in CI, so that a partial audit fails instead of passing.
SARIF locations are relative to the audited root, so for code scanning audit from the repository root, to match the repository's paths.

The archives attached to each release contain the binary for Linux, macOS and Windows, so no toolchain is needed.
Because the checker shares its code with the editor, it reports exactly what an author sees.
See xref:diagnostics.adoc[Diagnostics] for the codes.
