= adoc-kindle
Paul Snow
:revnumber: 0.0.0
:description: Kindle export: an export mapped to one book model, for AZW3 (KF8) and KFX (KF10) writers, in-house, with no PDF or Typst in between.

`adoc-kindle` turns a rendered view tree into a Kindle book.
It is at layer L2, beside `adoc-render`, which it reads.
The specification is `docs/prd/PRD-AdocFoundry_Kindle_Export.md` in the repository, and the spike's record is `docs/qa/spike-kindle.md`; neither is part of this site.
The engine calls the crate behind its `kindle` feature (`export.kindle_page`, `export.kindle_component` and `Engine::export_kindle_blocking`).
There is no CLI, app or MCP entry point for it yet (Kindle 7/9).

== What it does

The crate is given a `KindleDocument`, which is an article (a `KindlePage`) or a book (a `KindlePlan` of parts, headings and pages), and builds one `KindleBook` from it with `KindleBook::build`.
Each writer then writes that one book, so the two formats never differ in content.
It knows nothing of the engine, the workspace or a UI framework.

The book holds:

* chapters in reading order, with the ids `c1`, `c2` and so on, and their blocks and inlines;
* a nested table of contents;
* metadata: the title, authors, language, a stable `urn:uuid:` identifier derived from the title, authors and version, the publisher, the description, the date (from `revdate`) and the version (from `revnumber`);
* assets.

== Where it sits

`adoc-kindle` is headless.
It depends on `adoc-render`, an allowed same-layer pair listed in `SAME_LAYER_ALLOWED` in `xtask/src/layers.rs`, and on `adoc-core`, `adoc-dom` and `sha2`.
It must never build `adoc-pdf`, `adoc-docx`, Typst or the engine.
It starts no process and uses no network: `cargo xtask layers` refuses `std::process`, `Command::new`, `std::net`, `TcpStream` and `UdpSocket` in its sources.
It also checks that `adoc-kindle`, and the engine built with `--no-default-features --features kindle`, compile none of `adoc-pdf`, `adoc-docx`, `adoc-math` or Typst, which the test `kindle_builds_alone` holds.

== Anchors and links

* Anchors are generated, never taken from a path: `c<n>-a<m>` for an id a page defines, `c<n>-n<number>` for a footnote and `c<n>-r<number>` for its first mark.
They are stable, and cannot collide across pages.
* A cross reference becomes a link inside the book when its target page is in the book.
Otherwise it is the page's published URL when a site URL is configured, and failing that it stays text with a warning at its source.

== The API

`write_kindle(&KindleDocument, KindleFormat, &KindleOptions)` writes the book in memory and checks the bytes before returning them.
`KindleFormat::Azw3` is KF8, and `KindleFormat::Kfx` is KF10.
Both are written from the same `KindleBook`, and a format is never written in place of another.
A failure is a `KindleError`: `Unsupported`, `Invalid` or `TooLarge`.

The AZW3 writer exists (Kindle 3/9).
The KFX writer is still to come (Kindle 4/9), so writing KFX returns `KindleError::Unsupported`.

== The AZW3 writer

The writer is the `azw3` module.
It writes KF8 only, in a PalmDB/MOBI file with no MOBI7 part.

* Record 0 holds the PalmDOC header, a 264-byte version 8 MOBI header, the EXTH metadata (authors, publisher, description, date, identifier, start reading position, resource count, cover, title, language, writing mode and page progression) and the full title.
* The records after it are the text records, the fragment index and its CNCX strings, the skeleton index, the NCX index (the nested table of contents, with parent and child links), FDST (two flows: markup and stylesheet), the pictures, RESC (the spine), FLIS, FCIS and the end-of-file record.
* Each chapter is one skeleton with an empty `<body aid="...">`, and fragments of its body's top-level elements grouped up to 8 KiB.
* Internal links are `kindle:pos:fid:...:off:...`, written as fixed-width placeholders and filled in once every fragment is placed.
A link to an anchor the book lacks fails the export.
* Text records hold 4,096 bytes uncompressed, with only the multibyte trailing entry.
There is no PalmDOC compression and there are no indexing trailing byte sequences, both of which are optional for KF8 readers.
* The stylesheet sizes in `em` and names no font and no fixed width, so the reader's font, size and theme apply.
* The writer reads its own file back (the record list, record 0, every pointer's magic, FDST against the text length and the end-of-file record) before returning the bytes.

The tests use `adoc_kindle::testing::read_azw3` (feature `test-support`), a reader written apart from the writer.
It reassembles the chapters from skeletons and fragments, decodes the indexes and CNCX strings, and follows `kindle:pos` links.
The `mobi` crate (MIT, a dev-dependency only) reads the same files.
The tests are `azw3_is_a_kf8_container`, `azw3_reads_back_complete` and `kindle_never_substitutes_a_format` in the crate, and `kindle_and_pdf_select_the_same_pages` in the engine's `tests/kindle_export.rs`.

NOTE: The format facts come from epub3-kindle's MIT source (see the spike's record).
The output has not yet been checked on a Kindle device.
