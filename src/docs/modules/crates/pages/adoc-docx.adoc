= adoc-docx
Paul Snow
:revnumber: 0.0.0
:description: DOCX export: the view tree written as an editable Word package, in-house, with no PDF or Typst in between.

`adoc-docx` turns a rendered view tree into a Microsoft Word document that can be edited.
It is at layer L2, beside `adoc-render`, which it reads.
It is the first work package (DOCX 1/8, issue https://github.com/bovinemagnet/AdocFoundry/issues/618[#618]) of the DOCX export epic https://github.com/bovinemagnet/AdocFoundry/issues/613[#613].
The specification is `docs/prd/PRD-AdocFoundry_DOCX_Export.md` in the repository, which is not part of this site.
The engine calls the crate behind its `docx` feature (`export.docx_page`, `export.docx_component` and `Engine::export_docx_blocking`, DOCX 2/8), and there is still no CLI, app or MCP entry point for it (DOCX 7/8).

== What it does

The crate is given a `DocxDocument` and `DocxOptions`, and writes a `.docx` package to any `Write` sink.
It returns a `DocxReport` of diagnostics, or a `DocxError`.
It knows nothing of the engine, the workspace or a UI framework.

== Where it sits

`adoc-docx` is headless.
It depends on `adoc-render`, an allowed same-layer pair listed in `SAME_LAYER_ALLOWED` in `xtask/src/layers.rs`, and on `adoc-dom`.
It depends on `adoc-core` for `FileAccess`, through which it reads pictures.
It also uses `flate2` and `crc32fast`, and `resvg` at the workspace's version, which draws SVG; all were already in the dependency tree.
It must never build `adoc-pdf` or Typst.
`DOCX_EXCLUDED` in `xtask/src/layers.rs` lists them, `cargo xtask layers` checks it, and so does the test `docx_builds_without_typst`.

== The API

`write_docx(&DocxDocument, &DocxOptions, sink: impl Write) -> Result<DocxReport, DocxError>` is the one entry point.

[cols="1,3"]
|===
|Type |Meaning

|`DocxDocument`
|`Article(DocxPage)` or `Book(DocxBook)`.

|`DocxPage`
|A `key`, a `view` (the `ViewTree`) and a `depth`, which is how far the page's sections move down.

|`DocxBook`
|A `title`, an optional `subtitle`, `attributes` as a document header would set them, and `items`.

|`BookItem`
|`Part`, `Heading { title, depth }` or `Page`.

|`DocxOptions`
|A `paper`, `Paper::A4` by default or `Paper::Letter`, and `page_urls`, the published address of each page, which a cross reference to a page outside the document uses.
It also has `access`, the `FileAccess` that pictures are read through.

|`DocxReport`
|`diagnostics`, each a `DocxDiagnostic` with a `DocxSeverity`, a `message` and an optional `source` span.

|`DocxError`
|`Io` when the sink refuses the bytes, and `TooLarge` past 65,535 parts or 4 GiB, since the ZIP is written without ZIP64.
|===

== The package

The crate writes these parts, in a fixed order.

* `[Content_Types].xml`
* `_rels/.rels`
* `word/document.xml`, with `word/_rels/document.xml.rels`
* `word/styles.xml`
* `word/settings.xml`, always, holding compatibility mode 15 and, when there are footnotes, their separators
* `word/numbering.xml`, when there are lists
* `word/footnotes.xml`, when there are footnotes, with its separators first and its own relationships for links in footnotes
* `word/media/image<n>.png`, `.jpeg` or `.gif`, one for each distinct picture, each with its content type, and image relationships from the part that shows it (the document or the footnotes)
* `docProps/core.xml`, holding the title, the creator (from `author` or `authors`), the description and the keywords, and no dates

An external hyperlink is a relationship with `TargetMode="External"` of the part it is in.

== The body

Everything the crate writes comes from the view tree, by way of `body.rs` (blocks), `inline.rs` (runs, links and footnotes), `table.rs`, `numbering.rs` and `labels.rs`.

=== Headings, text and breaks

* The title is in the Title style, and a book's subtitle is in Subtitle.
* Sections and discrete headings use Word's built-in heading styles, `Heading1` to `Heading9`, named `heading 1` and so on, so that Word treats them as its own and gives them outline levels.
* Paragraphs are editable text, with tabs as Word tabs and line breaks as breaks.
* Thematic breaks are a bordered empty paragraph, and page breaks are page breaks.
* In a book, a page's title becomes a heading at the page's depth, and its sections move down by that depth.
* Where a book has parts, a part is Heading 1 on a new page, and everything else moves down one level.
* In a book, parts and chapters (pages and headings at depth 1) start a new page, except right after a part.

=== Inlines

* Strong, emphasis, mark (a yellow highlight), superscript and subscript are run properties.
* The `underline` and `line-through` roles are run properties too.
* Code is the character style `CodeChar`, and keys are `Keyboard`.
* Buttons and menus are bold.
* Hard line breaks are Word breaks, and tabs are Word tabs.

=== Lists

* Bullets and each ordered style (`arabic`, `loweralpha`, `upperalpha`, `lowerroman` and `upperroman`) have an abstract numbering of nine levels in `word/numbering.xml`.
* Each list is an instance of its own, and an ordered one overrides its level's start, so that it starts again at its `start`.
* The level is the list's nesting, up to Word's ninth, and an item's other blocks are indented under it.
* In a checklist only the items written with a box show one (a ballot box, ticked or not, then a tab), as in Asciidoctor.
The other items are bullets.
* A `reversed` list is numbered upwards, with a warning.
* A description list is its term in `DescriptionTerm` (bold), with the description indented below it.
* A callout list is `(n)` and a tab, and the listing shows ` (n)` at the end of its lines.

=== Code, quotes and captions

* Source and literal blocks are one paragraph each, in `SourceCode` and `LiteralBlock` (Consolas, shaded), with whitespace kept and lines as breaks.
There is no token colouring yet.
* Quotes are `Quote` paragraphs with a `QuoteAttribution`, and verses keep their lines in `Verse`.
* A block title is a `Caption` paragraph above its block, with the numbered caption.

=== Tables

* An AsciiDoc table is a Word table in the `AdocTable` style at full width, with its grid sized from `cols`.
* Header rows are repeated on each page (`tblHeader`).
* A column span is `gridSpan`.
A row span is `vMerge`, with its continuations placed on the grid below it, so that every row fills the grid.
* Cells take their alignment and their style: header and strong cells are bold, emphasis is italic, and monospace and literal cells use `CodeChar`.
* A short row is filled with empty cells.
Cells past the grid are left out, with a warning.
* Blocks in cells are written as anywhere else, nested tables included.
* Every cell ends with a paragraph, as Word requires.
* Two tables are kept apart by a `TableSpacer` paragraph, since Word would otherwise join them.
* The `frame`, `grid` and `stripes` options are not applied.

=== Admonitions, sidebars and examples

These are tables of one row, so that the blocks inside them stay editable in place.

* An admonition is `AdocAdmonition`, with a bar at the left and its label in a cell of its own.
The label comes from `note-caption` and the like.
* A sidebar is `AdocSidebar`, shaded.
* An example is `AdocExample`, boxed.

=== Links and bookmarks

* Every place a link can lead is named before anything is written, so a link may lead forward.
These are a page's start, every section and block id, and every inline anchor, as the PDF exporter's labels.
* Bookmarks are named `_a1`, `_a2` and so on, in document order.
Such a name is valid whatever the id, is at most 40 characters, and is hidden from Word's bookmark list by the underscore.
* A cross reference is decided as the PDF exporter decides it.
It leads to a bookmark of the document, else to the target page's published address (`DocxOptions::page_urls`, which the engine fills from `[pdf] site_url` or the playbook), else it stays text with a warning at its source.
* An external link is a hyperlink relationship with `TargetMode="External"` of the part it is in, so a link in a footnote is a relationship of `footnotes.xml`.
* Only `http`, `https`, `mailto`, `ftp`, `ftps`, `tel` and relative addresses are links.
Anything else stays text, with a warning.

=== Footnotes

* A footnote is a Word footnote, written in `word/footnotes.xml`, with a bookmark (`_f<n>`) around its mark.
* A later reference to the same footnote is a `NOTEREF _f<n> \f \h` field.
Word has no second reference to one footnote, so the field shows the same number in the footnote reference style and links to the footnote.
Its cached result is that number, so it reads correctly before any field update.
* A reference to a footnote the page does not have shows its number and is reported.

=== Pictures

Images, diagrams and formulas are embedded as inline DrawingML pictures.
`media.rs` reads, checks and keeps them, and `drawing.rs` writes them.

* A picture's format is told by its bytes, never by its extension.
PNG, JPEG and GIF are recognised, and so is SVG, by its root element past any declaration, comments and doctype.
* PNG, JPEG and GIF are embedded as they are, and identical bytes are one part however often the picture is shown.
Nothing in the package names the source files, so removing them changes nothing.
* An SVG, whether a file, a rendered diagram or a typeset formula, is drawn with `resvg` as a PNG at twice its own size, with its transparency kept.
Nothing is loaded from outside the file, and the system's fonts are read once per export, on the first SVG.
Only the PNG is written, because Word's SVG support (with a PNG fallback) is not shared by every reader, and a second copy would be needed.
* Pictures are read through `DocxOptions::access`, so an export for the MCP server reads only inside its roots.
* Each picture is checked whole, and its size is read from its headers without decoding it.
A file may be at most 64 MB, and a picture at most 10,000 pixels on a side and 40 million in all.
* Any other image is written as its alternative text, with a warning at its source that says why:
** it is missing, refused by the file access or unreadable;
** its format is not PNG, JPEG, GIF or SVG, which includes WebP, HEIC, BMP and TIFF, since Word may refuse them and converting them would need a decoder;
** it is cut short or damaged;
** it is too large.
* A remote image is never fetched.
It is written as a link to its address, when the address is a safe one, with a warning.
* The size comes from `width` and `height`, in pixels (`120` or `120px`) or as a share of the text width (`50%`).
When only one is given the other keeps the picture's proportions, and when neither is the picture has its own size at 96 pixels to the inch.
A picture is never wider than the text, or than its cell in a table.
* A block image, diagram or formula is a paragraph aligned by the block's `align`, with formulas centred by default.
Its title is the caption below it, aligned with it, as Asciidoctor places a figure's title.
* A block image's `link` makes the picture a hyperlink.
* Each picture's description in Word is its alt text: the image's alt, a diagram's `alt` attribute or its `diagram` name, or a formula's source.
* With the `typst` feature, block formulas arrive as rendered SVG and inline ones with their measures, and an inline formula is lowered to sit on the baseline of its line.
Without Typst, or where typesetting failed, a formula is its source, in `CodeChar` (inline) or `LiteralBlock` (block), with a warning.
Editable Word equations are not written.
* A diagram still rendering is its source with a warning.
A diagram that failed is its source too, and the engine reports the failure as it does for PDF.

=== Still written as text

These are written as text (alt text, source or address) and each is reported with its source span.

* Media (video and audio), passthrough blocks and unsupported blocks.

A table of contents block only gives a warning, until DOCX 5/8.
Cover and logo images come with DOCX 5/8.

=== Styles

The body uses these styles, which the package defines.
A reader can restyle any of them in Word, and the document follows.

[cols="1,3"]
|===
|Kind |Styles

|Paragraph
|`Title`, `Subtitle`, `Heading1` to `Heading9`, `Caption`, `Quote`, `QuoteAttribution`, `Verse`, `SourceCode`, `LiteralBlock`, `DescriptionTerm`, `FootnoteText` and `TableSpacer`

|Character
|`CodeChar`, `Keyboard`, `Hyperlink` and `FootnoteReference`

|Table
|`AdocTable`, `AdocAdmonition`, `AdocSidebar` and `AdocExample`
|===

== Why it is written in-house

The specification's open decision (§13) was whether to use the `docx-rs` crate.
This package's spike settled it against, for two findings about `docx-rs` 0.4.22.

* It numbers paragraphs, footnotes, bookmarks, headers and pictures from process-wide counters (`static AtomicUsize`), so a document's bytes would depend on what the process exported before.
The specification (§9) requires the same input to give the same bytes.
* It wrote control characters such as U+0001 straight into `word/document.xml`, which is then not well-formed XML.

So the crate writes the package itself, and needed no new dependency.

[cols="1,3"]
|===
|File |Responsibility

|`xml.rs`
|The one escaping writer every document string goes through.
It escapes `&`, `<` and `>`, and `"` in attributes, writes carriage returns and attribute tabs and line feeds as character references, and replaces the characters XML 1.0 forbids with U+FFFD.

|`zip.rs`
|Writes the ZIP in order, with every entry dated 1 January 1980 and no seeking.

|`package.rs`
|Writes the content types and each part's relationships in a fixed order.

|`parts.rs`, `body.rs`
|The parts' fixed contents, and the body written from the view tree.
|===

== Testing

[source,sh]
----
cargo test -p adoc-docx
ADOC_DOCX_OUT=/tmp cargo test -p adoc-docx --test package -- --ignored
ADOC_DOCX_OUT=/tmp cargo test -p adoc-docx --test content -- --ignored
ADOC_DOCX_OUT=/tmp cargo test -p adoc-docx --test media -- --ignored
----

`tests/package.rs` reads the package back with its own ZIP reader.
`docx_package_is_valid_opc` checks every CRC and size, that every part is well-formed and has a content type, that every relationship's target exists, that every `r:` id has a relationship and that every paragraph style used is defined.
These checks are shared in `tests/common`, and they also cover every part's relationships, the styles used, numbering, footnotes and bookmarks.
The same file holds `the_same_document_gives_the_same_bytes`, `a_book_s_pages_take_headings_at_their_depth` and `what_is_not_written_as_word_structure_yet_is_shown_as_text_and_reported`, which covers a missing image and a formula written as text.
`tests/content.rs` holds `docx_rich_content_uses_word_structures`, `docx_internal_links_reach_bookmarks`, `docx_unsupported_nodes_warn` and `a_link_that_is_not_a_web_or_mail_address_is_text`.
`tests/media.rs` holds `docx_media_is_embedded`, which embeds a PNG, a JPEG, a GIF, an SVG file, a diagram and inline and block formulas, and checks their sizes and content types, that one file shown twice is one part, that the SVG is drawn at twice its size and that nothing in the package names the source folder.
It also holds `docx_bad_images_are_reported`, in which each bad case is warned at its line and nothing is embedded, and a remote image is a link.
The engine's `diagrams_are_rendered_and_embedded` and `an_image_outside_the_roots_is_not_embedded` in `crates/adoc-engine/tests/docx_export.rs` cover the same through the export command.
`tests/escaping.rs` holds `docx_text_is_escaped`, `every_character_survives_or_is_replaced` (over every Unicode scalar value), `line_endings_become_breaks` and `empty_documents_are_written`.

The `ADOC_DOCX_OUT` command writes `article.docx` and `escaping.docx` (the `package` test) into the folder named, for opening by hand.
The `content` command writes `rich.docx` as well, and the `media` command writes `media.docx`.
LibreOffice 26 opened both and read the headings as headings.
In `rich.docx` it kept the table's spans, the nested lists, the footnote and the containers.
LibreOffice 26 rendered `media.docx` offline with every picture shown.
Microsoft Word has not been tried yet, and its manual checks come with DOCX 8/8.
