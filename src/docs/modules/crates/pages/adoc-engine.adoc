= adoc-engine
Paul Snow
:revnumber: 0.0.0
:description: The headless engine behind every front end: workspace, open documents, commands, undo, settings, workers, the pump and the events it publishes.

`adoc-engine` is the only entry point front ends use.
It is at layer L3, above the language and rendering crates and below the four front ends: `adocfoundry` (the desktop app), `adocfoundry-cli`, `adoc-ls` and `adoc-mcp`.
This page is a map of the crate and a guide to driving it.
The behaviour of each service is described in the developer guide's xref:developer:engine.adoc[engine page], which this page links to rather than repeats.

== What it does

The engine owns the workspace (its roots, Antora catalog and index), the open documents and their undo history, the command registry, the settings, the file watcher and the services built on them.
It publishes `EngineEvent` values.
Every user-visible action is a `Command` with a stable `CommandId`, so the app, the CLI, the language server and the MCP server all invoke commands and never reach into engine internals.
There is no public way to change a document's text except through a command, and every mutation is recorded in undo history.

=== Threading and the pump

One `Engine` is owned by a front end and mutated through `&mut self` on one thread.
Long work runs on workers, each started through `worker::spawn`, which turns a panic into the failure its job reports, so nothing waits for a worker that has gone.
A worker sends its result over a channel, and the front end applies it by calling `Engine::pump()`.
`next_due()` is the earliest deadline of every step of `pump`, `has_pending()` says whether to keep pumping, and `set_waker(f)` gives the engine a function that a worker, the writer or the watcher calls from any thread, so a front end sleeps until `next_due` or a wake rather than polling.
A new step in `pump` needs its deadline in `next_due` and a test in `tests/wake.rs`.
See xref:developer:engine.adoc#_threading_model[Threading model] and xref:developer:engine.adoc#_the_pump_and_worker_indexing[The pump and worker indexing].

=== Commands

A `Command` has a `CommandSpec` (a stable `CommandId` such as `document.save`, a title, a category, a default binding and a `when` context) and a `run` function taking `&mut Engine` and `CommandArgs`.
`commands::register_builtin` fills the `CommandRegistry` when an engine is made, and a duplicate id is a `RegistryError`.
`Engine::invoke(id, args)` runs a command, flushes pending index work first unless the command is typing, refreshes stale visual models afterwards, and emits `CommandFailed` on error.
Ids are constants in `commands::ids`.
`CommandOutcome` reports what happened (`Done`, `Opened`, `Location`, `Url`, `Preview` and others).

=== Events

`Engine::subscribe()` returns a `std::sync::mpsc::Receiver<EngineEvent>`.
Events include `WorkspaceIndexed`, `DocumentOpened`, `DocumentChanged` (with the version and the edits), `DiagnosticsUpdated`, `PreviewReady`, `ModelChanged`, `GraphChanged`, `AuditChanged`, `GitStatusChanged`, `ExportFinished` and `SettingsChanged`.
The full list and meanings are in xref:developer:engine.adoc#_events[Events].

=== Settings and features

`Settings` loads a user layer and a workspace layer (`<root>/.adocfoundry.toml`) from TOML.
Front ends never read the settings file themselves.
The keys are in xref:ROOT:settings.adoc#_keys[Settings: keys], and the engine's side is in xref:developer:engine.adoc#settings[Settings].
Two Cargo features, `typst` (PDF export and typeset STEM, through `adoc-pdf` and `adoc-math`) and `git` (`adoc-git`), are on by default for the crate and off in `[workspace.dependencies]`, so each front end names the ones it wants.
Without `git` the engine behaves as with `[git] enabled = false`; without `typst` the export commands are not registered.
See xref:developer:engine.adoc#_engine_features[Engine features].

== How to use it

A front end makes an engine from `Settings`, subscribes, opens a workspace, and then alternates between invoking commands and pumping.
This follows the engine's own integration tests.

[source,rust]
----
use std::{path::Path, time::Duration};

use adoc_core::SourceRange;
use adoc_engine::{commands::ids, CommandArgs, Engine, EngineEvent, Settings};

let settings = Settings::load(None, None).expect("settings").with_git_opt_in();
let mut engine = Engine::new(settings);
let events = engine.subscribe();

engine
    .open_workspace(vec![Path::new("tests/fixtures/simple").to_path_buf()])
    .expect("a folder");
assert!(engine.wait_for_workers(Duration::from_secs(10)));

let id = engine
    .open(Path::new("tests/fixtures/simple/guide.adoc"))
    .expect("a page");
engine
    .invoke(
        ids::EDIT_INSERT_TEXT,
        CommandArgs::Text {
            id,
            range: SourceRange::new(0, 0),
            text: "// note\n".to_owned(),
        },
    )
    .expect("edit");

engine.pump();
while let Ok(event) = events.try_recv() {
    if let EngineEvent::DocumentChanged { .. } = event {
        // Redraw from engine state.
    }
}
----

`Settings::with_git_opt_in()` keeps Git off unless a settings file turns it on, which is what a test that opens a fixture in place wants, since the fixtures lie inside a checkout.
A GUI does not block: it calls `pump` from a task that sleeps until `next_due()` or a wake.
A command line can block with `wait_for_workers`, `wait_until`, `render_blocking` or `export_blocking`.

The four front ends use it as follows.

* `adocfoundry` pumps from a task in `src/app.rs` and draws from engine state.
  See xref:developer:desktop-app.adoc[The desktop app].
* `adocfoundry-cli` runs commands and blocks on workers.
  See xref:adocfoundry-cli.adoc[adocfoundry-cli].
* `adoc-ls` opens the client's buffers with `Engine::open_client_text`, which the watcher never replaces and which keeps no undo history, and publishes diagnostics from `DiagnosticsUpdated`.
  See xref:adoc-ls.adoc[adoc-ls].
* `adoc-mcp` locks the engine on a blocking thread for each tool call, and sets `FileAccess::within(roots)` before it opens a workspace.
  See xref:adoc-mcp.adoc[adoc-mcp].

`adoc-engine` depends on `adoc-core`, `adoc-antora`, `adoc-audit`, `adoc-impact`, `adoc-diagrams`, `adoc-dom`, `adoc-graph`, `adoc-index`, `adoc-lang`, `adoc-model`, `adoc-parser`, `adoc-render` and `adoc-spell`, and, behind features, `adoc-git` (`git`) and `adoc-pdf` and `adoc-math` (`typst`).
It is the only crate allowed to depend on `adoc-audit` and `adoc-impact` (`ENGINE_ONLY` in `xtask/src/layers.rs`), and re-exports them as `adoc_engine::audit` and `adoc_engine::impact`.
The front ends that depend on it are `adocfoundry`, `adocfoundry-cli`, `adoc-ls` and `adoc-mcp`.
Nothing below the app may import a UI framework, nothing below `adoc-ls` may import LSP types, and no crate but the app may reach an HTTP client.
Logic that a front end could need belongs here, never in a view.

== Testing

[source,sh]
----
cargo test -p adoc-engine
cargo test --release -p adoc-engine --test perf -- --ignored --nocapture
cargo bench -p adoc-engine
----

Integration tests in `crates/adoc-engine/tests/` drive the engine headlessly through commands, one file per service (`documents.rs`, `keystroke.rs`, `preview.rs`, `visual.rs`, `export.rs`, `git.rs`, `audit.rs`, `impact.rs`, `graph.rs`, `wake.rs` and others).
`keystroke.rs` counts parses per keystroke with a `ManualClock`, and `wake.rs` checks that the pump and `next_due` agree.
`perf.rs` is a timing probe, ignored by default, and `benches/budgets.rs` holds engine paths to budgets (`BENCH_RECORD=1` only records).
Snapshots use `insta` and live in `tests/snapshots/`; review a changed snapshot rather than overwriting it.
Tests that open a fixture in place turn Git off with `Settings::with_git_opt_in()`.
Fixtures are under `tests/fixtures/`.
