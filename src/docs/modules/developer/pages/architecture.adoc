AdocFoundry is a layered workspace of crates.
A crate may depend only on crates in the layers below it.

Every crate also depends on `adoc-core`; the diagram shows that edge only for the language crates.

== The crates

[cols="1,2,5"]
|===
|Layer |Crate |Responsibility

|L0
|`adoc-core`
|Domain types only: `Document`, `LineIndex`, `SourceRange` (byte offsets), `Section`, `Anchor`, `Reference`, `IncludeDirective`, `ImageDirective`, `Location`, and `Diagnostic` with its `DiagnosticCode`. It has no dependencies at all.

|L1
|`adoc-parser`
|A line-oriented semantic parser, deliberately not tree-sitter and not a full AST. It extracts titles, sections, attributes, anchors, xrefs, includes and images from half-typed input without panicking, and runs on every keystroke.

|L1
|`adoc-dom`
|The full AST behind the `DocumentParser` trait, with `acdc-parser` as the parser and `asciidoc-parser` as a second implementation for comparison. It is the only crate that names a parser crate, so the parser stays swappable, and it applies typographic replacements to plain text.
acdc reads line ends as `\n`, so a page or include written with CRLF is given to it without its `\r` characters, and acdc's offsets are mapped back to the file's; spans in a Windows file cover the same text as in a Unix one.

|L1
|`adoc-antora`
|`antora.yml` and playbook parsing, `AntoraCatalog`, resource-ID parsing for `version@component:module:family$path`, the resolver, page aliases, descriptor reload, navigation trees, and the playbook's content sources (`ContentSource`) with the table of versions per branch (`PublishedVersions`).

|L1
|`adoc-index`
|`WorkspaceIndex`, with replacement-based updates and direct map lookups. It never scans every document. Path normalisation is lexical and never canonicalises, so unsaved files work; it keeps the leading `..` of a relative path and stops at the root of an absolute one. Reverse maps from the file name an xref or include names, and from each fragment, to the references (`xrefs_naming`, `includes_naming`, `references_with_fragment`) keep reference lookups from visiting every document.

|L1
|`adoc-lang`
|Editor-agnostic language features on byte offsets: definition, hover, completion, diagnostics, document and workspace symbols, and attribute resolution. Both `adoc-ls` and `adoc-engine` call it. It also finds references (`references_at`, `page_references`, `includes_of`) and renames anchors (`rename_anchor`).

|L2
|`adoc-render`
|A framework-free view tree (`ViewTree`, built from a `Dom` by `build_view` through a `ViewResolver`), a standalone HTML backend, and the optional external Asciidoctor renderer used by the language server's preview. The engine and the application use the view tree; the command-line `render` uses the HTML backend. `to_text` writes the view tree as plain text, for `adoc-mcp`'s `render_page`.

|L2
|`adoc-diagrams`
|Diagram rendering for the preview. Mermaid is rendered in process through `merman`, other kinds (Graphviz, PlantUML, D2) through external tools run from the paths given (`ToolPaths`, from the engine's `[tools]` settings) or discovered on the `PATH`, and every result is cached on disk by checksum.
`ExternalProvider` writes the source on a thread, reads both outputs on threads capped at `MAX_OUTPUT` (32 MB), and polls the child against a deadline (`with_timeout`, `ToolPaths::timeout`, `DEFAULT_TIMEOUT` of 30 s, from `[tools] diagram_timeout`), killing it and returning `DiagramError::TimedOut` or a `Failed` message.

|L2
|`adoc-model`
|The editable model behind the visual editor. It depends on `adoc-core` and `adoc-dom`, and the engine depends on it. A `Model` is typed blocks whose text is scanned losslessly into pieces (text, marks and atoms) that each know their exact source bytes, checked against the DOM. A `Step` on the model yields minimal `SourceEdit` values, an inverse, and a position `Mapping`. The source stays the truth; see xref:engine.adoc#the-visual-model-service[the engine].

|L2
|`adoc-git`
|Git repository discovery, head, status line diffs against HEAD, and branches and file contents at a branch, over `gix` (gitoxide) with no network transports. Nothing runs the `git` executable. The `test-support` feature provides `adoc_git::testing::TestRepo` for tests. The engine depends on it.

|L2
|`adoc-pdf`
|PDF export. A theme loader for asciidoctor-pdf's YAML themes, an emitter from the view tree to Typst, a Typst `World` with bundled fonts, in-process compilation with errors mapped back to AsciiDoc lines, book assembly, the index, and PDF/A-2a and PDF/UA-1. It depends on `adoc-core`, `adoc-render` and Typst. See xref:pdf.adoc[PDF export].

|L3
|`adoc-engine`
|Documents, commands, undo, workspace, file watcher, settings, Git state, search and rename, the preview, visual model and export services, and the `EngineEvent` stream. The only entry point front ends use. `report.rs` holds the diagnostics and Git status reports, and `inspect.rs` the target and resource-id queries; see xref:engine.adoc#reports-and-inspection[the engine].

|L4
|`adocfoundry`
|The GPUI desktop application. The only crate that imports a UI framework.

|L4
|`adocfoundry-cli`
|The headless binary: `check`, `symbols`, `follow`, `render`, `pdf` and `git-status`.

|L4
|`adoc-ls`
|The language server. The only crate that speaks the Language Server Protocol. It runs on `adoc-engine`, which it depends on without the `typst` and `git` features by default; `cargo xtask layers` checks that the default build compiles neither Typst nor Git.

|L4
|`adoc-mcp`
|The MCP server. It depends only on `adoc-engine` (with `typst` and `git`) and `adoc-core`. It uses `rmcp` 3.7.0 with its `server`, `macros`, `transport-io` and `transport-streamable-http-server` features. With `--http` it serves the Streamable HTTP transport through `hyper` and `hyper-util`, built with their server side only, on a loopback address and for requests carrying its token (`src/http.rs`). It runs on a current-thread tokio runtime (`rt`, `macros`, `io-std`, `time`, `net` and `signal`), and each tool locks the engine for its call; every HTTP session shares that engine. Path confinement is `paths::confine`, and the engine is confined too through `FileAccess`. See xref:ROOT:mcp-server.adoc[MCP server].
|===

The application sees `adoc-model` types only through the engine's re-exports.

== Layering rules

`cargo xtask layers` reads the `Cargo.toml` of every crate under `crates/` and fails the build if:

* a crate is not listed in the layer table in `xtask/src/layers.rs`;
* a crate depends on a crate in a higher or equal layer, except for the explicit same-layer pairs `adoc-index` to `adoc-parser`, `adoc-lang` to `adoc-parser`, `adoc-index` and `adoc-antora`, and `adoc-pdf` to `adoc-render`;
* `adoc-core` has any dependency;
* a UI framework crate (`gpui`, `gpui-pre`, `gpui-pre-platform`, `gpui-component`, `gpui-base`, `gpui-kit-assets`, `egui`, `eframe`) appears outside `adocfoundry`;
* an LSP crate (`lsp-types`, `lsp-server`) appears outside `adoc-ls`;
* an HTTP client crate (`reqwest` and its GPUI fork, `ureq`, `isahc`, `curl`, `attohttpc`, `surf`) is reachable from any crate except `adocfoundry`, directly or through its normal or build dependencies;
* `hyper` or `hyper-util` is reachable from any crate except `adocfoundry` and `adoc-mcp`, or `adoc-mcp`'s own build turns on a `client` feature of either;
* a parser crate (`acdc-parser`, `asciidoc-parser`) appears outside `adoc-dom`;
* `adoc-lang` depends on `url`, or its sources mention `lsp_types`, `lsp_server` or `url::`.

Adding a crate means adding a line to the layer table in `xtask/src/layers.rs` and to the ladder in the repository's contributor guidance.

=== The network rule

The network rule is checked against the resolved graph from `cargo metadata`, so a transitive dependency counts.
The application reaches an HTTP client only through `gpui-kit-assets`.
`hyper` and `hyper-util` have a server side and a client side.
`adoc-mcp` may reach them for its HTTP listener (`NETWORK_SERVER_ALLOWED`).
The check takes `adoc-mcp`'s features from `cargo tree -p adoc-mcp -e features` rather than from `cargo metadata`, because `cargo metadata` unifies features over the workspace.
A `client` or `client-…` feature of either crate in that build is a violation.
Everything below the application, including diagram rendering and PDF export, works locally and never contacts a server.

=== The one `lsp-types` exception

The editor widget in gpui-component offers definition, hover and completion only through provider traits typed with `lsp-types`.
Rewriting those widgets would cost far more than a translation module, so `adocfoundry` is permitted to depend on `lsp-types`.
The exception is listed in `LSP_ALLOWED` in `xtask/src/layers.rs`.
Only `crates/adocfoundry/src/editor/providers.rs` uses those types, translating engine results into them.
`lsp-server` stays confined to `adoc-ls`.

== Design rules to preserve

. The engine is the only owner of document text and semantics.
. All mutations are commands with stable ids and undo groups, with no exceptions for small edits.
. Language behaviour lives in `adoc-lang`; `adoc-ls` and the engine are thin over it.
. Byte offsets are used below the front ends, and `LineIndex` converts at the edge.
. UI framework imports stay in `crates/adocfoundry`, so a different UI toolkit would be a one-crate swap.
. tree-sitter is for syntax only: highlighting, folding, outline hints and injections. Attribute evaluation, include expansion, Antora coordinates and cross-file references never use it.
. Dependencies are pinned exactly and pass `cargo deny` (permitted licences are MIT, Apache-2.0, BSD, MPL-2.0, Unlicense and OFL for fonts).
. No Node.js, JVM or Ruby is required at run time. External tools are optional and discovered.

See also xref:engine.adoc[the engine] and xref:desktop-app.adoc[the desktop app].
