:description: The crate ladder, each crate's responsibilities and the layering rules that CI enforces.

AdocFoundry is a layered workspace of crates.
A crate may depend only on crates in the layers below it.

Every crate also depends on `adoc-core`; the diagram shows that edge only for the language crates.

== The crates

[cols="1,2,5"]
|===
|Layer |Crate |Responsibility

|L0
|`adoc-core`
|Domain types and the few helpers every layer shares: `Document`, `LineIndex` (columns in bytes), `SourceRange` (byte offsets), `Section`, `Anchor`, `Reference`, `IncludeDirective`, `ImageDirective`, `Location`, `Related`, and `Diagnostic` with its `DiagnosticCode`; section ids (`IdStyle`, `section_ids`); lexical paths (`normalize_path`); the default ignore list and its rule (`DEFAULT_IGNORED_DIRECTORIES`, `is_ignored_beneath`); `FileAccess`, which reads files only within given roots, following links to check them; and the `probe` counters tests read. It has no dependencies at all.

|L1
|`adoc-parser`
|A line-oriented semantic parser, deliberately not tree-sitter and not a full AST. It extracts titles, sections, attributes, anchors, xrefs, includes and images from half-typed input without panicking, and runs on every keystroke. Inside listing, literal, passthrough and comment blocks it reads only include directives (none in comment blocks), whatever the delimiter's length, because a block closes on a line matching its own delimiter; the same holds for `+```+` fences and for paragraphs styled `[source]`, `[listing]` or `[literal]`.

|L1
|`adoc-dom`
|The full AST behind the `DocumentParser` trait, with `acdc-parser` as the parser and `asciidoc-parser` as a second implementation for comparison, behind the crate's `comparison` feature. Only `adocfoundry-cli` enables it, for `render --parser asciidoc-parser`, so the app, `adoc-ls` and `adoc-mcp` do not compile it, and the `second_parser` test needs the feature (`required-features`). It is the only crate that names a parser crate, so the parser stays swappable, and it applies typographic replacements to plain text.
acdc reads line ends as `\n`, so a page or include written with CRLF is given to it without its `\r` characters, and acdc's offsets are mapped back to the file's; spans in a Windows file cover the same text as in a Unix one.

|L1
|`adoc-antora`
|`antora.yml` and playbook parsing, `AntoraCatalog`, resource-ID parsing for `version@component:module:family$path`, the resolver, page aliases, descriptor reload, navigation trees, and the playbook's content sources (`ContentSource`) with the table of versions per branch (`PublishedVersions`). `Playbook` and `ComponentDescriptor` give their `asciidoc.attributes` as `AttributeEntry`s (`attribute_entries`), unsets included, each with the range of its key.

|L1
|`adoc-index`
|`WorkspaceIndex`, with replacement-based updates and direct map lookups. It never scans every document. Path normalisation is lexical and never canonicalises, so unsaved files work; it keeps the leading `..` of a relative path and stops at the root of an absolute one. Reverse maps from the file name an xref or include names, and from each fragment, to the references (`xrefs_naming`, `includes_naming`, `references_with_fragment`) keep reference lookups from visiting every document. Every table is keyed by file, or holds the file's one shared path (`Arc<Path>`), so replacing or removing a file visits only what that file contributed. An anchor id maps to where it is first declared. The name and fragment maps hold each reference's place in its file's document rather than a copy of it. `AnchorLocation` and `ReferenceLocation` are views borrowed from the index. Symbol search keeps, for each word of a symbol's name, the files with a symbol holding it. A query intersects the files of each of its words, fewest first, and checks only those files' symbols. A file indexed from disk (`index_file`, `replace_from_disk`, and the parse workers of `index_roots_with`) keeps its parse but not its text, which was most of what the index held. `FileEntry::text` reads the text back from the file. It returns `None` once the file no longer holds the text that was parsed, checked by length and hash, so offsets into the parse are never applied to other text. A document given to `replace`, which is how the engine indexes an open page, keeps its text. `Document::text` is an `Arc<str>`, so an open page's parse and its index entry share one allocation. A page rename is refused while a page that references the renamed page has changed on disk and has not been indexed again, rather than leaving that reference out of the change. `tests/memory.rs` is an ignored probe of the index's time and peak memory for 10,000 pages of about 8 KB, run under `/usr/bin/time -l`. It measures about 200 MB peak (2 MB without pages) for 97 MB of text, 0.6 s to index, and 0.1 ms to replace one page.

|L1
|`adoc-lang`
|Editor-agnostic language features on byte offsets: definition, hover, completion, diagnostics, document and workspace symbols, and attribute resolution. Both `adoc-ls` and `adoc-engine` call it. It also finds references (`references_at`, `page_references`, `includes_of`) and renames anchors (`rename_anchor`), and `graph::links_from` resolves the xrefs and includes of one file for the link graph. Its `effective` module resolves an attribute's value at a place by Antora's rules (`effective_attribute`, `resolve`, and `attribute_name_at` for the name under the caret), and hover and definition use it.

|L1
|`adoc-math`
|Converts STEM notation to Typst maths markup: AsciiMath through `asciimath-parser`, converted in-house, and LaTeX through `mitex`. `is_safe` refuses any markup holding code (`#`) or a name outside Typst's maths scope and `HELPERS`. Only checked markup (`TypstMath`) ever reaches Typst's `eval`, and whoever evaluates it defines `HELPERS` in its scope. It has no internal dependencies. `adoc-pdf` typesets the checked maths in PDFs (see xref:pdf.adoc#_maths[Maths]), and the engine uses it for typeset STEM in the preview and HTML, which comes with the engine's `typst` feature.

|L1
|`adoc-spell`
|Spell checking with no knowledge of AsciiDoc. It wraps `spellbook`, which no other crate names (`cargo xtask layers` checks this). `Dictionaries` holds the bundled SCOWL `en_GB` and `en_US` dictionaries and any others loaded from a folder. `words` splits text into checkable words, skipping those that are not words (`OBJECT` stands in for an atom), and `WordList` holds the workspace and user word lists. The engine's `src/spelling.rs` reads prose from the visual model and checks open pages on a worker.

|L1
|`adoc-graph`
|General graph code with no knowledge of AsciiDoc and no internal dependencies. `GraphKey` (a normalised path or an unresolved target's text), `EdgeKind`, `NodeKind`, `GraphNode`, `GraphEdge`, `GraphSnapshot` and `GraphFilter` are its types. `GroupBy`, `Groups` and `group_name` name each node's group: its module or its component version, or `Other` outside Antora. `GraphSnapshot::collapse` draws named groups as one node keyed `GraphKey::Group` (kind `NodeKind::Group`), with their links merged and their counts summed. `LinkStore` keeps each file's links keyed by the file that owns them (a navigation file owns its tree's links), with the reverse maps hashed because `Path` compares component by component. `Layout` is a seeded, deterministic force-directed layout: Barnes–Hut above 500 nodes, `f32` only, no trigonometry, and it cools and settles. `Layout::set_roots` seeds starts from root-relative paths. `Layout::set_grouping` adds a pull towards each group's centre and a push between groups, still deterministic and `f32` only, and one step for 2,000 nodes stays within the same 8 ms bench budget grouped or not. It has its own `Point`. `tree.rs` holds `MindMap`, built by `MindMap::build(snapshot, root, depth, owned)` (`owned` being the links a navigation file root owns, so its tree is only its own entries) breadth first with one parent for each node chosen by link rank, then the parent's order, and giving `children`, `parent`, `depth`, `is_tree_link`, `visible(collapsed)` and `positions(style, collapsed)` for a `TreeStyle` (`Horizontal` or `Radial`) spaced by `LEVEL_GAP` and `SIBLING_GAP`; the radial layout uses polynomial sines and cosines of its own, so every platform gives the same bits. `GraphSnapshot::restrict(keep)` cuts a snapshot down to some nodes, recounting links, and `Layout::set_targets` eases nodes towards given places instead of moving them by force, keeping the targets across `sync` and leaving pinned nodes where they are. `cargo bench -p adoc-graph` also times building and laying out a mind map of 2,000 nodes and 6,000 edges within the same 8 ms budget. `LastChanged` (`Uncommitted` or `At(seconds)`) is a node's `last_changed`, set through `NodeInput::last_changed`; `ColourBy::Age` and `Palette` (`Palette::of(snapshot, by)` and `colour(node, dark)`; `Palette::with_groups` ranks a drawing's groups among the workspace's, through `colour_groups` and the engine's `graph_colour_groups`, so a group keeps its colour in any part of the graph) give each node its colour, and a collapsed group takes its newest member's age. The engine's `graph.rs` joins it to `adoc-lang`'s `graph::links_from`; see xref:engine.adoc#the-link-graph[the engine].

|L2
|`adoc-render`
|A framework-free view tree (`ViewTree`, built from a `Dom` by `build_view` through a `ViewResolver`), a standalone HTML backend, and the optional external Asciidoctor renderer used by the language server's preview. The engine and the application use the view tree; the command-line `render` uses the HTML backend, and `embed_local_files` turns its local `file://` images into `data:` URIs for the application's HTML export. `to_text` writes the view tree as plain text, for `adoc-mcp`'s `render_page`.

|L2
|`adoc-diagrams`
|Diagram rendering for the preview. Mermaid is rendered in process through `merman`, other kinds (Graphviz, PlantUML, D2) through external tools run from the paths given (`ToolPaths`, from the engine's `[tools]` settings) or discovered on the `PATH`, and every result is cached on disk by checksum.
`DiagramRequest::directory` is the page's folder, in which the external tools run, `DiagramProvider::identity` is empty by default and, for `ExternalProvider`, holds the program's fingerprint (resolved path, size and modification time), that folder, and the size and modification time of each file `DiagramProvider::inputs` names, and `Diagrams::checksum` folds a non-empty identity into `DiagramRequest::checksum`, so Mermaid keeps its key.
`ExternalProvider::inputs` (`reads.rs`) finds the local files a diagram names for its tool (PlantUML includes, imports and `!theme ... from`, Graphviz `image` and `shapefile`, D2 imports and `icon` paths), conservatively and lexically: only plain paths inside the page's folder, never a URL, variable or standard-library name. The engine adds them to a preview's and a visual view's sources, so the watcher's report of a change to one shows the page again.
The fingerprint is kept once the program is found, until `Diagrams::look_for_tools_again` (the engine's `preview.retry_diagrams`), and a program not found is looked for again after a second, so one installed meanwhile is used.
`ExternalProvider` writes the source on a thread, reads both outputs on threads capped at `MAX_OUTPUT` (32 MB), and polls the child against a deadline (`with_timeout`, `ToolPaths::timeout`, `DEFAULT_TIMEOUT` of 30 s, from `[tools] diagram_timeout`), killing it and returning `DiagramError::TimedOut` or a `Failed` message.
The tool runs in a process group of its own and is stopped with everything it started, through `adoc_diagrams::process` (`in_own_group`, `stop`: `rustix`'s `kill_process_group` on Unix, `taskkill /T` on Windows), which the engine's site build uses too.
`MermaidProvider` (`with_timeout`) gives merman's `OperationControl` the same deadline and returns `DiagramError::TimedOut` when it passes.

|L2
|`adoc-model`
|The editable model behind the visual editor. It depends on `adoc-core` and `adoc-dom`, and the engine depends on it. A `Model` is typed blocks whose text is scanned losslessly into pieces (text, marks and atoms) that each know their exact source bytes, checked against the DOM. A `Step` on the model yields minimal `SourceEdit` values, an inverse, and a position `Mapping`. The source stays the truth; see xref:engine.adoc#the-visual-model-service[the engine].

|L2
|`adoc-git`
|Git repository discovery, head, status line diffs against HEAD, and branches and file contents at a branch, over `gix` (gitoxide) with no network transports. Nothing runs the `git` executable. `history.rs` gives `Repository::last_changed(paths, limit)`, one walk of `HEAD`'s first-parent history that finds when each path last changed, following moves, as `LastChanges` (a `LastChange` of commit and time for each path, and `cut_short`), with `HISTORY_LIMIT` (10,000 commits). `last_changed_since(paths, since, limit)` stops at the commit `since` when `HEAD` descends from it by first parent, and lists the paths no later commit changed, with their names there, in `unchanged_since`; in a shallow clone it stops at the boundary as at the limit. The `test-support` feature provides `adoc_git::testing::TestRepo` for tests, including `commit_all_at(message, seconds)`. The engine depends on it.

|L2
|`adoc-pdf`
|PDF export. A theme loader for asciidoctor-pdf's YAML themes, an emitter from the view tree to Typst, a Typst `World` with bundled fonts, in-process compilation with errors mapped back to AsciiDoc lines, book assembly, the index, and the PDF/A-1b, PDF/A-1a, PDF/A-2a and PDF/UA-1 profiles. It depends on `adoc-core`, `adoc-render` and Typst. See xref:pdf.adoc[PDF export].

|L2
|`adoc-audit`
|The documentation quality audit's model, pure and synchronous: no threads, settings files, file writes, subprocesses or network. `RuleId` and `RULES` give the stable rule IDs and the registry. A `FindingCode` is either one of the audit's `quality.*` rules or an existing `DiagnosticCode`, aggregated with its own severity and message and never restated as a rule. `AuditBuilder` collects findings, skips and coverage gaps in any order, and `finish` applies the `Policy` and sorts them, giving an immutable, serialisable `AuditReport` versioned by `SCHEMA_VERSION`. Its paths are relative to a workspace root, use `/` separators and are never absolute. `Completeness` describes coverage with stable gap reasons, and a skipped dynamic construct never makes a report partial. The `Policy` holds rule severities, exclusions (one resource each, by resource ID, with a reason), `fail_on` and `require_complete`, and `AuditReport::verdict` gives the pass, fail or untrustworthy result a gate uses. It depends on `adoc-core`, `adoc-antora`, `adoc-index` and `adoc-lang`. `audit` takes an `AuditInput` (the workspace's index and catalog, its roots, and a reader for navigation files, so unsaved buffers count) and a scope, and returns the findings, skips and per-version navigation coverage (`NavCoverage`) to finish under a policy. An audit is made of parts that never depend on the scope, each file's (`audit_file`) and each component version's (`audit_version`), which `assemble` puts together for a scope; `audit` computes the parts in scope and assembles them, and the engine keeps the parts and assembles them on request, so both give the same report. `to_sarif` writes a report as SARIF 2.1.0, with excluded findings as suppressed results, gaps as tool execution notifications and 1-based character regions from a `Region` lookup the caller gives, since only the caller reads files. It passes through every in-scope file's existing diagnostics, a navigation file's unresolved entries among them as its own `adoc.unresolved-xref-file`, and runs three rules: `quality.navigation.unlisted-page` (a published page that no navigation file of its own component version reaches, aliases included; the start page counts as listed; a version whose navigation includes another file, names an attribute or cannot be read has its unlisted pages skipped), `quality.page.missing-title` (skipped when an include before the first section may give the title) and `quality.image.missing-alt` (block and inline image macros in pages and partials with no alternative text written at all). The engine reads the `[quality]` settings and re-exports the crate as `adoc_engine::audit`; front ends never name it.

|L2
|`adoc-impact`
|The impact analysis's model, pure and synchronous like `adoc-audit`: no threads, Git, file writes, processes or network, and `cargo xtask layers` checks its sources against the same forbidden-paths list. It depends on `adoc-core`, `adoc-antora`, `adoc-index` and `adoc-lang`, with `serde`. Given the files a change touched and a `DependencySnapshot` for each side, `analyse` reports the pages the change affects. The engine re-exports the crate as `adoc_engine::impact`; front ends never name it. See xref:engine.adoc#impact-analysis[the impact analysis].

|L3
|`adoc-engine`
|Documents, commands, undo, workspace, file watcher, settings, Git state, search and rename, the preview, visual model and export services, and the `EngineEvent` stream. The only entry point front ends use. `report.rs` holds the diagnostics and Git status reports, and `inspect.rs` the target and resource-id queries; see xref:engine.adoc#reports-and-inspection[the engine].

|L4
|`adocfoundry`
|The GPUI desktop application. The only crate that imports a UI framework.

|L4
|`adocfoundry-cli`
|The headless binary: `check`, `symbols`, `follow`, `render`, `pdf`, `git-status`, `graph` and `doctor`.

|L4
|`adoc-ls`
|The language server. The only crate that speaks the Language Server Protocol. It runs on `adoc-engine`, which it depends on without the `typst` and `git` features by default; `cargo xtask layers` checks that the default build compiles neither Typst nor Git.

|L4
|`adoc-mcp`
|The MCP server. It depends only on `adoc-engine` (with `typst` and `git`) and `adoc-core`. It uses `rmcp` 3.7.0 with its `server`, `macros`, `transport-io` and `transport-streamable-http-server` features. With `--http` it serves the Streamable HTTP transport through `hyper` and `hyper-util`, built with their server side only, on a loopback address and for requests carrying its token (`src/http.rs`). It runs on a current-thread tokio runtime (`rt`, `macros`, `io-std`, `time`, `net` and `signal`), and each tool locks the engine for its call; every HTTP session shares that engine. Path confinement is `paths::confine`, and the engine is confined too through `FileAccess`. See xref:ROOT:mcp-server.adoc[MCP server].
|===

The application sees `adoc-model` types only through the engine's re-exports.

== Layering rules

`cargo xtask layers` reads the `Cargo.toml` of every crate under `crates/` and fails the build if:

* a crate is not listed in the layer table in `xtask/src/layers.rs`;
* a crate depends on a crate in a higher or equal layer, except for the explicit same-layer pairs `adoc-index` to `adoc-parser`, `adoc-lang` to `adoc-parser`, `adoc-index` and `adoc-antora`, and `adoc-pdf` to `adoc-render`;
* `adoc-core` has any dependency;
* a UI framework crate (`gpui`, `gpui-pre`, `gpui-pre-platform`, `gpui-component`, `gpui-base`, `gpui-kit-assets`, `egui`, `eframe`) appears outside `adocfoundry`;
* an LSP crate (`lsp-types`, `lsp-server`) appears outside `adoc-ls`;
* an HTTP client crate (`reqwest` and its GPUI fork, `ureq`, `isahc`, `curl`, `attohttpc`, `surf`) is reachable from any crate except `adocfoundry`, directly or through its normal or build dependencies;
* `hyper` or `hyper-util` is reachable from any crate except `adocfoundry` and `adoc-mcp`, or `adoc-mcp`'s own build turns on a `client` feature of either;
* a parser crate (`acdc-parser`, `asciidoc-parser`) appears outside `adoc-dom`;
* `spellbook` appears outside `adoc-spell`;
* a front end (`adocfoundry`, `adocfoundry-cli`, `adoc-ls` or `adoc-mcp`) names `adoc-audit` or `adoc-impact` directly instead of reaching it through `adoc-engine` (the `ENGINE_ONLY` list in `xtask/src/layers.rs`);
* `adoc-lang` depends on `url`, or its sources mention `lsp_types`, `lsp_server` or `url::`.

Adding a crate means adding a line to the layer table in `xtask/src/layers.rs` and to the ladder in the repository's contributor guidance.

=== The network rule

The network rule is checked against the resolved graph from `cargo metadata`, so a transitive dependency counts.
The application reaches an HTTP client only through `gpui-kit-assets`.
`hyper` and `hyper-util` have a server side and a client side.
`adoc-mcp` may reach them for its HTTP listener (`NETWORK_SERVER_ALLOWED`).
The check takes `adoc-mcp`'s features from `cargo tree -p adoc-mcp -e features` rather than from `cargo metadata`, because `cargo metadata` unifies features over the workspace.
A `client` or `client-…` feature of either crate in that build is a violation.
Everything below the application, including diagram rendering and PDF export, works locally and never contacts a server.

=== The one `lsp-types` exception

The editor widget in gpui-component offers definition, hover and completion only through provider traits typed with `lsp-types`.
Rewriting those widgets would cost far more than a translation module, so `adocfoundry` is permitted to depend on `lsp-types`.
The exception is listed in `LSP_ALLOWED` in `xtask/src/layers.rs`.
Only `crates/adocfoundry/src/editor/providers.rs` uses those types, translating engine results into them.
`lsp-server` stays confined to `adoc-ls`.

== Design rules to preserve

. The engine is the only owner of document text and semantics.
. All mutations are commands with stable ids and undo groups, with no exceptions for small edits.
. Language behaviour lives in `adoc-lang`; `adoc-ls` and the engine are thin over it.
. Byte offsets are used below the front ends, and `LineIndex` converts at the edge.
. UI framework imports stay in `crates/adocfoundry`, so a different UI toolkit would be a one-crate swap.
. tree-sitter is for syntax only: highlighting, folding, outline hints and injections. Attribute evaluation, include expansion, Antora coordinates and cross-file references never use it.
. Dependencies are pinned exactly and pass `cargo deny` (permitted licences are MIT, Apache-2.0, BSD, MPL-2.0, Unlicense and OFL for fonts).
. No Node.js, JVM or Ruby is required at run time. External tools are optional and discovered.

See also xref:engine.adoc[the engine] and xref:desktop-app.adoc[the desktop app].
