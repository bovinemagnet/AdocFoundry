= The engine
Paul Snow
:revnumber: 0.0.0
:description: How adoc-engine owns documents, runs commands, records undo, publishes events and indexes in the background.

`adoc-engine` is the only entry point that front ends use.
The desktop app, the command-line checker and any future integration invoke commands on an `Engine`; none of them reach into engine internals.

== Threading model

The engine is single-threaded by design.
One `Engine` is owned by the front end and mutated through `&mut self` on the thread that owns it.
Long work, such as the initial indexing of a workspace, runs on a `std::thread` worker.
The worker sends its result back over a channel, and the front end applies it by calling `Engine::pump()`.
This keeps the engine testable without an async runtime.

== Documents

An open document (`OpenDocument`) holds:

* its `DocumentId` and path, which need not exist on disk for an untitled document;
* the text, as a `ropey::Rope` indexed by bytes;
* a version counter and a dirty flag;
* the parsed `Document` and its diagnostics.

The rope in the engine is the truth.
Front ends mirror it, they do not own it.

A text mutation is a list of `TextEdit` values, each a byte range in the pre-edit text and a replacement.
Applying edits updates the rope, bumps the version, re-parses with `adoc-parser`, replaces the index entry and recomputes diagnostics for the open documents.
It then publishes `DocumentChanged` and `DiagnosticsUpdated`.

Re-parsing is synchronous on every edit, so the text and outline are always exact.
A typed character is the one exception for the rest: re-indexing the document and refreshing diagnostics wait until typing pauses for `INDEX_SETTLE` (150 ms), when `pump` applies them.
On a 5,000-line document that work takes several milliseconds, too long to repeat on every keystroke.
Every other command brings the index up to date before it runs, so search, rename, save and replace never see a stale index.

== Commands

A `Command` has a `CommandSpec` and a `run` function.

* `id` is a stable `CommandId` such as `document.save`.
* `title` is the English title shown in the palette.
* `category` is Document, Edit, Navigate, Workspace or View.
* `default_binding` is a `cmd-s` style string that the front end maps to its platform.
* `when` is the context in which the command applies: `Always` or `ActiveDocument`.

Commands are registered once in a `CommandRegistry`, and registering a duplicate id is an error.
They are invoked with `Engine::invoke(id, args)`, where `CommandArgs` carries a document, an offset, a text edit, a path or a request.
They return a `CommandOutcome`, such as `Done`, `Opened`, `Location`, `External`, `Url`, `Preview`, `Committed` or `CommitDraft`.
`Url(String)` carries an address for the front end to open (`cx.open_url`) or copy, so the engine needs no browser-opening crate.

== Undo groups and typing coalescing

Each document has an undo stack of entries holding an undo group, the forward and inverse edits and the versions before and after.

* A single-character `edit.insert_text` is recorded in typing mode.
Consecutive typing within 500 ms coalesces into one entry, so a burst of typing undoes as one step.
* Any other insert, and every `edit.replace_range`, gets its own group.
* Multi-file operations share one group across documents.
`edit.undo` on any document in the group undoes the whole group, including file moves, and reports which documents changed.

The engine takes an injectable clock so that coalescing is tested without sleeping.

== The preview service

The engine renders the previews that front ends ask for.
It never draws anything: it publishes a framework-free view tree, and each front end paints it.

[cols="2,4"]
|===
|Item |Purpose

|`request_preview(id)` and `release_preview(id)`
|Ask for a document to be rendered and kept up to date, and release it again.

|`rendered_preview(id)`
|The latest published `RenderedPreview` (document, version, path and `ViewTree`). It is named so because `Engine::preview(PreviewId)` already returns Phase 1's multi-file edit previews.

|`PreviewLayout`
|Whether the preview is `visible`, `detached`, has `scroll_sync` and is `pinned` to a document. The `view.*` and `preview.*` commands change it.

|`preview_target()`
|The document the preview shows: the pinned document, or else the active one, while the preview is visible. The engine requests and releases that target itself, so following the active page and pinning are engine state, testable headlessly, and the docked and detached views render the same target.

|`PREVIEW_SETTLE`
|100 ms. A render starts this long after the last edit to the document or to any file it includes.

|`render_blocking(id, timeout)`
|Renders a document once and waits for its diagrams. The command-line `render` uses it because it has no event loop to pump.

|`set_document_parser(parser)`
|Chooses the `DocumentParser`. `acdc` is the default.

The parse runs on a worker thread against a snapshot of the open buffers, so unsaved edits show.
The worker reports back over the same channel as indexing, and `pump()` applies it.
A result is dropped when a newer job has started for the document, or when the document or a file it includes changed after the job started.
An edit during a render therefore never flashes the old text; the replacement job follows after the settle time.

The view is built from the cached parse on the engine thread by `adoc_render::build_view`, with an engine resolver that answers xrefs, includes and images through the Antora catalog and the index.
Each diagram block the view needs becomes a job on its own worker.
When one finishes, the preview is built again from the cached parse and republished, so a slow diagram never delays the page.
Diagrams are cached on disk by checksum under the first workspace root, in `.cache/adocfoundry/diagrams/`.

STEM goes through the same path.
The engine registers a `StemProvider`, a `DiagramProvider` for the kinds `stem-asciimath` and `stem-latex`, with its diagram cache.
Formulas render to SVG on a worker with `adoc_pdf::render_math_svg` at 15 pt (block) and 13 pt (inline), and are cached by checksum like diagrams.
The view tree's `ViewKind::Stem` carries a `DiagramView` (pending, an SVG path or failed), and `ViewInline::Stem` carries an optional SVG path.
The export's view tree asks for no formula images, because the PDF typesets them itself.

[[the-export-service]]
== The export service

The engine exports a page, or a component version in navigation order, to PDF.
`export.pdf_page` and `export.pdf_component` take `CommandArgs::Export(ExportArgs)`, with an `ExportTarget`, the output path, an optional theme, the standards, a fonts directory and an optional path for the generated Typst.

The pages are parsed on a worker from their open buffers or files, their views are built on the engine thread, and their diagrams are rendered.
Once no diagram is pending, a worker typesets with `adoc-pdf`, writes the file and reports.
The result arrives as `EngineEvent::ExportFinished`, with an `ExportSummary` (the page count and diagnostics) or the error.

`Engine::export_blocking(args, timeout)` runs the same job and waits, for the command-line `pdf`, and `Engine::is_exporting()` is true while a job is in flight.
The settings' `[pdf]` table supplies the default theme, the themes and fonts directories, the site address and the standards.
See xref:pdf.adoc[PDF export] for the flow and the crate.

Showing the source again drops it.

=== Keeping the model current

The text is the truth, so the model is rebuilt from a parse whenever it could differ from it.

* A typed source edit marks the model stale and schedules a rebuild after `MODEL_SETTLE`.
`pump` performs it.
* Any other command rebuilds a stale model before it returns, so undo, replace, rename, a reload from disk and an edit to an included file are never seen through an old model.
* A visual command checks the version first.
A command whose `VisualArgs::version` is older than the document's is refused, because its selection may point at different text.
A model that is merely stale is rebuilt first.
* A step that changes no structure (typing, deleting and mark changes inside a text block) is *local*.
The model is updated in place by rescanning that block, so typing stays immediate on long pages, and the model is reconciled with a fresh parse once edits pause for `MODEL_SETTLE`.
* Any other step is *structural*.
The model is rebuilt from a fresh parse before the command returns, so structure is always exactly what the parser sees.
* While a visual command edits a document, the change does not mark that document's own model stale.

When a diagram finishes rendering, the models whose views were waiting for it rebuild their view tree and publish `ModelChanged` again.

=== Visual commands

A visual command takes `CommandArgs::Visual(VisualArgs)`: the document, the version the selection is in, the selection as source offsets, the `MarkSet` that typed text carries, and a `VisualValue` (text, a link, a block type, a new block, an admonition kind, a table size, or an image).
It returns `CommandOutcome::Selection`, the selection to use afterwards.

The command asks the model for the step's result, which is source edits in pre-step coordinates, the selection after, and the updated model for a local step.
The edits are applied to the document as one edit, recorded in undo history, and `DocumentChanged` and `ModelChanged` are published.
A step that cannot be expressed without changing the meaning of other text is reported as `EngineError::Refused` with the step's message and changes nothing.
A join that is not possible, such as Backspace at the start of a paragraph after a heading, does nothing rather than report an error.

=== One undo history

A visual edit is a source edit, so there is no second history.
A run of visual typing coalesces like source typing, and every other visual command is its own undo group.
Undo and redo apply to the document whichever editor invoked them, and the model is rebuilt before they return.
The inverse of a step is the source edits that restore the text before it.

== The pump and worker indexing

`open_workspace` starts indexing on a worker thread and starts watching the roots.
The worker returns a finished `WorkspaceState`, which is applied by `pump()`.
Open documents are newer than the files the worker read, so they are kept.
If a newer workspace has replaced the one a worker indexed, its result is discarded.

`pump()` applies worker results and debounced file-system changes and returns the number of events applied.
`has_pending()` tells a front end whether it should keep pumping, and `wait_for_workers(timeout)` blocks until workers finish, which the command-line checker uses.

== The file watcher

A `notify` watcher, with a 250 ms debounce, feeds the pump.

* A created, modified or removed AsciiDoc file is re-indexed.
* A document with unsaved edits is never overwritten; the engine emits `DocumentChangedOnDisk` instead.
* A modified `antora.yml` reloads that component version, and diagnostics are re-run for affected files.
* A directory created or removed under a module re-indexes the root.

[[git]]
== Git

`Engine::git()` returns a `GitState`, built on the `adoc-git` crate.
It holds one `GitRepository` (`workdir`, `git_dir`, `head`, `ahead` and the `roots` it serves) per repository, however many workspace roots lie inside it.
`repositories()`, `repository_for(path)`, `head_for(root)`, `status_for(path)`, `statuses()` and `hunks_for(DocumentId)` read it.

`open_workspace` discovers each root's repository and reads its status on a worker thread, and the result arrives through `pump()` as indexing does.
A workspace outside any repository, or with `git.enabled` turned off, has no repositories and publishes no Git events.

The hunks of an open document are its changes against HEAD, computed from the buffer text and not from the file on disk.
They are recomputed `GIT_SETTLE` (150 ms) after typing pauses, at once on open, save and any other edit, and after every status refresh.
Untracked and ignored files have no hunks.

The file watcher also watches each repository's `.git/HEAD`, `index`, `packed-refs` and `refs/`, which are otherwise ignored along with `.git`.
A commit, a branch switch or staging therefore refreshes the status and the head.
A change to any file in the working tree refreshes the status as well, after the watcher's 250 ms debounce.

`git.refresh` (Refresh Git Status, Workspace category, no default binding) runs discovery again.

`Engine::hunks_now(id)` computes a document's changes on the engine thread from its current text.
Revert and navigation use it, so they never act on hunks a few keystrokes old.
`Engine::head_text(id, &hunk)` gives the lines a hunk replaced.

Four commands act on the hunks:

* `git.revert_hunk` (Revert Change, Edit category, no default binding) replaces the change at the source caret with its `HEAD` lines as one undo step.
It reports "there is no change here" when the caret is in no change.
* `git.next_change` (Go to Next Change, Alt-Down) and `git.previous_change` (Go to Previous Change, Alt-Up) move the caret to the next or previous change, wrapping round at the ends.
They report "there are no changes" when there are none.
* `git.show_changes` (Show Changes, View category) switches the sidebar to the Changes panel.

`GitRepository::ahead` is an `Option<usize>`: the commits on the current branch that the remote named by `git.remote` does not have, or `None` when the branch has no remote-tracking branch.
It is refreshed with the status.

=== Staging, committing and pushing

`src/commit.rs` holds the commands, which are all in the palette with no default binding.
`Engine::changed_writer_files` gives the files the Changes panel lists, and `git.stage_all_adoc` stages the same list.

[cols="2,3"]
|===
|Command |Purpose

|`git.stage` (Stage), `git.unstage` (Unstage)
|Take `CommandArgs::Path` or `CommandArgs::Custom` with a `"paths"` array. From the palette they act on the active file.

|`git.stage_all_adoc` (Stage All Changes)
|Stages every file in `changed_writer_files`.

|`git.commit` (Commit)
|Takes `CommandArgs::Custom` with a `"message"` and optional `"paths"`. With paths, open documents among them that have unsaved edits are saved first and the paths are staged. It returns `CommandOutcome::Committed { commit, saved }`. From the palette, with no arguments, it opens the dialog.

|`git.push` (Push)
|Pushes the current branch to `[git] remote`. The push runs on a worker thread and publishes `EngineEvent::GitPushed { message }`.

|`git.save_and_commit` (Save and Commit, Document category)
|Saves the active page, stages it and returns `CommandOutcome::CommitDraft { message, paths }` for the front end to open the dialog with.
|===

Staging, unstaging and committing go through `adoc-git` and `gix` in process.
`Repository::stage`, `unstage` and `commit` change the index and `HEAD`, and `identity` and `signs_commits` read the configuration.
`unpushed(remote, branch)` counts the commits ahead of the remote-tracking branch, `has_upstream(branch)` says whether the branch has one, and `head_commit_id` gives the new commit.
`GitError::NoIdentity` and `GitError::NothingToCommit` are the two refusals.
`discover_isolated` opens a repository reading only its own configuration, so that a test can show the no-identity refusal whatever the developer's global identity is.

A commit made with `commit.gpgsign` set, and every push, runs the `git` executable from `[tools] git`, else `git` on `PATH`.
A push without one fails with "pushing needs the git executable: install Git or set [tools] git".
A branch with no upstream is refused before anything is run.

=== Blame and remote links

`Repository::blame(path, current)` and `Repository::head_blame(path)` use gix's blame (the `blame` feature) from the HEAD commit.
`blame_through(head_blame, hunks, lines)` carries the HEAD blame over to the current text.
A `BlameLine` is `{ line, commit: Option<short id>, author, time (Unix seconds), summary }`, and a line with no commit is not committed.

`Engine::request_blame(id)` computes the HEAD blame lazily on a worker and publishes `EngineEvent::GitBlameChanged(id)` when it is ready.
`Engine::blame_for(id)` returns the blame overlaid with the document's current hunks.
The blame is forgotten on save, on a status refresh and on rediscovery.

`git.show_blame` (Toggle Blame, View category, no default binding) shows or hides the column in the front end.
`Engine::remote_link(id, offset)` builds the address of the line at an offset.
It uses `Repository::is_pushed(remote, branch)` and `remote_link_for_line(remote_url, head, path, line, hosts)`, where `HostKind` is `GitHub`, `GitLab`, `Bitbucket` or `Azure` and `hosts` comes from `[git.hosts]`.
`navigate.open_on_remote` (Open on Remote) and `navigate.copy_remote_link` (Copy Remote Link) are Navigate commands with no default binding.
Both return `CommandOutcome::Url`, or an error when there is no such remote, the branch is not pushed or the host is not recognised.

[[versions-table]]
=== Versions per branch

`Engine::version_badge(path)` gives the component version and branch for a path, as shown in the status bar and the Navigation panel.
`Engine::other_versions(id)` lists the other versions of the document's component that have the same page in the workspace, in Antora's order.

The engine builds the table of which branch publishes which version on a worker (`src/versions.rs`).
It reads the playbook's sources through `adoc-antora` (`ContentSource`), lists the repository's branches with `Repository::branches()`, and reads each taken branch's `antora.yml` with `Repository::file_at(branch, path)`.
The result is a `PublishedVersions` table, set on the catalog as `BranchVersions { current, published }` with `AntoraCatalog::set_branch_versions`.
`adoc-lang` reads it to report `adoc.antora.version-not-on-branch`.

The table is built after Git discovery, after each index and after a branch switch.
A change to `.git/HEAD` indexes the workspace again, so descriptors and pages are reloaded, and diagnostics are refreshed.

`navigate.open_in_version` (Open in Another Version, Navigate category, no default binding) takes `CommandArgs::Custom` with `{ "document": <id>, "version": "1.0" | null }`.
It opens the same resource id in the chosen version, in the workspace root that holds it.

== Settings

`Settings` loads the user and workspace TOML layers described in xref:ROOT:settings.adoc[Settings].
The UI never reads the settings file itself.

== Search, replace and rename previews

Multi-file changes are computed first as an `EditPreview`: a list of file moves and per-file edits.
Nothing is changed until `workspace.apply_preview` is invoked with the preview's id.

Applying a preview creates one undo group that spans every document it touches, including file moves.
One undo therefore restores every xref and moves a renamed page back.

`workspace.search` returns immediately and delivers matches as `SearchResults` events.
`workspace.replace` and `page.rename` return a `Preview` outcome.
Rename finds every xref that resolves to the page using the index and the resolver.

== Language features

The engine delegates definition, hover, completion and diagnostics to `adoc-lang`.
That is why the editor, the command-line checker and the language server give identical answers.

== Navigation history

Back and forward history is engine state, so every front end and the command-line tests share it.
`navigate.follow_link` opens and activates the target and records the position that was left.
