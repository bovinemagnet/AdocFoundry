= The engine
Paul Snow
:revnumber: 0.0.0
:description: How adoc-engine owns documents, runs commands, records undo, publishes events and indexes in the background.

`adoc-engine` is the only entry point that front ends use.
The desktop app, the command-line checker and any future integration invoke commands on an `Engine`; none of them reach into engine internals.

== Threading model

The engine is single-threaded by design.
One `Engine` is owned by the front end and mutated through `&mut self` on the thread that owns it.
Long work, such as the initial indexing of a workspace, runs on a `std::thread` worker.
The worker sends its result back over a channel, and the front end applies it by calling `Engine::pump()`.
This keeps the engine testable without an async runtime.

== Documents

An open document (`OpenDocument`) holds:

* its `DocumentId` and path, which need not exist on disk for an untitled document;
* the text, as a `ropey::Rope` indexed by bytes;
* a version counter and a dirty flag;
* the parsed `Document` and its diagnostics.
* `asciidoc`, which is false for a file that is not AsciiDoc.
Such a document is never put in the index or diagnosed, the rendered preview skips it, and `view.show_visual` and `view.show_split` refuse it.
`Engine::read_text` refuses a file that is binary or not UTF-8 for every open, browse and reload.

The rope in the engine is the truth.
Front ends mirror it, they do not own it.

A text mutation is a list of `TextEdit` values, each a byte range in the pre-edit text and a replacement.
Applying edits updates the rope, bumps the version and drops the document's semantic parse, then replaces the index entry and recomputes diagnostics for the open documents.
It then publishes `DocumentChanged` and `DiagnosticsUpdated`.

The parse is lazy.
`OpenDocument::parsed()` holds it in a `OnceCell`, and the first read after an edit runs `adoc-parser` on the text again, so the outline is always exact when it is read.
A typed character therefore parses nothing: the index parses it once when typing pauses, or a language feature does when it asks.
Edits that are indexed at once parse at once.
Whether a page is unsaved is decided without hashing it: `DocumentState` keeps `saved_len` beside `saved_hash` (`mark_saved`, `is_saved`), text of another length is unsaved, and only text of the saved length is hashed.
Re-indexing the document and refreshing diagnostics are different for the typing commands: `edit.insert_text`, `edit.replace_range`, `visual.insert_text`, `visual.delete_backward` and `visual.delete_forward` (`TYPING_COMMANDS` in `engine.rs`).
A small edit made by one of them, one replacement of at most four bytes by at most one character (`is_small`), waits until typing pauses for `INDEX_SETTLE` (150 ms), when `pump` applies it.
Larger edits, such as a paste, and edits made by any other command (Rename, Replace, undo, a reload) are indexed at once.
On a 5,000-line document that work takes several milliseconds, too long to repeat on every keystroke.
The typing commands do not flush what earlier typing left pending.
Any other command indexes what is pending before it runs, so search, rename, save and replace never see a stale index.

When a document is indexed, only the open documents its change can affect are re-diagnosed.
`Engine::refresh_diagnosed_with` re-diagnoses the open documents in `adoc_lang::diagnosed_with(ws, path)`, taken before and after the change.
That set is the file itself, the files whose xrefs name its file name (`WorkspaceIndex::xrefs_naming`), the files whose includes name it (`includes_naming`), those including them in turn up to the include depth, and the files it composes (`includes::composed_files`).
Name matches stand in for resolution, so the set is generous but never misses a file.
Workspace-level changes (indexing, a descriptor, files changed on disk) still re-diagnose every open document.

On a 5,000-line page in a 500-page workspace with 20 tabs open (release build), Backspace fell from a median of 3.8 ms to 0.7 ms per key and visual typing from 4.6 ms to 1.5 ms.
The ignored probes `backspace_loop` and `visual_typing_loop` in `tests/perf.rs` measure this.

== Auto-save

`auto_save.rs` holds the optional auto-save (`[editor] auto_save`).
`AutoSave` is `Off`, `OnFocusChange` or `AfterDelay`, and lives in `EditorSettings::auto_save`; any other value is a settings warning and leaves it `Off`.

* Each edit records its time on the engine's clock, so tests use `ManualClock`.
`pump` saves the pages left unedited for `AUTO_SAVE_DELAY` (1 s) when the setting is `AfterDelay`, and `has_pending` stays true meanwhile.
* `Engine::set_active` and `set_active_image` save the page left when the setting is `OnFocusChange`.
* `Engine::focus_lost()` saves every edited page with `OnFocusChange` and does nothing otherwise.
* `start_save` snapshots the page's text, a rope clone that costs O(1), and returns at once.
The write runs on the <<writer>>, as `document.save` writes it but without waiting.
When it is done, `pump` applies the result: the page is clean against what was written, unless it was edited after the snapshot, and then it stays dirty.
`DocumentSaved` is emitted.
* A failure is the `CommandFailed` event for `document.save`, and the page is left alone until it is saved by hand.
* A save of a page that is already being written waits for the next pause in its edits.
Untitled documents and documents without unsaved edits are skipped.
* A page whose save is refused, such as by the changed-on-disk check, is remembered and not auto-saved again until a successful save, overwrite or reload.

[#writer]
== The writer

`writer.rs` holds the engine's writer.
It is one background thread, started on first use, that writes files in the order they were asked for.
No write, and none of its `fsync`, runs on the thread that serves the front end, and a later write never lands before an earlier one.
Each job counts in `has_pending` until `pump` applies its result, and `wait_for_workers` waits for it too.

Its jobs are:

* page saves: the changed-on-disk check, the temporary file and rename, and the local-history versions;
* recovery records, and their removal;
* the sidebar state file (`sidebar-state.json`), which is read, merged and written on the writer;
* the recent folders file (`recent-folders.json`).

Opening a workspace waits for pending writes before it reads the sidebar state file.

The session file is not one of the writer's jobs.
`write_session` still writes it directly, and only when the app quits or the window closes.

[#crash-recovery]
== Crash recovery

`recovery.rs` keeps the text of pages with unsaved edits so that a crash does not lose it.
Like word counts, it is opt-in: a front end calls `Engine::enable_recovery()`, as the app does in `AppState::new`, while `adoc-ls`, `adoc-mcp` and the CLI never write records.
Without a state folder (`Settings::state_dir()`) nothing is written.
Only the app's `main.rs` sets one, with `.with_state_dir(Settings::default_state_dir())`, so tests, `adoc-ls`, `adoc-mcp` and the CLI never write there.
`default_state_dir()` returns `dirs::state_dir()`, else `dirs::data_local_dir()`, joined with `adocfoundry`; `with_state_dir(Option<PathBuf>)` sets it and it is kept across `reload`.

* Records are JSON files in `RECOVERY_DIR` (`recovery`) in the state folder, named `<session>-<document id>.json`.
* A session is named `<pid>-<milliseconds>.<n>` and holds an exclusive lock (`File::try_lock`) on `<session>.lock` from its first record until the engine is dropped.
* An edit that leaves the page dirty schedules a record, and `pump` writes it `RECOVERY_SETTLE` (2 s) later (`write_due_recovery`); `has_pending` stays true meanwhile.
An edit that leaves the page clean removes the record, as do save, `mark_saved` (reload), close and undo to the saved text.
* A record's text is copied and serialised on the <<writer>>.
Removing a record is queued after the write that made it.
* `Engine::write_recovery_now()` writes the waiting records and then waits for every write the engine has started, saves included; the app calls it from `cx.on_app_quit`.
Dropping the engine also waits for every write.
* `Engine::recoverable()` lists the records of other sessions whose lock can be taken, newest first, as `Recoverable` values.
A running session's records, and the engine's own, are never listed.
* `Engine::recovery_diff(&Recoverable)` diffs the file on disk, which is empty for an untitled or deleted page, against the record, using <<line-diff>>.

The commands are `document.recover_unsaved` (Recover Unsaved Changes…, context `Always`, returning `CommandOutcome::Recoverable(Vec<Recoverable>)`), `document.recover` and `document.discard_recovery`.
The last two take `CommandArgs::Path(record)`; `recover` returns `CommandOutcome::Opened(id)` with the text applied as one undo group, and `discard_recovery` returns `Done`.
Both accept only a record that `recoverable()` currently lists, so they never touch a file outside the store.
Discarding the last record of a session also removes its lock file.

[#local-history]
== Local history

`local_history.rs` keeps the saved versions of each page.
A front end calls `Engine::enable_local_history()`, as the app does in `AppState::new`; without it, or without a state folder, nothing is kept.

* Each page has a folder in `HISTORY_DIR` (`history`) in the state folder, named from a SHA-256 digest of the page's path.
It holds a `path` file naming the page and one file per version, named `<milliseconds>-<first 16 hex digits of the text's SHA-256>`.
Each name is strictly later than the one before.
* A save keeps its versions in two steps.
The engine thread decides where the versions go and whether the save sweeps the store (`history_job`, which also tracks `HISTORY_SWEEP_INTERVAL`).
The <<writer>> keeps the versions and prunes (`HistoryJob::record`).
A save keeps the previous text when the history does not hold it yet, then the saved text.
Saving text the history already holds as its latest version keeps nothing, and text over `HISTORY_MAX_PAGE` (4 MiB) is not kept.
* `Engine::local_history(path)` returns `Vec<SavedVersion>`, each with `id`, `saved` and `size`, newest first.
`saved_version(path, id)` reads only a version the history lists.
`version_diff(document, version)` diffs the version against the open text using <<line-diff>>.
* Pruning follows `HistorySettings { enabled, keep_days, max_versions }` in `Settings::history`, a user-file-only `[history]` table.
A page's own folder is pruned when it is saved (`keep_days`, `max_versions`).
At the first save of a session, and then at most once every `HISTORY_SWEEP_INTERVAL` (1 hour), a save also prunes every page's folder and then removes the oldest versions across all pages until the total is under `max_size_mb` (`history.max_size_mb`).
* `move_file` in `search.rs` calls `move_history(from, to)`, so a renamed page's history moves with it, joined with any history the new path had, and `recovery_changed(id)`, so its recovery record is rewritten under the new path.
Renames made by other programs start a new history.

The commands are `document.local_history` (Local History…, context `ActiveDocument`), which takes `CommandArgs::Document(id)` or uses the active page and returns `CommandOutcome::LocalHistory { document, versions }`, and `document.restore_version` (Restore Saved Version), which takes `CommandArgs::Custom({"document": id, "version": id})`, applies the text as one undo group and returns `Done`.

[#line-diff]
== The line diff

`line_diff.rs` turns two texts into the lines a dialog shows.
`line_diff(old, new) -> Vec<DiffLine>` returns `DiffLine::Same`, `Removed`, `Added` or `Skipped(n)`, keeping `DIFF_CONTEXT` (3) unchanged lines around each change and counting the rest as `Skipped`.
It is built on the `similar` crate (2.7.0, already in the tree through `insta`), a direct dependency of the engine with only its `text` feature.

== Directory listings

`files.rs` is framework-free and serves the Files view.
`Engine::request_directory`, `refresh_directory` and `refresh_directories` list a folder one level deep on a worker, which answers with `WorkerMessage::DirectoryListed`.
`Engine::directory(dir)` gives a `Listing`: `Loading`, `Loaded(Vec<DirectoryEntry>)` or `Failed(DirectoryError::PermissionDenied | DirectoryError::Unavailable)`.
Each `DirectoryEntry` has a `name`, a `path`, a `kind` (`EntryKind::Directory`, `File` or `Link { to_directory }`) and `excluded`.
Entries are sorted folders first, then by natural, case-insensitive name, with the exact path breaking ties.
`directory_with_excluded` includes the excluded entries, and `set_show_excluded` toggles them, emitting `EngineEvent::DirectoryListed(dir)` for every listed folder.
A request outside the roots, or through a link, is refused with `EngineError::Refused`.
Results answer a request id, so an answer to an older request, or for a workspace since closed (`open_workspace` clears the listings), is dropped.
The watcher's debounced changes relist the listed folders that hold them (`directories_changed`).

[[quick-open]]
== Quick Open

`quick_open.rs` holds the ranking behind `workspace.quick_open` (Quick Open…), so it is tested headlessly and the front ends only display the result.
`Engine::quick_open(query, limit)` returns `Vec<QuickOpenItem>`, each with `path`, `relative_path`, `title` and `resource_id`.
It reads the index, never the disk, so it lists AsciiDoc files only.
The command takes `CommandArgs::Query { query, document }` (it ignores `document`) and returns `CommandOutcome::QuickOpen(Vec<QuickOpenItem>)`, with at most `QUICK_OPEN_LIMIT` (100) items.

Each space-separated word of the query must match the file name, title, resource ID or path as an in-order, case-insensitive subsequence.
File name matches score highest, then the title, with bonuses for word starts and runs.
Recently active files come first, most recent first, then the rest by score; an empty query gives recent files, then every file by path.
Recency is recorded whenever a document becomes the active tab (`Engine::set_active`, and `activate_last_tab` when a closed tab hands over), and is kept for the session only.
The items are kept in a `QuickOpenCache` on the engine, built from the index, the catalog and the roots.
The index worker builds it alongside each full index, so the first query after indexing makes no items.
`WorkspaceIndex::revision` and `AntoraCatalog::revision` count changes to the files and to the resources, so a query can tell whether the cache is still current.
When only files changed, the cache is walked beside the index in path order: unchanged items are kept, a changed title is replaced, and an item is made only for a file added since.
When the catalog or the roots changed, it is rebuilt.
A query scores every item without allocating (`fuzzy_score` reads the candidate's characters in place, lowering each one as it goes), then keeps only the best `limit` (`select_nth_unstable_by`), and clones only those items.
The `QuickOpenItem` probe counts items made, so a test can check that a keystroke makes none.
The `quick_open_in_a_workspace_of_20000_pages` probe in `tests/perf.rs` (one Antora component of 20,000 pages) measures under 5 ms a query in a release build, and about 4 ms for the first query after an edit.

[[sessions]]
== Sessions and recent folders

`session.rs` restores the last session and remembers recent folders.
Like recovery, it is opt-in: `Engine::enable_sessions()` turns it on, and only the app calls it, in `AppState::new`.
Without it, or without a state folder, nothing is read or written.

* `Engine::write_session(&carets)` writes `SESSION_FILE` (`session.json`): the roots, the tabs in tab order (path, editor mode, caret byte offset and whether it is the preview tab), the active tab and the pinned page by their place in the tab list, and the preview layout.
The engine does not know where carets are, so the front end passes a map from `DocumentId` to caret offset: the visual editor's caret in visual mode, otherwise the source editor's.
Untitled documents are left out.
* `Engine::restore_session()` reads the file and opens the roots that are still directories as the workspace.
It reopens each tab whose file still exists through `open_item`, with `OpenDisposition::Preview` for the tab that was the preview tab and `Persistent` for the rest, sets editor modes (AsciiDoc pages only) without building their visual models (`set_editor_mode_later`), and activates the saved active tab.
The active page's model is built the next time the engine is pumped, and every other page's when it is made active (`set_active`), so a restore builds none.
The open pages' diagnostics are refreshed once, after the last tab is open, not as each page opens.
It restores the preview layout, the PDF preview only when built with the `typst` feature.
It returns a map from each reopened page's new `DocumentId` to its caret, clamped inside the text and to a character boundary, for the front end to place.
A missing, damaged or other-version file restores nothing.
* `open_workspace` records the roots, when sessions are enabled, in `RECENT_FOLDERS_FILE` (`recent-folders.json`): at most `RECENT_FOLDERS` (10), most recent first.
`Engine::recent_folders()` returns those still present.
* `workspace.open_recent` returns them as `CommandOutcome::RecentFolders(Vec<PathBuf>)`; the front end shows the picker and opens the chosen folder with `workspace.open_folder`.

Both files carry a format version, and are written through the engine's write-replacing helper (a temporary file renamed over the old one).

[[images]]
== Images and tabs

`images.rs` holds the engine's side of the image viewer, and the engine never reads an image file.
An `ImageId` names an `OpenImage { id, path, revision }`.
`is_image_path` is true for the case-insensitive extensions in `IMAGE_EXTENSIONS`: `png`, `jpg`, `jpeg`, `gif`, `webp`, `bmp`, `ico`, `tif`, `tiff`, `svg`, `avif`, `heic` and `heif`.

* `open_image_as(path, disposition)` opens an image as a preview or a persistent tab.
It refuses a path that is not a file before anything changes.
* `close_image` closes it.
* `reload_image` bumps the `revision` and emits `ImageChanged`; the `image.reload` command calls it.
* `images_changed` is called from the file watcher with the paths that changed.
* `active_image` and `set_active_image` read and set the active image.

`tabs.rs` holds the tab order and the preview tab as `TabItem`, which is `Document(DocumentId)` or `Image(ImageId)`.
`open_item(path, disposition)` is the one decision about how to open a resource: an image goes to `open_image_as`, anything else to `open_as`.
`document.open`, `document.browse` and navigation all use it.
`activate(item)`, `active_item()`, `close_item`, `keep_open(item)`, `closed_by(command, item)` (which returns the `TabItem`s a close command closes) and `closed_by_any` work on either kind.

While an image is active, `Engine::active()` is `None`, so document commands are unavailable and cannot act on the page that was active before.
Following an image link opens it as a preview and is recorded in back history, and going back or forward to an image reopens it.
Images are never indexed, diagnosed or previewed.

== Commands

A `Command` has a `CommandSpec` and a `run` function.

* `id` is a stable `CommandId` such as `document.save`.
* `title` is the English title shown in the palette.
* `category` is Document, Edit, Navigate, Workspace or View.
* `default_binding` is a `cmd-s` style string that the front end maps to its platform.
* `when` is the context in which the command applies: `Always`, `ActiveDocument`, `ActiveTab` (the close and keep-open commands, which act on a page or an image) or `ActiveImage`.

Commands are registered once in a `CommandRegistry`, and registering a duplicate id is an error.
They are invoked with `Engine::invoke(id, args)`, where `CommandArgs` carries a document, an offset, a text edit, a path or a request.
They return a `CommandOutcome`, such as `Done`, `Opened`, `Location`, `Peek`, `External`, `Url`, `Preview`, `Committed` or `CommitDraft`.
`OpenedImage(ImageId)` reports an image opened instead of a document, and `CommandOutcome::opened(item)` builds either from a `TabItem`.
`Url(String)` carries an address for the front end to open (`cx.open_url`) or copy, so the engine needs no browser-opening crate.

[#undo-groups]
== Undo groups and typing coalescing

Each document has an undo stack of entries holding an undo group, the forward and inverse edits and the versions before and after.

* A single-character `edit.insert_text` is recorded in typing mode.
Consecutive typing within 500 ms coalesces into one entry, so a burst of typing undoes as one step.
* Any other insert, and every `edit.replace_range`, gets its own group.
* Multi-file operations share one group across documents.
`edit.undo` on any document in the group undoes the whole group, including file moves, and reports which documents changed.

A group is undone or redone only as a whole, because taking back some documents would leave a moved page and the references to it disagreeing.
When `workspace.apply_preview` succeeds, the engine records the documents taking part in the group.
`Engine::check_group` is consulted by `edit.undo` and `edit.redo`, and by `Engine::undo` and `Engine::redo`, which return `false` when refused.
For every participating document still open, the group must be its latest undo entry (for undo) or its latest undone entry (for redo).
Otherwise the command fails with `EngineError::GroupBlocked { path, redo }`, naming the first such document, and nothing changes: no text and no file move.
Undoing the later edits on that page first lets the change undo as a whole from any of its pages.
An edit after the change was undone clears that page's redo history, so the change can no longer be redone from the other pages either.
A participating document closed since is passed over, as its history and its part of the change went with it; closing discards unsaved edits, so the file keeps what was last saved.

The engine takes an injectable clock so that coalescing is tested without sleeping.

== The preview service

The engine renders the previews that front ends ask for.
It never draws anything: it publishes a framework-free view tree, and each front end paints it.

[cols="2,4"]
|===
|Item |Purpose

|`request_preview(id)` and `release_preview(id)`
|Ask for a document to be rendered and kept up to date, and release it again.

|`rendered_preview(id)`

The parse runs on a worker thread against a snapshot of the open buffers, so unsaved edits show.
The worker reports back over the same channel as indexing, and `pump()` applies it.
A result is dropped when a newer job has started for the document, or when the document or a file it includes changed after the job started.
An edit during a render therefore never flashes the old text; the replacement job follows after the settle time.

The view is built from the cached parse on the engine thread by `adoc_render::build_view`, with an engine resolver that answers xrefs, includes and images through the Antora catalog and the index.
Each diagram block the view needs becomes a render request.
When one finishes, the preview is built again from the cached parse and republished, so a slow diagram never delays the page.
Requests are queued (`rendered.rs`): `spawn_diagram` queues a request, `start_queued_diagrams` starts up to `DIAGRAM_WORKERS` (4) at once, and each finished render starts the next.
Mermaid runs in process but uses the same pool, and the preview, the visual editor and PDF export share this path.
Superseded renders are not cancelled; results are cached by checksum, so a stale render that finishes only fills the cache.

Diagrams are cached on disk by checksum under the first workspace root, in `.cache/adocfoundry/diagrams/`.

STEM goes through the same path.
The engine registers a `StemProvider`, a `DiagramProvider` for the kinds `stem-asciimath` and `stem-latex`, with its diagram cache.
Formulas render to SVG on a worker with `adoc_pdf::render_math_svg` at 15 pt (block) and 13 pt (inline), and are cached by checksum like diagrams.
The view tree's `ViewKind::Stem` carries a `DiagramView` (pending, an SVG path or failed), and `ViewInline::Stem` carries an optional SVG path.
The export's view tree asks for no formula images, because the PDF typesets them itself.

== The export service

The engine exports a page, or a component version in navigation order, to PDF.
`export.pdf_page` and `export.pdf_component` take `CommandArgs::Export(ExportArgs)`, with an `ExportTarget`, the output path, an optional theme, the standards, a fonts directory and an optional path for the generated Typst.

The pages are parsed on a worker from their open buffers or files, their views are built on the engine thread, and their diagrams are rendered.
Once no diagram is pending, a worker typesets with `adoc-pdf`, writes the file and reports.
The result arrives as `EngineEvent::ExportFinished`, with an `ExportSummary` (the page count and diagnostics) or the error.

`export.html_page` takes the same `CommandArgs::Export` with an `ExportTarget::Page` and an output path (the PDF options are ignored), returns at once and reports with `EngineEvent::ExportFinished` (an `ExportSummary` with one page and no diagnostics).
It is implemented in `html_export.rs`: `Engine::render_now` starts the page's render, and the crate-private `finished_preview` tells when it is complete, diagrams included.
The HTML comes from `adoc_render::to_html`, and `adoc_render::embed_local_files` then replaces local `file://` image addresses with `data:` URIs.
Remote images, unreadable files and files that are not images keep their addresses.
It exports the open buffer, and needs no Typst.

`Engine::export_blocking(args, timeout)` runs the same job and waits, for the command-line `pdf`, and `Engine::is_exporting()` is true while a job is in flight.
The settings' `[pdf]` table supplies the default theme, the themes and fonts directories, the site address and the standards.
See xref:pdf.adoc[PDF export] for the flow and the crate.

== Word counts

The engine counts the words of the active page for the status bar.
Counting is opt-in: a front end calls `Engine::enable_word_count()`, as the app does in `AppState::new`, while the CLI, `adoc-ls` and `adoc-mcp` never count.

Only the active document is counted.
`WORD_COUNT_SETTLE` (500 ms) after the last change to the page, a worker parses a snapshot with `OwnedInput::parse`, the parse the preview uses, and counts the prose in the `adoc-dom` tree.
Switching to another tab, or opening a page, counts it straight away.
The count is in `crates/adoc-engine/src/words.rs`.

`Engine::word_count(id)` returns the last count as `Option<WordCount>`, which may lag the text until it settles.
`WordCount` holds `words` and `minutes`, the reading time at `WORDS_PER_MINUTE` (200) rounded up.
`adoc_engine::count_words(&str)` counts any text by the same rule, and the app uses it for the selection.
When a new count differs from the last, the engine publishes `EngineEvent::WordCountChanged(DocumentId)`.

=== Keeping the model current

The text is the truth, so the model is rebuilt from a parse whenever it could differ from it.

* A typed source edit marks the model stale and schedules a rebuild after `MODEL_SETTLE`.
When that time passes, `pump` rebuilds the model of the active page.
* After a command other than source typing, the active page's model is rebuilt before the command returns, but only if that command made a model stale.
So undo, replace, rename, a reload from disk and an edit to an included file are never seen through an old model on the page being shown.
* A read-only command (Quick Open, hover, About and so on) rebuilds nothing.
A model that only earlier source typing made stale keeps waiting for its `MODEL_SETTLE` rebuild.
* Only the model of the active page is rebuilt eagerly.
The model of a page in a background tab is left stale.
It is rebuilt when its page becomes active again, through `Engine::set_active` or the tab activated after a close.
* A visual command checks the version first.
A command whose `VisualArgs::version` is older than the document's is refused, because its selection may point at different text.
A model that is merely stale is rebuilt first.
* A step that changes no structure (typing, deleting and mark changes inside a text block) is *local*.
The model is updated in place by rescanning that block, so typing stays immediate on long pages, and the model is reconciled with a fresh parse once edits pause for `MODEL_SETTLE`.
* Any other step is *structural*.
The model is rebuilt from a fresh parse before the command returns, so structure is always exactly what the parser sees.
* While a visual command edits a document, the change does not mark that document's own model stale.

When a diagram finishes rendering, the models whose views were waiting for it rebuild their view tree and publish `ModelChanged` again.

=== One undo history

A visual edit is a source edit, so there is no second history.
A run of visual typing coalesces like source typing, and every other visual command is its own undo group.

== The pump and worker indexing

`open_workspace` starts indexing on a worker thread and creates the watcher, but places no watches itself, so it does no watching on the caller's thread.
The worker walks the roots with `index_roots_with(roots, ignore, on_directory)` in `adoc-index` and `adoc-lang`.
It calls `on_directory` before it reads each folder, and the engine uses that call to place the watch, so nothing read afterwards is missed.
The index, Antora discovery and the watcher all take the one `workspace.ignore` list.
Files are read and parsed on up to four threads.
A folder or file that cannot be read is left out of the index and recorded in `Indexed::unreadable`, and the rest of the workspace is indexed.
The engine reports the first unreadable path once, as `CommandFailed` for `workspace.reindex`, with a message such as "could not read <path> and N more; the rest of the workspace is indexed".
The worker returns a finished `WorkspaceState`, which is applied by `pump()`.
Open documents are newer than the files the worker read, so they are kept.
Each index job carries a generation, as preview rendering and Git discovery do, and a result or failure from a job that a newer one has superseded is discarded.
So a reindex of the same roots that finishes after a later one cannot replace the later index, and a newer workspace always wins over the one a worker was indexing.

== The file watcher

A `notify` watcher, with a 250 ms debounce, feeds the pump.
Its `WatchMode` is chosen per platform.

* `WatchMode::Roots` puts one recursive watch on each root.
FSEvents on macOS and `ReadDirectoryChangesW` on Windows keep that without walking the tree, and changes in ignored folders are filtered out.
* `WatchMode::Folders`, used on Linux, puts a non-recursive watch on each folder the index enters, because inotify watches one folder at a time.
Ignored folders such as `node_modules` and `.git` are never watched.
A new folder is watched when the re-index that its creation triggers enters it.

The `Watches` are shared, and the index worker locks them to add each watch.
In `Folders` mode `Indexed` also carries the folders `entered`.
When the engine applies a current-generation result, it unwatches every folder not in that set, such as one that was removed or is now ignored.
A result from a superseded job is discarded and changes no watches.
The watcher never follows symbolic links, as the index never did.
If a watch cannot be added, for example at Linux's `fs.inotify.max_user_watches` limit, the engine reports it once as `CommandFailed` for `workspace.open_folder` ("file watching is incomplete: …") and keeps working.


* A created, modified or removed AsciiDoc file is re-indexed.
* A document with unsaved edits is never overwritten; the engine emits `DocumentChangedOnDisk` instead.
* A modified `antora.yml` reloads that component version, and diagnostics are re-run for affected files.
* A directory created or removed under a module re-indexes the root.
A folder that is removed and then touched in the same debounce window still counts as a folder change.
* A changed file that is open as an image calls `images_changed`, which reloads it.

Saving checks the same thing.
The check and the write run on the <<writer>>.
`save` and `overwrite` first wait for any auto-save of that page already being written, then queue theirs and wait for it, so they still return their result.
While a save of a page is being written, the watcher ignores changes to that page's file, because the save's result settles them.
`Engine::save` returns `EngineError::SaveConflict { path }` when the file's contents differ from the hash of what the engine last read or wrote (`saved_hash`), and writes nothing.
`save_all` saves the other documents and reports the conflict, and `git.save_and_commit` stops at it.
`Engine::overwrite` and `Engine::reload` are the two explicit choices, behind the `document.overwrite` and `document.reload` commands: `overwrite` writes the buffer regardless, and `reload` replaces the buffer with the file as one undo step and leaves the document clean.
A file that no longer exists is written again by `save`.
Every write goes to a temporary file in the same directory and is renamed over the page, keeping the file's permissions; a symbolic link has its target written and the link kept.
The command-line tool and the MCP server return the conflict's message to their caller.

[[git]]
== Git

`Engine::git()` returns a `GitState`, built on the `adoc-git` crate.
It holds one `GitRepository` (`workdir`, `git_dir`, `head`, `commit`, `ahead` and the `roots` it serves) per repository, however many workspace roots lie inside it.
`commit` is the commit `HEAD` is at, or `None` before the first commit.
`repositories()`, `repository_for(path)`, `head_for(root)`, `status_for(path)`, `statuses()` and `hunks_for(DocumentId)` read it.

`open_workspace` discovers each root's repository and reads its status on a worker thread, and the result arrives through `pump()` as indexing does.
A workspace outside any repository, or with `git.enabled` turned off, has no repositories and publishes no Git events.

The hunks of an open document are its changes against HEAD, computed from the buffer text and not from the file on disk.
They are recomputed `GIT_SETTLE` (150 ms) after typing pauses, at once on open, save and any other edit, and after every status refresh.
The engine keeps each open document's text in `HEAD`, read once and kept until `HEAD`'s commit moves (a commit, a branch switch or rediscovery).
A recomputation therefore only diffs the buffer against that text, without opening the repository.
The documents due are computed in one job per working tree, on a worker.
A working tree still computing makes its documents wait for that job, so there is never more than one hunk job per repository.
Results from before `HEAD` moved are dropped.
Untracked and ignored files have no hunks.

The file watcher also watches each repository's `.git/HEAD`, `index`, `packed-refs` and `refs/`, which are otherwise ignored along with `.git`.
A commit, a branch switch or staging therefore refreshes the status and the head.
A change to any file in the working tree refreshes the status as well, after the watcher's 250 ms debounce.

`git.refresh` (Refresh Git Status, Workspace category, no default binding) runs discovery again.

`Engine::hunks_now(id)` computes a document's changes on the engine thread from its current text.
Revert and navigation use it, so they never act on hunks a few keystrokes old.
`Engine::head_text(id, &hunk)` gives the lines a hunk replaced.

Four commands act on the hunks:

* `git.revert_hunk` (Revert Change, Edit category, no default binding) replaces the change at the source caret with its `HEAD` lines as one undo step.
It reports "there is no change here" when the caret is in no change.
* `git.next_change` (Go to Next Change, Alt-Down) and `git.previous_change` (Go to Previous Change, Alt-Up) move the caret to the next or previous change, wrapping round at the ends.
They report "there are no changes" when there are none.
* `git.show_changes` (Show Changes, View category) switches the sidebar to the Changes panel.

`GitRepository::ahead` is an `Option<usize>`: the commits on the current branch that the remote named by `git.remote` does not have, or `None` when the branch has no remote-tracking branch.
It is refreshed with the status.

=== Blame and remote links

`Repository::blame(path, current)` and `Repository::head_blame(path)` use gix's blame (the `blame` feature) from the HEAD commit.
`blame_through(head_blame, hunks, lines)` carries the HEAD blame over to the current text.
A `BlameLine` is `{ line, commit: Option<short id>, author, time (Unix seconds), summary }`, and a line with no commit is not committed.

`Engine::request_blame(id)` computes the HEAD blame lazily on a worker and publishes `EngineEvent::GitBlameChanged(id)` when it is ready.
`Engine::blame_for(id)` returns the blame overlaid with the document's current hunks.
It returns an `Arc<Vec<BlameLine>>`, built once for each version of the text, hunks and blame, so the front end can ask for it on every frame.
The blame is forgotten on save, when `HEAD`'s commit moves and on rediscovery.
A status refresh that leaves `HEAD` where it was (a save, staging) keeps it.

`git.show_blame` (Toggle Blame, View category, no default binding) shows or hides the column in the front end.
`Engine::remote_link(id, offset)` builds the address of the line at an offset.
It uses `Repository::is_pushed(remote, branch)` and `remote_link_for_line(remote_url, head, path, line, hosts)`, where `HostKind` is `GitHub`, `GitLab`, `Bitbucket` or `Azure` and `hosts` comes from `[git.hosts]`.
`navigate.open_on_remote` (Open on Remote) and `navigate.copy_remote_link` (Copy Remote Link) are Navigate commands with no default binding.
Both return `CommandOutcome::Url`, or an error when there is no such remote, the branch is not pushed or the host is not recognised.

== File access

`adoc_core::FileAccess` is the policy for which files the engine may read.
It has two variants: `Any`, the default, and `Within(roots)`.
`permits(path)` checks the path lexically, then checks the part of it that exists with symbolic links followed.

The engine holds one policy (`Engine::set_file_access` and `Engine::file_access`) and applies it when it opens a document, to includes (`SnapshotIncludes`), and to the pages an export reads.
`adoc-pdf` receives it through `PdfOptions::access`.
When the policy is confined, the engine chooses `Diagrams::in_process`, so only Mermaid renders and Graphviz, PlantUML and D2 are not run, as they can read files themselves.

`adoc-mcp` sets `FileAccess::Within(roots)` before it opens the workspace.
The application, `adocfoundry-cli` and `adoc-ls` leave it at `Any`.

== Search, replace and rename previews

Multi-file changes are computed first as an `EditPreview`: a list of file moves and per-file edits.
Nothing is changed until `workspace.apply_preview` is invoked with the preview's id.

Applying a preview creates one undo group that spans every document it touches, including file moves.
One undo therefore restores every xref and moves a renamed page back.
The undo is refused, naming the page, if a page of the change was edited afterwards; see <<undo-groups>> for the rule.

A preview is applied as a checked transaction.
Each `FileEdits` records in `base` the text its edits were computed against, which is also the text the confirmation dialog shows, so a buffer with unsaved edits is previewed from the buffer and not the file on disk.
Apply returns `EngineError::PreviewStale { path }` if any listed file's text differs from its `base`, and changes nothing.
Before anything changes, `validate_moves` checks that each source is a file, that nothing is at the destination, that the destination's nearest existing folder is a folder, and that no two files move to the same place.
`apply_group` then applies the edits and moves; if a move fails, `roll_back` discards the group with `discard_group` and reverses the recorded moves, so no edit, move or undo or redo entry of the change remains.

`workspace.search` returns immediately and delivers matches as `SearchResults` events.
The worker reads each file itself: an open page's buffer, unsaved edits included, otherwise the file on disk.
It does not copy every file's text out of the index first.
Each event carries up to 500 matches, or whatever was found once 50 ms have passed.
Every batch has `done: false` except the last, which has `done: true`.
A search stops at `SEARCH_MATCH_LIMIT` (10,000) matches, and its last event then has `limited: true`.
Starting another search stops the earlier one at its next file, but the earlier one still sends its final `done: true` event.
`wait_for_workers` counts a search's worker as finished only at its `done` batch.
Lines are counted (`LineIndex`) only in a file with a match.
`workspace.replace` and `page.rename` return a `Preview` outcome.
Rename finds every xref that resolves to the page using the index and the resolver.
`Engine::rename_preview` also adds `outgoing_edits` for the moved page itself.
It resolves each of the page's xref, include and image targets from its current place with `adoc_lang::definition_at_offset`, and rewrites those whose meaning the move would change (`rewritten`): `relative_path` for folder-relative targets and `antora_id` for resource IDs.
Attribute-based targets, URLs and pure fragment references are left as written, and the edits belong to the same preview and undo group.

[[new-page]]
== New Page

`new_page.rs` makes a page in an Antora module.
`page.new` takes `CommandArgs::NewPage(NewPage { module, title, add_to_nav })`, where `module` is the module's root (`.../modules/<name>`), and returns `CommandOutcome::Opened(id)`.
`Engine::new_page(&NewPage)` does the work.
`Engine::new_page_modules()` returns the `PageModule { root, label, nav, active }` values a front end offers: `label` is `version@component:module` (or `component:module`), `nav` is the module's `nav.adoc` if it has one, and `active` marks the module of the active page.

The file is created with `create_new`, so an existing page is never overwritten.
The component's descriptor is then reloaded so that the catalog knows the page, which emits `CatalogChanged` and rebuilds the Navigation panel.
The engine opens the page, pushes an empty undo marker in its history, and applies the navigation edit in the same `UndoGroup`.
The group's documents are recorded in `group_documents`, so it undoes only as a whole, and the file in `group_created`.
If opening the page or editing the navigation file fails, the file is removed and nothing remains in the undo history.

The entry's position comes from `Engine::nav_trees_of` for that file, which reads buffers and not the disk.
Each entry's resolved target is matched against the active page's Antora coordinate.

`Engine::undo` and `Engine::redo` call `replay_creations` after `replay_moves`.
Undo deletes the file only while it holds exactly what New Page wrote and the page has no unsaved edits.
Redo writes the file again and reopens it without changing the active tab.

== Language features

The engine delegates definition, hover, completion and diagnostics to `adoc-lang`.
That is why the editor, the command-line checker and the language server give identical answers.
For an open page the engine calls `adoc_lang::definition_in`, `hover_in` and `completion_in` with the page's own parse; `definition_at_offset`, `hover_at_offset` and `completion_at_offset` take text, parse it with `with_document` and call them, and `adoc-ls` uses those.
`Engine::completes_after(id, offset, typed)` reads only the caret's line (`adoc_parser::completion_context`) and says whether typing `typed` there is inside something that completes: a target being typed, `<<`, or an attribute reference.

`adoc-ls` is a front end of the engine.
It opens workspace folders with the engine, and keeps client buffers in it with `Engine::open_text(path, text)`, which works for a file that does not exist.
Each incremental change becomes one `edit.replace_range`.
Further engine methods serve it:

* `Engine::references(id, offset)` returns the references to the page or anchor at an offset.
* `Engine::anchor_rename_edits(id, offset, new_id)` returns the edits that rename an anchor and every reference to it.
* `Engine::asciidoctor_executable()` returns the Asciidoctor in use, from `tools.asciidoctor` or `PATH`.
* `Settings::with_git_opt_in()` leaves Git off unless the user settings file sets `[git] enabled = true`. It is kept across settings reloads.

`page.rename` also rewrites includes: an Antora include keeps its family and coordinates, a relative one stays relative, and one written through an attribute is left as written.

[[problems]]
== Problems

`src/problems.rs` keeps the diagnostics of the whole workspace, so a front end does not diagnose it again itself.
A front end opts in with `Engine::enable_problems()`; the app does in `AppState::new`, while the CLI, `adoc-ls` and `adoc-mcp` do not and pay nothing.
`Engine::problems()` returns each file with problems as a `BTreeMap<PathBuf, Vec<Problem>>`, and `Engine::problem_count()` returns their number.
A `Problem` holds `range`, `line`, `column`, `severity`, `code` and `message`.
`line` and `column` count from 1, the column in characters rather than bytes.
They are computed from the index's own text of the file, or for a component descriptor from the file, read through the engine's `FileAccess`.

Whenever every open document is re-diagnosed, a worker diagnoses the whole workspace again over a copy of `WorkspaceState`.
It is started from `pump`, so a burst of changes runs one pass, and the generation of a newer pass drops an older result.
After an edit, only the files `diagnosed_with` gives, open or not, are re-diagnosed at the next `pump`.
Edits made while a full pass runs wait for its result.
Each update publishes `EngineEvent::ProblemsChanged`, and `has_pending()` counts problems still to compute.

== Reports and inspection

Headless front ends need answers that are not editor features.
Two engine modules provide them.

`report.rs` builds the reports that `adocfoundry-cli` prints:

* `check_report` returns the workspace's diagnostics and whether they meet a failure level.
* `git_status_report` returns each root's branch and changed AsciiDoc files.

The CLI prints these, and `adoc-mcp` returns them, so the two cannot drift.

`inspect.rs` answers questions about the catalog:

* `resolve_target` resolves a macro as written, or a bare xref target, read with the page's attributes.
* `resource_id` gives the Antora resource id of a file.
* `resolve_resource_id` finds the file for a resource id.
* `resource_id_string` writes a resource id as `version@component:module:family$path`.

`adoc-mcp` may depend only on the engine and `adoc-core`, so what it needs from the catalog comes through these methods.

[[the-doctor]]
== The doctor

`doctor.rs` builds the support report that `adocfoundry-cli doctor` prints and the app's *Show Diagnostics* dialog shows.
`Engine::doctor()` gathers, on the engine thread, what the report needs into a `Doctor`: the tool settings, the theme source and fonts directories as PDF export resolves them without a page, and the settings files and their warnings.

A front end adds what only it knows with `Doctor::program(name, version)` and `Doctor::add_section(DoctorSection)`.
`Doctor::search_path` overrides `PATH`, for tests.

`Doctor::run()` can be called off the engine thread.
It runs each tool's version command in parallel, each with a timeout of 15 seconds (`PROBE_TIMEOUT`), checks the theme's fonts with `adoc_pdf::missing_fonts`, and returns a `DoctorReport`.
A report is sections of labelled lines; `to_text()` aligns them and it serialises to JSON.
It holds no page content, and the engine makes no network request.

The command `app.diagnostics` (*Show Diagnostics*, in the Help category) returns `CommandOutcome::Diagnostics(Box<Doctor>)`, leaving the front end to run it.
See xref:desktop-app.adoc#diagnostics[Diagnostics] for the app's side.

[[about]]
== About

`about.rs` builds what the app's *About AdocFoundry* dialog shows.
The command `app.about` (*About AdocFoundry*, in the Help category) returns `CommandOutcome::About(Box<About>)`.
`About` holds the name, version, optional build, the licence (`CARGO_PKG_LICENSE`) and its text (`LICENSE`), the repository and documentation addresses (`DOCUMENTATION`), and the `Notices`.

A front end names itself with `About::program(name, version, build)` and gives its embedded notices with `About::notices(Notices::from_json(...))`.
`Notices::from_json` refuses notices that name a text they lack.
`Notices::texts(notice)` and `Notices::text(notice)` give a component's texts.
As with the doctor, the engine owns the command and the view only renders it.
See xref:building-and-releasing.adoc#notices[cargo xtask notices] for how the notices are generated and xref:desktop-app.adoc#about[About] for the app's side.

== Engine features

The engine has two Cargo features, `typst` and `git`.
Both are on by default for the crate and off in `[workspace.dependencies]`, so each front end names the ones it wants.
Without `git`, the engine behaves as with `[git] enabled = false`.
Without `typst`, the export commands are not registered and `export_blocking` fails.

== Navigation history

Back and forward history is engine state, so every front end and the command-line tests share it.
`navigate.follow_link` opens and activates the target and records the position that was left.
