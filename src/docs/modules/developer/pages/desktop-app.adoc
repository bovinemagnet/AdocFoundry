= The desktop app
Paul Snow
:revnumber: 0.0.0
:description: How the GPUI application renders engine state, stays in sync with the editor widget and binds keys.

`adocfoundry` is the desktop application.
It is the only crate that imports GPUI, gpui-component or any other UI framework.
Views are thin: they render engine state and dispatch commands.
Logic that could live in `adoc-engine` lives there.

== GPUI and gpui-component

The application is built on GPUI through the `gpui-pre` snapshot crates and `gpui-component` (all Apache-2.0), with `gpui-pre-platform` for the platform layer and `gpui-kit-assets` for icons.
The choice was confirmed by a spike, recorded in `docs/qa/spike-gpui.md` and summarised in xref:testing.adoc#platform-status[Testing].

== AppState and the pump

`AppState` is the single owner of the `Engine`.
Views hold an `Entity<AppState>`, invoke commands through it and subscribe to the engine events it re-emits.

A background task pumps the engine every 16 ms while work is pending, such as indexing or a search, and every 100 ms when idle.
Each pump applies worker and watcher results and then re-emits every engine event to the views.
`AppState::invoke` also drains events before it returns, so the effect of a command is visible immediately.

=== Redraws

In GPUI a `cx.notify()` on any entity redraws the window, and an uncached view's `render` runs on every redraw.
`AppState::drain` therefore does not notify.
It pumps the engine and re-emits its events, and each view redraws itself for the events it shows.
Events that only say something is ready to read again (`DiagnosticsUpdated`, `WordCountChanged`, `SpellingChanged`, `GitHunksChanged`, `GitBlameChanged`, `GitStatusChanged`, `ProblemsChanged`, `NavigationChanged`, `PreviewLayoutChanged`, `DirectoryListed` and `ImageChanged`; see `is_idempotent`) are passed on once per drain however often they came.
Events that carry what changed, such as `DocumentChanged` with its edits, search results and failures, are each passed on.

`WorkspaceView::on_engine_event` notifies only for events that change what the workspace window itself draws: its tabs, sidebar, status bar and title.
`WorkspaceView::shows` decides.
It says no to `DirectoryListed`, `SearchResults`, `PreviewReady`, `PdfPreviewReady`, `ModelChanged`, `SpellingChanged`, `GitBlameChanged`, `ImageChanged` and `DiagnosticsUpdated`, because the Files panel, the search view, the preview, the editors and the image viewer redraw themselves for those.
A `DocumentChanged` notifies only when the unsaved mark on the page's tab flips (`shown_dirty`).

The source editor, the visual editor and the docked preview are embedded as cached views (`Entity::cached` with a full-size style), so a redraw of the workspace around them reuses their last frame.
GPUI re-renders a cached view when it, or an entity it read while rendering, is notified.
`SourceEditorView` notifies on the widget's state changes only when the caret or the scroll offset moved, because the change markers follow scrolling; the widget redraws its own text.
The visual editor also redraws on `SpellingChanged` for its document, as it draws the engine's misspellings.

== Editor synchronisation

The editor widget owns a display buffer for speed, and the engine rope is the truth.

The widget reports that its text changed but not the edit range.
The application therefore recovers each edit as the single replacement between the common prefix and suffix of the widget text and the engine text, in `editor/sync.rs`.
It compares the widget's rope and the engine's rope (both `ropey` 2) chunk against chunk from the start and the end, with slice comparisons and no copy of either text, and allocates only the replacement.
`sync_widget_to_engine` takes the widget's rope, which a clone shares, and returns the version its edit made.
`SourceEditorView` keeps those versions (`own_versions`) and does not reconcile the engine's `DocumentChanged` for them; an edit from elsewhere still reconciles.
That is exact for typing, deletion and paste, and still correct, if wider, for anything else.
Typing arrives at the engine one character at a time, so undo coalescing works.

In the other direction, a change that originates elsewhere (undo, replace, rename or a reload from disk) arrives as an engine event and is applied back to the widget.

Undo, redo, go to definition, follow link and peek include are bound in the editor's key context after gpui-component's own bindings.
They therefore take precedence and go through the engine instead of the widget's own history.

== Engine-backed providers

gpui-component's definition, hover and completion hooks take and return `lsp-types` values.
`editor/providers.rs` translates the engine's answers into those types.
Every answer comes from the engine, and so from `adoc-lang`, exactly as `adoc-ls` gives it.
The completion provider asks `Engine::completes_after` in `is_completion_trigger`, so typing prose never asks for completions.
This module is the only place the app uses `lsp-types`; see xref:architecture.adoc[Architecture].

Link detection under the pointer and modifier-click handling live in the editor module.
Opening a target activates its tab.
An image target opens in an image tab, and an external target such as an attachment opens in the system's default application.

== Keymap

`editor/bindings.rs` binds the `default_binding` of every command's `CommandSpec` to a GPUI action.
The engine writes bindings as `cmd-s`; the application maps `cmd` to GPUI's `secondary` modifier, which is Command on macOS and Control elsewhere.
A command has an action only when the application defines one for its id.

Three actions have no engine command and are bound in the application: the command palette, the theme toggle and the read-only second window.
The palette lists every command with its title from the registry.

== Menus

`src/menus.rs` holds the application menu shown by the ☰ button in the title bar.
`MENUS` is the layout: for each menu, a list of command ids, the three UI-only actions and separators.
`AppMenu` is the title bar entity, which shows the button or, while a menu is open, the menu names.

Titles come from each command's spec in the engine's registry.
Actions come from `action_for` and `ui_action` in `editor/bindings.rs`, the same ones the keymap and the palette use, so a menu item can never run something different from its key.
The popup is gpui-component's `PopupMenu`, given the focus handle that had focus when the menu opened as its action context.
The action therefore reaches the source editor or the visual editor, whichever was focused.

An item whose command cannot run is disabled, not hidden.
A command the build lacks, such as the PDF export commands without the `typst` feature, is left out.

The test `every_command_is_in_a_menu` fails when a command with an action is in no menu and not in the short `NOT_IN_MENUS` list.
That list holds `document.overwrite` (Save, Overwriting the File on Disk, offered only after a conflict), `visual.split_block` (New Paragraph, bound to kbd:[Enter]), and `document.close_left` and `document.close_right` (Close Left and Close Right, which belong to the tab menu).
A new command must therefore be added to a menu or to that list.

== Recovery and local history dialogs

`src/history_view.rs` holds both dialogs: `show_recovery` and `show_history`.
Their views, `RecoveryList` and `HistoryList`, share one diff view that draws the engine's `line_diff` output, removed lines red, added lines green and skipped runs counted.
They invoke `document.recover`, `document.discard_recovery` and `document.restore_version`; the views hold no copy of the text.

`WorkspaceView::offer_recovery_at_start_up` opens the recovery dialog after the window is first drawn (`window.defer`) when `Engine::recoverable()` is not empty.
`on_recover_unsaved` and `on_local_history` handle the File menu items, whose actions are `RecoverUnsaved` and `LocalHistory`.
Neither has a default key binding.
`main.rs` sets the state folder with `.with_state_dir(Settings::default_state_dir())`, `AppState::new` enables recovery and local history, and `cx.on_app_quit` calls `Engine::write_recovery_now()` so that pages unsaved at quit are offered at the next launch.
See xref:engine.adoc#crash-recovery[Crash recovery] and xref:engine.adoc#local-history[Local history].

== Window focus

`WorkspaceView` observes window activation (`observe_window_activation`) and calls `Engine::focus_lost` when its window becomes inactive, which is how `on_focus_change` auto-save saves edited pages when the window loses focus.

== Windows

Window creation lives in `app.rs`.
`open_secondary_window` takes a `WindowKind`.
`Mirror` is a read-only view of the active document that follows its edits.
`Preview` is the rendered preview detached from the workspace window, and closing it docks the preview again.

== The preview

`crates/adocfoundry/src/preview/` paints the engine's `ViewTree`.
It owns no document semantics: the engine decides what is previewed, and the view renders `rendered_preview(id)` each time `PreviewReady` arrives.

[cols="1,4"]
|===
|Module |Responsibility

|`mod.rs`
|The preview view and its toolbar (title, Pin, Sync and Detach buttons), scroll positions remembered per page, and syntax highlighting of source blocks with the editor's tree-sitter grammars.

|`blocks.rs`
|Painting block elements: sections, lists, tables, admonitions, code, images and diagrams. A missing image gets a placeholder, and a diagram that is still rendering or has failed shows its source.

|`inlines.rs`
|Painting inline content and its links. An unresolved xref gets a wavy underline in the danger colour.

|`sync.rs`
|Scroll sync in both directions, between the caret and the topmost visible block.
|===

The docked pane and the detached window are two views of the same engine state.
Detaching sets the layout through `view.detach_preview` and opens a `Preview` window; closing that window docks the preview again.

Clicks become commands.
A click on a block invokes `navigate.reveal` with the position of its source, which may be in a partial that is opened in a tab.
A click on a resolved xref invokes `navigate.go_to`, so it is recorded in history.
External links open in the browser and file links in the system's default application.
Block lookups use `adoc_render::block_at` and `block_by_trail`, which map between source offsets and a block's index trail.

The application depends on `adoc-render` for the view types only; `adoc-dom` and the parser crates stay behind the engine.

== The visual editor

`crates/adocfoundry/src/visual/` draws the engine's `VisualDocument` as rendered text that can be edited in place.
Like the preview, it owns no document semantics.
It holds a selection and a few pieces of view state, invokes visual commands, and draws what `visual(id)` returns each time `ModelChanged` arrives.

[cols="1,4"]
|===
|Module |Responsibility

|`mod.rs`
|`VisualView`: renders a document, holds the selection, the pending block and the typing marks, and dispatches commands. It maps clicks and drags to selections, and follows the source editor's caret in split mode.

|`text.rs`
|An editable text block: styled runs, wrapping, the caret and selection painted over the text, and hit testing. The layout of every text block drawn in a frame is recorded by path, so a click maps back to a display offset and arrow keys move by visual line.

|`input.rs`
|The visual editor's key bindings (`bind`), caret movement and deletion as actions, and the window's input handler for typing and IME composition.

|`blocks.rs`
|Model nodes to elements. Text blocks are drawn for editing. What the model keeps read-only (images, diagrams, included content, verbatim source) is drawn by the preview's block renderer from the `ViewTree` built with the model.

|`format.rs`
|Marks on the selection or on the text typed next, and the link and image dialogs.

|`toolbar.rs`
|The formatting toolbar and the block-type picker.
|===

=== Selection as source offsets

A `Selection` is an anchor and a head, both byte offsets into the page source.
The selection therefore survives a model rebuild unchanged, and maps through an edit made elsewhere like a source selection.
When the document changes under the view, the selection is moved with the engine's `Mapping` of the edits.
Offsets are converted to display positions only when painting and hit testing, through the model.

The caret carries the marks of the text before it, so typed text continues a mark.
With nothing selected, Bold, Italic, Code and Highlight toggle the marks the next typed text carries; the view holds them and resets them when the caret moves.

=== Hit testing and layouts

Each frame, every text block records its shaped layout under its path in the model.
The text block holding the caret is found once per frame, in `blocks::document`, and each block compares its path with it.
`Model::text_block_at` searches an index of the text blocks ordered by where they start.
The index is built on the first lookup and is not carried by a clone (a model is cloned to be changed), so a lookup no longer walks the model.
The misspellings and the Git hunks are sorted once per frame, and each block finds its own by binary search.
The typeset formulas' gaps are measured again only when the model shown, the font or its size changes.
The model shown changes with a new `VisualDocument`, not merely a new version, since formulas are typeset after the model is published.
In the preview, each text holding formulas keeps its measured gaps as GPUI element state, keyed by the formulas' images and fonts and the text's size.
A click looks up the layout under the pointer, finds the display offset, and asks the block for the nearest caret stop.
Clicking read-only content does not place a caret: it shows the source in split mode and moves the source editor to the content, through `view.show_split` and `navigate.reveal`.

=== Input and IME

The view is the window's input handler while it has focus.
Typed text becomes `visual.insert_text` over the selection.
An IME composition is shown underlined in place at the caret but is not in the document; it is committed as one `visual.insert_text` when the input method commits it.
The test platform exercises this path, which is not evidence that a real input method works.

=== The pending block

Enter at the end of a block begins a paragraph or list item that exists only in the view, as `Pending`.
AsciiDoc has no empty paragraph or empty list item, so nothing is written to the source until its first character, when `visual.insert_block` writes it.
A second Enter on a pending list item leaves the list instead.
Moving the caret away discards a pending block.

=== The toolbar

Every toolbar button runs the same engine command as its key binding and palette entry.
Marks show as selected when the caret is in text that has them.
The Table menu appears only while the caret is in a table cell.

=== Split mode

The mode buttons beside the tabs are in `workspace_view.rs` and invoke the `view.show_*` commands.
In split mode the visual editor reveals the block holding the source editor's caret (`reveal_offset`) without moving its own selection, and the source editor scrolls to the visual caret.
Edits in either editor reach the other through the engine: the source editor applies `DocumentChanged` edits to its widget, and the visual editor redraws from the model once it is rebuilt.

== Tabs and the sidebar

Opening a tab follows the engine's active document.
Link following, back and forward and palette commands therefore all arrive the same way, and the views do not hold a second record of which page is open.

The engine also owns the tab order (`Engine::tab_order`) and which tab is the preview tab (`is_preview`).
`Engine::open_as(path, OpenDisposition::Preview | Persistent)` opens a page either way, and the commands `document.browse` (open as a preview, driven by clicks and with no action of its own) and `document.keep_open` (Keep Open) are the front end's way in.
Every text change goes through `edit_document`, which keeps the document open, and so does saving.
Replacing the preview tab reads the new file first, so a file that cannot be read leaves the tab as it was.
The new document takes the old one's place in the tab order, the engine emits `EngineEvent::PreviewTabReplaced { old, new }` and then closes the old one.
Close Left and Close Right follow the tab order.
Only a front end that shows tabs calls `Engine::enable_preview_tabs`: the app does in `AppState::new`, so the CLI, the language server and the MCP server keep every document they open.
In the app, `WorkspaceView::open_at` takes an `OpenDisposition` and returns the opened `TabItem`, and `replace_tab` moves the new tab into the old one's slot.
The workspace's tabs are `TabView::{Editor, Image}`, following the engine's `TabItem`s.

The sidebar's Navigation, Modules and Problems trees and the outline are built from engine state in `sidebar.rs`.
Every leaf's id encodes where clicking it leads, so one handler serves all of them.

The Problems panel (`sidebar::problems`) builds its rows from `Engine::problems()` when `EngineEvent::ProblemsChanged` arrives and when a window opens, each labelled `line:column message`.
It does not diagnose the workspace or read files, and nothing is computed while the sidebar renders.
Peek Include shows the text in the `CommandOutcome::Peek` that `navigate.peek_include` returns, and reads nothing itself.

The engine owns the expansion settings (`ExpansionPolicy` and `SidebarSettings`) and the expansion state (`src/expansion.rs`).
The front end builds the trees and passes their branches, as `Branch { key, children }`, to `Engine::resolve_expansion`, which gives every branch it sees its policy default once.
After that `Engine::branch_expanded` reports a branch and `Engine::set_branch_expanded` records the user's choice.
The bulk operations are the commands `sidebar.expand_all`, `sidebar.collapse_all`, `sidebar.collapse_one_level` and `sidebar.reset_expansion`, which take `CommandArgs::Panel(SidebarPanel)`, act on the tree resolved last and emit `EngineEvent::ExpansionChanged(panel)`.
The app binds them to the actions `ExpandSidebar`, `CollapseSidebar`, `CollapseSidebarLevel` and `ResetSidebar`.
The command palette and the View menu dispatch those actions, which `WorkspaceView` sends to the panel shown, while the panels' own context menu names its panel directly.
`SidebarMenu` is bound to `shift-f10` in gpui-component's `Tree` key context, and `WorkspaceView` then opens the panel's menu as a `PopupMenu` drawn over the shown tree.
Only chosen branches are saved, in a versioned JSON file written atomically 500 ms after the last change (`EXPANSION_SAVE_SETTLE`) and keyed by the workspace's roots; `open_workspace` loads it after writing the previous workspace's state.

In the app, `sidebar.rs` builds `Node`s with stable keys taken from component@version, then module and family, or nav file and entry (title and link target, counted among alike siblings).
Keys never use row numbers.
A node's tree item id is its key followed by its target.
`WorkspaceView` resolves the nodes before showing them, so a rebuilt tree never flashes fully open, records `TreeEvent::Expanded` and `TreeEvent::Collapsed`, and shows a panel again on `ExpansionChanged`, keeping the selection or its nearest shown ancestor.

The Files view is the `FilesView` entity in `files_view.rs`.
Its row ids are the root plus the native path, and a map from id to row holds the exact path.
It holds the expanded folders, the placeholder note rows ("Loading…", "Empty folder" and the failures), Reveal in Files (`reveal`, with `forced` paths shown though excluded) and the context menus.
It asks the engine for a folder's listing with `Engine::request_directory` when the folder is opened, and draws `Engine::directory(dir)`.
`opens_externally` lists `pdf` only, the one extension a click or Space hands to `open_with_system`.
Images go to the engine's `open_item`, which opens them in an image tab.
Any other file is opened as text through the engine, which refuses a file that is binary or not UTF-8, so selecting a file can never run or install it.
A symbolic link is never handed to the system by a click; Open Externally in the context menu is the one way to open any other file in the system's application.
Space is bound to `OpenFileEntry` in the `FilesTree` key context.
The editor's highlighting comes from `editor::language::for_document`: AsciiDoc for pages, gpui-component's grammar named by the file's extension, or plain text.

== Quick Open

`WorkspaceView::on_quick_open` shows gpui-component's `Command` palette with `filterable(false)`, and asks the engine for `workspace.quick_open` on each query change.
The engine ranks and the picker only displays the rows; see xref:engine.adoc#quick-open[Quick Open] in the engine.
Enter opens the file with `OpenDisposition::Persistent`.

== Sessions and Open Recent Folder

`WorkspaceView::new` calls `Engine::restore_session` when it is given no folder and no files.
It then gives every restored tab its tab view, its visual editor when its mode needs one, and its caret.
`WorkspaceView::write_session` passes the engine the carets (the visual editor's in visual mode, otherwise the source editor's) and runs from `cx.on_app_quit` and from the main window's `on_window_should_close`.
`AppState::new` calls `Engine::enable_sessions`.

The Open Recent Folder picker is the command palette's `Command` with its built-in filter over the name and path.
It shows the folders from `workspace.open_recent` and opens the chosen one with `workspace.open_folder`.
See xref:engine.adoc#sessions[Sessions and recent folders] in the engine.

== New Page

`WorkspaceView::on_new_page` builds the New Page dialog from `Engine::new_page_modules`.
It is an alert dialog holding an input for the title, gpui-component's `Select` for the module and a `Checkbox` for the navigation entry, which is disabled when the chosen module has no `nav`.
Create invokes `page.new` with `CommandArgs::NewPage`.
When the command is refused the dialog stays open, so that another title can be tried, and the reason is shown in a notification.
See xref:engine.adoc#new-page[New Page] in the engine.

[[image-viewer]]
== The image viewer

`image_decode.rs` is pure and needs no display, and has its own unit tests.
`decode_file(path, Limits)` returns `Decoded { info, pixels }`, where `info` is an `ImageInfo { format, width, height, file_bytes, intrinsic, has_alpha }` and `pixels` are BGRA.
Raster formats are decoded with the `image` crate, at the version GPUI uses.
The limits are checked from the header before decoding, and the allocation is capped.
SVG is rendered with `resvg`, also at GPUI's version, with an `ImageHrefResolver` that refuses every href that is not a `data:` URI, so a file can load no other file or address.
System fonts are loaded once, for SVG text.
Failures are a `DecodeError`: `Unreadable`, `Unsupported`, `Corrupt` or `TooLarge`.
The file's content, not its extension, decides the format.

`image_view.rs` holds `ImageView`, which decodes on a background task.
Each load has a generation, and a result from an older generation is dropped.
A replaced or closed image is released from the GPU with `drop_image`.
`Zoom` is `Initial`, `Fit` or `Scale`.
`Initial` shows the image whole and never above actual size, `Fit` follows the canvas, and `Scale` is a chosen factor that survives resizing.
Its key context is `ImageViewer`, which carries the zoom keys.
A failed reload keeps the last pixels and shows a banner with Retry.

The fixture `tests/fixtures/image-viewer` is an Antora component with a PNG, a JPEG with EXIF orientation, a GIF, a WebP, a BMP, an ICO, a TIFF, an SVG, a corrupt PNG, a text file named `.png` and a HEIC stand-in.
The app's image tests are in `src/ui_tests.rs`.

[[diagnostics]]
== Diagnostics

`src/diagnostics.rs` completes the engine's `app.diagnostics` command, which returns a `Doctor` (see xref:engine.adoc#the-doctor[The doctor]).
It names the program, adds a Display section that only the app can fill, runs the doctor with `cx.background_spawn` so the probing of tools does not block the window, and shows the result in a dialog with a Copy button.
The Display section gives the graphics backend, the GPU and display server where the platform reports them, the scale factor, and whether the editor and interface fonts are installed.

[[about]]
== About

`src/about.rs` completes the engine's `app.about` command, which returns an `About` (see xref:engine.adoc#about[About]).
It embeds the `notices.json` that `build.rs` writes, names the program with the build string from `ADOCFOUNDRY_BUILD`, and shows the dialog for the `ShowAbout` action.
The dialog is a `uniform_list` of components beside the chosen component's licence texts, with Repository and Documentation buttons and a Copy Licence button.

== Change markers and the Changes panel

`src/editor/changes.rs` paints the source editor's markers over the editor.
It takes positions from the editor's own layout (`EditorState::range_to_bounds`) after the editor has laid out the frame, so the markers follow scrolling, soft wrap and folding.
Clicking a marker opens the card, which reads the old lines through `Engine::head_text` and reverts through `git.revert_hunk`.
`git.show_markers` is read each frame.

`src/editor/blame.rs` paints the blame column and watches the line-number gutter.
It takes line positions from the editor's layout as the markers do, so the column follows scrolling, soft wrap and folding.
It reads `Engine::blame_for` and asks for it with `Engine::request_blame`.
With `git.blame_on_hover`, resting on the gutter for 400 ms shows the tooltip.
`relative_time` and `describe` are unit-tested there.
A `CommandOutcome::Url` from Open on Remote or Copy Remote Link is opened with `cx.open_url` or copied.

The visual editor's bars are drawn in `visual/blocks.rs`: a block is marked when its source range intersects a hunk.

The Changes panel is `sidebar::changes`.
It is built from the engine's Git statuses and shown only when a root is in a repository.
Clicking a row invokes `document.open`, asks the engine for the document's changes with `Engine::hunks_now`, and places the caret on the first one (`WorkspaceView::open_first_change`, then `open_at`).
A deleted file's name is struck through and its row opens nothing.
The rows come from `Engine::changed_writer_files`, the list that Stage All uses.
Each row has a checkbox, ticked when the file has changes staged, and it invokes `git.stage` or `git.unstage`.
*Stage All* invokes `git.stage_all_adoc` and is disabled when the list is empty, and *Commit…* is disabled when nothing is staged.

The commit dialog is `commit_dialog`.
It holds the message field, the summary count ("Summary: N of 72 characters", in the warning colour past 72) and the files to be committed.
*Commit* invokes `git.commit` with the message and the paths, and *Commit and Push* then invokes `git.push`.
It reports the outcome in a notification: `Committed abc1234`, or `Saved N file(s) and committed abc1234`.
The `CommandOutcome::CommitDraft` from Save and Commit opens it with the message and paths filled in.
The status bar adds `↑n` from `GitRepository::ahead`.

The status bar also shows `Engine::word_count` for the active document.
For a selection it shows the words from `count_words` over the selected text, using the visual editor's selection in Visual mode and in Split mode while the visual side has focus, and the source editor's selection otherwise.

== Tree-sitter grammars

`grammars/tree-sitter-asciidoc` is a git submodule tracking the `master` branch of `bovinemagnet/tree-sitter-asciidoc`.
The fork is maintained for AdocFoundry and the zed-asciidoc extension now that the upstream project has been archived.
The application depends on its binding crates, `tree-sitter-asciidoc` and `tree-sitter-asciidoc-inline`, as path dependencies.
They are built with `cc` there because turning the C entry point into a `tree_sitter::Language` needs `unsafe`, which the workspace forbids.

`editor/language.rs` registers both grammars with gpui-component.
The queries live in `crates/adocfoundry/languages/`.
The inline grammar is injected into paragraphs, titles, table cells and macro targets, and source blocks are injected by their language.
tree-sitter is for highlighting, folding and injections only; every semantic question goes to the engine.

gpui-component derives folds from multi-line syntax nodes and does not read `folds.scm`.
The query is still kept and checked against the grammar.
