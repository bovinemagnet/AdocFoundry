= Implementation notes
Paul Snow
:revnumber: 0.0.0
:description: Where building Phases 1 and 2 departed from their specifications, and why.

Where building a phase showed its specification to be wrong or incomplete, the implementation made the smallest change that works.
This page summarises the departures that each phase specification records.
The specifications are the authoritative records.

== Phase 1

This section summarises section 20 of `docs/prd/PRD-AdocFoundry_Phase_1_Implementation_Specification.md`.

[cols="1,2,3,3"]
|===
|Area |Specification |Implementation |Why

|Order
|Work package 1.1 (the spike) before 1.2
|1.2, the workspace bring-up, first, then the spike
|The spike calls `adoc_lang::definition_at_offset` in process, which needs the migrated crates and `adoc-lang`.

|GPUI crates
|`gpui-pre` and `gpui-component`
|Also `gpui-pre-platform` and `gpui-kit-assets`
|gpui-pre 0.3.9 moved the platform code into its own crate, and gpui-component 0.8 depends on `gpui-pre` under the name `gpui`. Both extra crates are confined to `adocfoundry` by `cargo xtask layers`.

|LSP types
|`lsp-types` only in `adoc-ls`
|`adocfoundry` may also depend on it, as one listed exception
|gpui-component's editor offers definition, hover and completion only through provider traits typed with `lsp-types`. `providers.rs` is the only module that uses them.

|Grammar build
|`cc` in the application's `build.rs`
|The submodule's binding crates as path dependencies, built with `cc`
|Converting the C entry point into a `tree_sitter::Language` needs `unsafe`, which is forbidden workspace-wide.

|`Location`
|Defined in `adoc-lang`
|Defined in `adoc-core` and re-exported
|`NavItem` in `adoc-antora` needs it, and `adoc-antora` cannot depend on `adoc-lang`.

|`NavTree`
|`component`, `version` and `items`
|Adds `path` and `diagnostics`
|The `adoc.antora.nav-unresolved` diagnostics need somewhere to live, and a component may list several navigation files.

|`UnknownVersion`
|A new resolution error
|Added, but diagnostics treat it like an unknown component and do not report it
|A version of a known component that is absent from the workspace is usually published from another branch or repository, so reporting it would be a false positive.

|Engine API
|As in section 10.3
|Adds `with_clock`, `wait_for_workers`, `has_pending`, `document_for_path`, `workspace_diagnostics`, `nav_trees`, `outline`, `search`, `replace_preview`, `rename_preview` and `apply_preview`
|Command implementations and front ends need them. Every mutation still goes through a command.

|Events
|As in section 10.2
|Adds `DocumentMoved` and `DocumentChangedOnDisk`
|Rename moves an open document's file, and the watcher must tell the UI when a dirty buffer's file changed on disk.

|Folding
|`folds.scm`
|The query is written and checked, but not read by the widget
|gpui-component 0.8 derives folds from multi-line syntax nodes itself.

|Injections
|Rust, Java, JS/TS, Python, Go, JSON, YAML, TOML, shell, SQL, XML/HTML and Dockerfile
|All except XML and Dockerfile
|gpui-component 0.8 ships no XML or Dockerfile grammar. HTML is injected.

|CLI
|`follow <file> <byte-offset>`
|Adds `--root <dir>`, defaulting to the parent of the nearest `antora.yml`
|Following a cross-component xref needs the other components indexed.

|Editor sync
|Widget edits sent as edits
|The edit is recovered as the replacement between the common prefix and suffix of widget and engine text
|gpui-component 0.8 does not expose edit ranges. Typing still arrives as single-character inserts, so undo coalescing works.

|Packaging
|Linux aarch64 cross-built with `cross`
|Built natively on GitHub's `ubuntu-22.04-arm` runners
|GPUI links against system Wayland, X11 and Vulkan libraries, which a native runner provides without a cross sysroot.

|`xtask`
|`layers`, `fixtures` and `package`
|`layers` and `package`
|The fixtures are hand-written and checked in, so nothing needs generating.
|===

== Phase 2

This section summarises section 12 of `docs/prd/PRD-AdocFoundry_Phase_2_Implementation_Specification.md`.
Where it differs from the earlier sections of that specification, section 12 wins.

[cols="1,2,3,3"]
|===
|Area |Specification |Implementation |Why

|acdc-parser licence
|acdc-parser 0.11 (MIT OR Apache-2.0)
|used, with its `evalexpr` dependency replaced by AdocFoundry's own `vendor/evalexpr` through `[patch.crates-io]`
|acdc-parser depends on `evalexpr = "13"`, which is AGPL-3.0-only. acdc uses only `eval_float` and `eval_int` (for `ifeval` operands); the stand-in implements those two in-house under Apache-2.0. See `vendor/README.md`.

|`IncludeResolver`
|`resolve(from, target)`
|`read(requested_path)`: the parser hands over the path it computed from the including file's directory and the target as written
|acdc's include provider receives that path, not the pair. A resolver recognises Antora ids such as `partial$x.adoc` inside it.

|DOM shape
|a variant per block, each carrying span, id, roles and title
|`Block { meta: BlockMeta, kind: BlockKind }`, plus `Heading` (discrete headings) and `Media` (audio and video) kinds
|One place for the common fields; the extra kinds exist in AsciiDoc and must not fall back to raw source.

|`build_view`
|`build_view(dom, resolver)`
|`build_view(source, dom, resolver)`
|The DOM does not carry the page path, and local images and references resolve against it.

|`ViewResolver::image`
|`image(from, target)`
|`image(from, target, imagesdir)`
|`imagesdir` is a document attribute the resolver cannot see; outside Antora it decides where an image lives.

|`block_at` result
|`Option<BlockPath>`
|`Option<Vec<usize>>` (child indices from the root), read back with `block_by_trail`
|A plain index trail needs no new type; list items' and table cells' blocks count as children.

|acdc spans
|Not specified
|`Location::absolute_end` is the start of the last character; the converter extends spans past it, using the page or included file's text
|Without it every span was one character short, and a cell's single-character paragraph had an empty span.

|acdc image targets
|Not specified
|block (`+image::ROOT:image$x.svg[]+`) and inline (`+image:ROOT:x.svg[]+`) images whose target contains `:` or `$` are recovered from the paragraph or text acdc leaves
|acdc rejects those characters in an image target, so every Antora image id fell back to text.

|merman dependency floor
|Not specified
|the workspace pins move to `serde_json =1.0.154` and `serde-saphyr =1.3.0`
|merman 0.9.2 requires those minimums; both are compatible updates and every existing test passes on them.

|`ExternalProvider`
|`{ kind, program, args }`
|`{ kinds, program, args }`: one tool may serve several block styles (`graphviz` and `dot`; `plantuml` and `uml`)
|Asciidoctor Diagram accepts both names for each.

|`Engine::preview`
|`preview(id) -> Option<Arc<RenderedPreview>>`
|`rendered_preview(id)`
|`Engine::preview(PreviewId)` already returns Phase 1's multi-file edit previews.

|Preview target
|front ends call `request_preview`/`release_preview`
|those exist, and the engine also requests the preview target itself: the pinned document, or else the active one, while the preview is visible (`preview_target()`, `PreviewLayout`)
|Following the active page and pinning are then engine state, testable headlessly, and the docked and detached views render the same target.

|Stale results
|a newer request supersedes an older one
|a result is dropped when a newer job has started for the document, or when the document or a file it includes changed after the job started
|An edit during a render must not flash the old text; the replacement job follows after the settle time.

|Diagram tools in settings
|found on `PATH` or set in settings
|found on `PATH` only
|Settings for tool paths are deferred; Mermaid, the common case, needs no tool.

|Mermaid output
|SVG from merman
|merman's resvg-safe pipeline (`SvgPipeline::resvg_safe()`), and a render revision in the cache key
|Mermaid's default labels are HTML inside `foreignObject`, which GPUI's SVG renderer (resvg) does not draw; the revision makes caches written by an earlier renderer miss.

|Preview link and click commands
|`navigate.follow_link` semantics
|`navigate.go_to` (a position, recorded in back/forward history, for xrefs clicked in the preview) and `navigate.reveal` (a position, not recorded, for click-to-source), both taking `CommandArgs::Position`
|`follow_link` needs an open document and a caret offset in it; the preview knows the resolved target, and the source of a block may be an unopened partial.

|Typographic replacements
|Not specified
|applied by `adoc-dom` to plain text outside verbatim content, honouring backslash escapes
|acdc leaves the `replacements` substitution to the converter; without it `(C)`, `--`, `...` and arrows reached the preview unchanged. Found by the fidelity harness.

|Fidelity harness discovery
|skipped when `asciidoctor` is not on `PATH`
|skipped when `asciidoctor --version` does not succeed
|A broken installation (here, Asciidoctor.js's CLI under a newer Node) is as unusable as a missing one. The comparison treats a rendered diagram as the listing block Asciidoctor writes without its diagram extension, and compares paragraph text with character references decoded.

|`render_blocking`
|Not specified
|`Engine::render_blocking(id, timeout)` renders a document once, waiting for its diagrams
|The CLI has no event loop to pump.

|Second parser
|`AsciidocParser` over asciidoc-parser 0.31
|as specified; section and block titles come from its rendered HTML with tags stripped, because the crate exposes no inline tree for them, and line comments (which it parses as empty paragraphs) are dropped
|The crate's public API; Asciidoctor emits nothing for a comment. The corpus comparison lists one disagreement: where a `[qanda]` list after a description list lands.

|Parser choice
|Not specified
|`Engine::set_document_parser` and `adocfoundry-cli render --parser acdc\|asciidoc-parser`; acdc is the default
|The comparison is a development tool; the app keeps one parser.

|Qualified include targets
|Not specified
|before acdc parses a page or an included file, the colons of an include target that is a qualified Antora id (`module:family$path`, `component:module:family$path`) are replaced by a one-byte placeholder, and restored in the path handed to the `IncludeResolver` and in span file chains
|acdc reads `module:` as a URI scheme and links the include instead of reading it. The placeholder is the colon's length, so every offset is unchanged.

|Include paths for relative pages
|Not specified
|acdc joins targets onto an absolute base; the path handed to the `IncludeResolver` is made relative again when the page was given by a relative path, including one above the working directory
|The workspace's include map is keyed by the path as the page was given.

|Legacy asset directories
|Not specified
|`ResourceFamily::directories()`: images and attachments are also discovered under a module's `assets/images` and `assets/attachments`, read first so the standard directory wins when both hold a file; hover names resource ids from either
|Antora still reads this older layout, and real projects use it; their images were unresolved in the preview.
|===
