= Testing
Paul Snow
:revnumber: 0.0.0
:description: The layers of automated tests, the performance probe and the manual QA record.

A change is done when `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`, `cargo deny check` and `cargo xtask layers` all pass.
Always pass `--workspace` or `-p <crate>`: the default workspace member is the application crate only.

== Unit tests

Unit tests live in `#[cfg(test)] mod tests` beside the code.
Add a test with every parser, resolver, engine, command or language-feature change.
Add a regression test for every panic fixed, because incomplete AsciiDoc is normal input.

Shared fixtures are in `tests/fixtures/`, grouped by scenario:

* `simple/`, `includes/`, `xrefs/`, `images/`, `attributes/`
* `antora-single-component/`, `antora-multi-component/`, `antora-versions/`
* `antora-nested-pages/`, `antora-nested-includes/`, `antora-invalid-descriptor/`
* `broken-references/` and `antora-broken-references/`
* `render/`, the preview corpus described below

Reach them with `Path::new(env!("CARGO_MANIFEST_DIR")).join("../../tests/fixtures/...")`, never with absolute paths.
Keep fixtures small and readable, and add one alongside every behaviour change.

== Engine tests

`crates/adoc-engine/tests/` drives the engine headlessly through commands: documents, language features, navigation, search and replace, settings and workspace indexing.
No window is involved.
`tests/about.rs` covers the `app.about` command and the notices it carries.
The notices generator's tests are in `xtask/src/notices.rs`: `every_dependency_of_the_release_build_has_a_notice` and `every_bundled_file_has_its_notice`.
Add a test here rather than in the application crate whenever the behaviour can be reached through the engine.

`adoc_core::probe` counts the work a keystroke does: `Probe::{Parse, HashText, Diff, Reconcile}`, counted per thread with `probe::hit`, read with `probe::count` and cleared with `probe::reset`.
They count only with adoc-core's `probe` feature, which the engine's and the application's dev-dependencies turn on; in a normal build `hit` does nothing.
`tests/keystroke.rs` asserts them: `one_keystroke_parses_at_most_once`, `typing_never_hashes_the_document`, `completion_during_typing_does_not_reparse` and `only_typing_inside_something_that_completes_asks_for_completions`.
In the application crate, `ui_tests::typing_diffs_once_and_never_reconciles` types 20 characters and expects 20 diffs and no reconcile, then expects an edit from the engine to reconcile once.

== CLI snapshot tests

`crates/adocfoundry-cli/tests/cli.rs` runs the binary through `CARGO_BIN_EXE_adocfoundry-cli`.
It checks each Antora fixture and compares the output with `insta` snapshots.
It also follows a link in `tests/fixtures/xrefs/`.

== Preview and render tests

[[render-tests]]
The render corpus is `tests/fixtures/render/`: `blocks.adoc`, `block-options.adoc`, `inline.adoc` and `tables.adoc`, with a `partials/` directory for includes.
`crates/adoc-dom/tests/` checks each parser over the corpus, and `crates/adoc-render/tests/view.rs` checks the view tree.
`crates/adoc-engine/tests/preview.rs` drives the preview service headlessly: the settle time, included-file changes, stale results, diagram completion, following and pinning, history for `navigate.go_to` and `navigate.reveal`, and `render_blocking`.

The fidelity harness, `crates/adocfoundry-cli/tests/fidelity.rs`, renders every corpus page with `adocfoundry-cli render` and with `asciidoctor`.
It normalises both to their block structure and paragraph text.
Block structure must match, and text differences are reported.
The harness is skipped, with a message, when `asciidoctor --version` does not succeed, because a broken installation is as unusable as a missing one.
It treats a rendered diagram as the listing block Asciidoctor writes without its diagram extension.

It also compares a third normalisation, `presentation`, and fails on a difference.
That covers each ordered list's classes and `type`, `start` and `reversed`, each table's classes and width style, each cell's alignment classes, each image block's classes and link, and each `<details>` and `<summary>`.
Rendered diagrams are skipped there too.
`block-options.adoc` holds the lists, tables, images and a collapsible block that this exercises.
It is a file of its own because the snapshot, round-trip and word-count tests of other crates read `blocks.adoc` and `tables.adoc`.

Application tests for the preview are in `ui_tests.rs`: rendering the active document, the detached preview following edits, click-to-source (including into a partial) and scroll sync in both directions.

[[round-trip-tests]]
=== Round-trip property tests

`roundtrip.rs` is the phase's Definition of Done in test form: a documentation page edited visually produces a Git diff that touches only the lines the writer changed.
The corpus is every fixture under `tests/fixtures/` and every page of `src/docs`, so the documentation site itself is a test input.

`serialise_is_identity_on_the_corpus`::
Builds a model of every page in the corpus and checks that serialising it gives the page back byte for byte, and that each text block serialises to its own source.

`edits_stay_inside_the_touched_block`::
Applies random steps at random caret stops over the corpus, with a fixed seed, and checks that every source edit lies inside the block the step touched, and that a locally updated model serialises to the edited text.

`a_long_editing_session_touches_only_edited_lines`::
Applies a scripted session of several hundred steps (more than 500 must apply) over real pages, in the documentation and the render fixtures.
It then takes a line diff against the original and checks that every line that differs is one a step touched.

`the_session_model_matches_a_rebuild`::
Checks that what a locally updated model shows (the text and marks of each block) matches a rebuild from the resulting text in at least 95% of local steps.
The rebuild after `MODEL_SETTLE` corrects the rest.

These tests read the documentation pages, so editing a page can change what they exercise.

`crates/adoc-engine/tests/visual.rs` drives the model service headlessly through commands, with a manual clock: `editor_mode_requests_a_model`, `visual_typing_edits_the_source`, `visual_typing_is_one_undo_step`, `undo_restores_source_and_model`, `source_edits_rebuild_the_model_after_settle`, `stale_model_refuses_visual_edits`, `read_only_text_refuses_visual_edits`, `included_files_rebuild_the_model`, `marks_and_links_are_one_undo_step_each`, `structural_steps_rebuild_the_model` and `tables_and_images_are_edited_through_commands`.

The application tests for the visual editor are the last in `ui_tests.rs`, on GPUI's test platform: `visual_mode_renders_the_document`, `typing_in_visual_mode_edits_the_source`, `clicking_text_places_the_caret`, `ime_composition_commits_once`, `keyboard_formatting_marks_the_selection_or_what_is_typed`, `enter_splits_the_paragraph`, `typing_in_a_table_cell_edits_only_the_cell`, `source_edits_update_the_visual_editor`, `undo_is_shared_between_editors`, `toolbar_bold_toggles_strong` and `included_content_is_not_editable`.
None of them needs a display.
As with the other application tests, `ime_composition_commits_once` is not evidence that a real input method works.

=== Visual regression

`crates/adocfoundry-cli/tests/pdf_regression.rs` renders each reference document with `asciidoctor-pdf` and with `adocfoundry-cli pdf`, rasterises both at 40 dpi with `hayro`, and compares them.
Page counts must be equal.
After blurring, the mean absolute grey difference of each page must be at most 0.02, and the bounding boxes of the ink must agree to within 6 pt.
Books are not compared, because asciidoctor-pdf cannot assemble an Antora component.
The reference article ends with a Formulas section.
asciidoctor-pdf has no native STEM and shows the source in a code box, so that page is held to the same mean difference and edge limits, with the right edge of the ink left out.
Failing pages are written as PNG pairs under `target/pdf-regression/`.
The test is skipped, with a message, when `asciidoctor-pdf` is not on the `PATH`.

=== Corpus checks

Three checks are ignored by default and are driven by environment variables.

[cols="2,4"]
|===
|Variable |Effect

|`ADOC_PDF_CORPUS`
|A directory. The `compile.rs` test exports every page under it as an article, and none may fail to typeset.

|`ADOC_PDF_THEME_CORPUS`
|`<themes dir>:<expected dir>`. The `themes.rs` test loads each theme and compares its keys with asciidoctor-pdf's key map, `<name>.json` in the expected directory. The format is described in `tests/fixtures/pdf/themes/expected/README.md`.

|`ADOC_PDF_OUT`
|A directory. The `reference.rs` tests write reference PDFs there for inspection.
|===

[source,sh]
----
ADOC_PDF_CORPUS=/path/to/docs cargo test -p adoc-pdf --test compile -- --ignored
ADOC_PDF_THEME_CORPUS=/path/to/themes:/path/to/expected cargo test -p adoc-pdf --test themes -- --ignored
ADOC_PDF_OUT=/tmp/pdf cargo test -p adoc-pdf --test reference -- --ignored
----

== Git tests

Tests that need a repository build one with `adoc_git::testing::TestRepo`, available through the `test-support` feature of `adoc-git`.
It creates a temporary repository with `gix`, so no test touches a developer's checkout and none runs the `git` executable.
The shared fixtures in `tests/fixtures/` lie inside the project's own checkout, so a test that opens one in place turns Git off with `Settings::with_git_opt_in()`; with Git on, the engine would discover the checkout and take its status and watch its `.git` files, making the test as slow as the developer's working tree.

`crates/adoc-git/tests/repository.rs` checks discovery, the head, status and line diffs.
`crates/adoc-engine/tests/git.rs` drives the engine's Git state headlessly: discovery, status, hunks and the events, with `revert_hunk_restores_head_text_as_one_undo` and `next_change_wraps_around` for the commands.

Branch-aware versions are covered at each layer.
`TestRepo::checkout` checks out a branch for tests.

* `adoc-antora`: `playbook_parses_sources_branches_and_start_path` and `branches_for_version_matches_globs`, over `tests/fixtures/antora-versions/antora-playbook.yml`.
* `adoc-git`: `branches_and_files_at_a_branch`.
* `adoc-lang`: `xref_to_version_on_other_branch_warns`, `xref_to_version_present_in_workspace_is_silent` and `no_playbook_no_version_diagnostic`.
* `adoc-engine`: `head_change_reloads_descriptors_and_rediagnoses` and `open_in_version_resolves_same_resource_in_other_root`.

Blame and remote links are covered at each layer.
`TestRepo::add_remote(name, url)` adds a remote and `TestRepo::track_remote(remote)` records its remote-tracking branches.

* `adoc-git`: `blame_attributes_committed_lines`, `blame_marks_uncommitted_lines`, `remote_link_github_ssh_and_https`, `remote_link_gitlab_self_hosted_uses_dash_blob`, `remote_link_unknown_host_is_none`, `remote_link_detached_head_uses_commit` and `remote_tracking_and_pushed_branches`, with a unit test of `blame_through` around insertions, changes and deletions.
* `adoc-engine`: `blame_is_lazy_and_invalidated_on_save` and `remote_links_need_a_known_host_and_a_pushed_branch`.

Staging, committing and pushing are covered at each layer.
`TestRepo::set_identity(name, email)` writes the identity to the repository's own configuration, so a developer's global identity never reaches a test.

* `adoc-git`: `stage_and_unstage_round_trip`, `commit_uses_config_identity`, `commit_refuses_without_identity`, `commit_refuses_empty_index` and `unpushed_count_against_remote_tracking`.
* `adoc-engine`: `commit_saves_dirty_documents_first`, `save_and_commit_prefills_message`, `stage_all_stages_the_changed_writer_files` and `push_disabled_without_git_executable`.

== Language server tests

`crates/adoc-ls/tests/stdio.rs` starts the real `adoc-ls` binary and speaks LSP to it: initialise and shutdown, completion, hover, the preview commands and command routing.

`crates/adoc-ls/tests/engine.rs` drives the binary over stdio through the engine-backed features: open, change and close, diagnostics, references, file renames, anchor renames and the workspace check.
The preview tests run in process, in `src/protocol.rs`, with a sink that never opens a browser. They take a guard of their own, because the `spawn_guard()` in `adoc-render` is crate-private.

`crates/adoc-ls/tests/parity.rs` runs the command-line checker and the language server over the fixtures and asserts that they report the same diagnostics.

Tests that spawn a real process must take the crate-private `spawn_guard()` mutex in `adoc-render`, which works around `ETXTBSY`.
Do not remove the guard or add an unguarded spawning test.

== Application tests

Application tests are in `crates/adocfoundry/src/ui_tests.rs`.
They run on GPUI's test platform and need no display.
They cover:

* typing reaching the engine, and undo going through it;
* engine edits reaching the widget;
* following a link opening a tab and recording history;
* the second window mirroring the active document;
* the preview rendering the active document, and following edits when detached;
* the search panel showing workspace results;
* composed input committing the composed text;
* the Git change markers and the Changes panel: `gutter_marks_follow_hunks`, `clicking_a_mark_shows_head_text_and_reverts`, `visual_blocks_marked_when_range_intersects_hunk` and `changes_panel_lists_changed_adoc_files_only`;
* committing from the app: `save_and_commit_commits_the_page_and_counts_it_unpushed`;
* the blame column and hover: `blame_column_toggles_and_hover_shows_the_commit`;
* the version badge: `status_bar_shows_the_version_and_branch`;
* the About dialog: `about_shows_the_version_and_each_components_licence`;
* `every_command_is_in_the_palette` (in `editor/bindings.rs`), which fails when an engine command has no UI action, apart from those driven by typing and clicks.

The last one exercises the widget's input handler on the test platform.
It is not evidence that a real input method works.

Never add a test to `crates/adocfoundry` that needs a display when the behaviour can be tested in `adoc-engine`.
In CI the application crate is built, and its tests are run only where the platform allows.

== Performance probe

The engine's work per keystroke is measured by a release-mode probe on a synthetic 5,008-line document.

[source,sh]
----
cargo test --release -p adoc-engine --test perf -- --ignored --nocapture
----

The budget is 5 ms.
The recorded result is a median of 0.33 µs and a worst case of 50 µs for a keystroke (`keystroke_on_a_5000_line_document`), independent of the page's size, 0.29 µs for `backspace_loop` and 0.87 ms for `visual_typing_loop`, which is the visual model's rebuild; workspace diagnostics for 501 files take 2.3 ms.
That leaves most of each 16 ms frame to the widget.

[[manual-qa]]
== Manual QA

`docs/qa/phase1.md` to `docs/qa/phase5.md` are checklists for what automated tests cannot cover, one for each phase.
They are run on macOS 13+, Windows 10+ (x64 and ARM64) and Ubuntu 22.04+ before a release, from the release's artefacts, and each records its runs in a results table.
`phase1.md` covers the sidebar, the editor, link following, search and rename, themes, settings, the second window and the packages; `phase5.md` covers the release packages, typeset STEM, the language and MCP servers in real clients, and the fixes from the tracker.
