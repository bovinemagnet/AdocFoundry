# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

AdocFoundry is a native desktop editor for AsciiDoc documentation laid out the Antora way, written in Rust for macOS, Linux and Windows. It is built as a thin GPUI shell over a headless engine, with the language crates that began life in `bovinemagnet/zed-asciidoc` as its foundation.

The architecture and phase plan live in `docs/design/DESIGN-AdocFoundry_Architecture.md`. Each phase has an implementation specification under `docs/prd/`; the spec for the phase in progress is the source of truth for scope. `README.md` tracks what is and is not implemented and must be updated when setup or visible behaviour changes.

Phases, in order: (1) source editor with Antora support and link following; (2) native rendered preview; (3) WYSIWYG editing; (4) PDF export with themes; (5) release readiness, fixes, typeset STEM, `adoc-ls` on the engine and an MCP server; (6) inline STEM in the text flow, MCP over HTTP, signed releases and updates; (7) an interactive graph view of the workspace's links (`docs/prd/PRD-AdocFoundry_Phase_7_Implementation_Specification.md`). Do not start a later phase's features unless the current phase's spec says so or you are asked.

**Current state:** Phases 1 to 7 are implemented (work packages 1.1–1.9, 2.1–2.8, 3.1–3.8, 4.1–4.7, 5.1–5.8, 6.1–6.5 and 7.1–7.5); 0.1.0, 0.2.0, 0.2.1, 0.3.0, 0.4.0, 0.5.0, 0.6.0 and 0.7.0 are released, and the manual QA in `docs/qa/phase5.md`, `docs/qa/phase6.md` and `docs/qa/phase7.md` continues, with 0.7.0's release checks in issue #385. Signing needs the Apple and Azure secrets listed in the developer documentation; without them releases build unsigned. Where the implementation departs from a spec, its "Implementation Notes" section records it (§20 of the Phase 1 spec, §12 of the Phase 2 spec, §11 of the Phase 3 and Phase 4 specs, §12 of the Phase 5 spec, §9 of the Phase 6 and Phase 7 specs); read them before changing those areas. The manual checks that automated tests cannot cover are listed in `docs/qa/phase1.md` (IME, frame timing, macOS and Windows runs, packages), `docs/qa/phase2.md` (the preview in the app), `docs/qa/phase3.md` (an hour of visual editing and its Git diff) and `docs/qa/phase4.md` (PDFs side by side with asciidoctor-pdf, validators, the app's export), the documentation quality audit's in `docs/qa/quality.md`, the MCP agent workflows' in `docs/qa/mcp.md`, New Antora Project's in `docs/qa/new-project.md`, the impact inspector's in `docs/qa/impact.md`, font sets' in `docs/qa/font-sets.md`, font sets' in `docs/qa/font-sets.md`, and the GPUI spike's findings are in `docs/qa/spike-gpui.md`.

## Commands

```sh
cargo check --workspace
cargo fmt --check
cargo clippy --workspace --all-targets -- -D warnings   # CI treats warnings as errors
cargo test --workspace
cargo run -p adocfoundry                                 # launch the desktop app
cargo xtask run -- path/to/docs                          # the same; on macOS from a dev bundle in target/, so the Dock shows the icon
cargo run -p adocfoundry-cli -- check tests/fixtures/antora-single-component
cargo run -p adocfoundry-cli -- pdf tests/fixtures/pdf/reference/article.adoc --output /tmp/article.pdf
cargo run -p adoc-ls -- --version                        # smoke-test the language server
cargo run -p adoc-mcp -- tests/fixtures/references       # the MCP server over stdio
cargo deny check                                         # licences and advisories
cargo xtask layers                                       # the crate ladder and confinement rules
cargo xtask package                                      # release build and archive in dist/
git submodule update --init                              # the grammars, needed to build the app
```

`default-members = ["crates/adocfoundry"]`, so a bare `cargo test` or `cargo check` only covers the app crate. **Always pass `--workspace`** (or `-p <crate>`) when working on engine or language crates.

Targeted runs:

```sh
cargo test -p adoc-engine                          # one crate
cargo test -p adoc-antora resolves_cross_component # single test by name substring
cargo test -p adocfoundry-cli --test cli           # one integration test file
cargo test -p adoc-model --test roundtrip          # the visual editor's round-trip properties
cargo test -p adocfoundry-cli --test fidelity      # render vs Asciidoctor (allowed differences in its ALLOWED table); skips itself without asciidoctor
cargo test --release -p adoc-engine --test perf -- --ignored --nocapture   # timing probe (ignored by default)
cargo bench -p adoc-engine                         # benchmarks held to budgets (BENCH_RECORD=1 to only record)
cargo test -p adoc-pdf --test themes               # theme loader against asciidoctor-pdf's key maps
cargo test -p adocfoundry-cli --test pdf_regression   # PDFs vs asciidoctor-pdf, rasterised; skips without it
ADOC_PDF_OUT=/tmp cargo test -p adoc-pdf --test reference -- --ignored   # write the reference PDFs and Typst
python3 fuzz/seed.py && cargo +nightly fuzz run parse_dom -- -max_total_time=120 -rss_limit_mb=4096   # fuzz/ (own workspace, nightly, cargo-fuzz 0.13.2); each crash becomes a regression test
```

The CLI and engine integration tests use `insta` snapshots (`tests/snapshots/`); review a changed snapshot rather than overwriting it blindly.

The user and developer documentation is an Antora site in `src/docs` (modules `ROOT` and `developer`). Gradle exists only to build it: `gradle25w antora` builds the site to `build/site` and reports errors. Nothing in Gradle is needed to build or run the app.

CI (`.github/workflows/ci.yml`) runs on pull requests and pushes to `main`, except those changing only `.md` and `.adoc` files outside `crates/` and `tests/` (its `paths` filters; the docs site, `README.md`, `AGENTS.md` and the design doc are read by tests, so a change to them alone is checked by the next run that changes code), and is called by `release.yml` on `v*` tags, which always runs: lint, `cargo deny` and `cargo xtask layers` on Ubuntu; `cargo test --workspace --exclude adocfoundry` on Ubuntu, macOS and Windows (Ubuntu with asciidoctor and asciidoctor-pdf, so `fidelity` and `pdf_regression` run); the app crate's tests on macOS, where GPUI's test platform needs no display; and veraPDF over the reference PDFs. `release.yml` builds the packages on `v*` tags, signs them when the `APPLE_*` and `AZURE_*` secrets are set (`packaging/macos/bundle.sh` signs inside out, notarises and staples; Azure Artifact Signing on Windows), writes `SHA256SUMS`, and smoke-tests the downloads, signatures included (`packaging/smoke-test.py --expect-signed`, its checks unit-tested in `packaging/test_smoke_test.py`); `publish` waits for that CI run as well as the smoke tests (checked by `packaging/test_workflows.py`, which also fails a job without `timeout-minutes`, an action not pinned to a commit, a checkout that keeps its credentials, a tool installed other than by `cargo install <tool> --version <x.y.z> --locked`, or an unversioned download). Every job installs the toolchain `rust-toolchain.toml` names with `rustup toolchain install`. Never add a test to `crates/adocfoundry` that needs a display when the same behaviour can be tested in `adoc-engine`.

## Architecture

The workspace is a layered crate ladder. A crate may depend only on crates in the layers below it, apart from the same-layer pairs listed in `SAME_LAYER_ALLOWED` in `xtask/src/layers.rs` (`adoc-index` and `adoc-lang` on `adoc-parser`; `adoc-lang` on `adoc-index` and `adoc-antora`; `adoc-pdf` on `adoc-render`). The dependency direction is enforced by `cargo xtask layers` in CI; do not add a dependency that violates it. A new crate needs an entry in `LAYERS` there, and a mention in `AGENTS.md`, `README.md`, the design doc and the developer documentation's crate table and diagram (`architecture.adoc`, `crate-layers.mmd`), which `every_crate_is_documented` in `xtask` checks.

```
L4  adocfoundry (GPUI app)   adocfoundry-cli (headless)   adoc-ls (LSP, stdio)   adoc-mcp (MCP, stdio)
L3  adoc-engine     sessions, documents, command registry, undo, watcher, settings, events
L2  adoc-render     adoc-diagrams     adoc-model     adoc-git     adoc-pdf     adoc-audit     adoc-impact
L1  adoc-parser     adoc-dom     adoc-antora     adoc-index     adoc-lang     adoc-math     adoc-spell     adoc-graph
L0  adoc-core       domain types only; no internal deps; no editor, LSP or UI types
```

- **`adoc-core`** — `Document`, `LineIndex`, `SourceRange` (byte offsets), `Section`, `Anchor`, `Reference`, `IncludeDirective`, `ImageDirective`, `Diagnostic`/`DiagnosticCode`. Diagnostic codes are stable strings (`adoc.unresolved-xref-file`, `adoc.antora.unknown-module`). Never add dependencies here.
- **`adoc-parser`** — line-oriented semantic parser (`parse(uri, text) -> ParseResult`), deliberately *not* tree-sitter and *not* a full AST. It extracts titles, sections, attributes, anchors, xrefs, includes and images from half-typed input without panicking. Keep it fast; it runs on every keystroke-debounce.
- **`adoc-dom`** — the full AST behind `trait DocumentParser`, with spans that map through includes. `AcdcParser` (acdc-parser) is the one the engine uses; `AsciidocParser` (asciidoc-parser) exists for comparison, behind the crate's `comparison` feature, which only `adocfoundry-cli` (for `render --parser asciidoc-parser`) enables and without which the `second_parser` test does not build. External parser crates are only ever referenced inside this crate.
- **`adoc-render`** — the framework-free view tree (`build_view`, references, images and diagrams resolved through a `ViewResolver`), `block_at` for scroll sync, and the HTML backend (`to_html`). The GPUI preview, the CLI and the fidelity harness all render from the same tree.
- **`adoc-diagrams`** — Mermaid in process (merman), Graphviz, PlantUML and D2 through optional tools on `PATH`, and a checksum cache in `<workspace>/.cache/adocfoundry/diagrams`.
- **`adoc-model`** — the visual editor's model, built from `adoc-dom`'s tree and the page text. Its scanner reads each text block losslessly into pieces (text, mark delimiters, atoms) and the build checks that reading against the DOM, making any block where they disagree read-only; such a block's text is drawn from the view tree as the parser read it (`Node::drawn_from_view`, at the place `view_text` names), never from the disagreeing pieces. Steps (`Model::apply`) return the smallest source edits, the selection after, and the updated model for steps that change no structure (structural steps leave the model to be rebuilt). Inline edits are verified by rescanning: typed markup is escaped only where it would form a construct, marks keep their delimiters, and a step that cannot keep the meaning of the text around it is refused. `Delete` across blocks (`delete_across` in `block.rs`) rewrites what is left of both ends as one block through the same rescan, and has no local model; the engine parses the page as it would be (`model_after_deleting`) when more follows, so the whole is one edit and one undo step. It refuses comments and read-only content between the ends, and the edge of a delimited block. The round-trip property tests in `tests/roundtrip.rs` are the phase's Definition of Done in test form; keep them passing.
- **`adoc-git`** — Git over `gix` (pure Rust, no network transports): `Repository::discover`, head, status, line diffs against `HEAD` of a buffer's text, file content at `HEAD`, remote URLs, and revisions read from objects alone (`resolve_revision`, `tree_files`, `text_at`, `tree_changes` with renames, in `revision.rs`). `stage` goes through gix's to-Git filter pipeline with its drivers removed, and refuses a file under a named `filter` (`GitError::FilterNotRun`), so it never runs a configured command; `tests/git_add.rs` compares it with the `git` executable. Never runs the `git` executable. Its `test-support` feature provides `testing::TestRepo`, temporary repositories built with `gix`, for any crate's tests; never test against a developer's checkout.
- **`adoc-pdf`** — PDF export: `theme/` loads asciidoctor-pdf 2.3 YAML themes exactly as its `ThemeLoader` does (checked key by key against golden maps in `tests/fixtures/pdf/themes/expected/`); `emit.rs` writes the view tree as Typst with every document string a Typst string literal, so a document can never inject Typst code (keep it that way: only numbers and enum values are ever spliced); `adoc.typ` is the template, reading the theme's keys as `t` and document facts as `doc`; `world.rs` is the Typst `World` (only listed files, fonts registered under the theme's family names, no packages). The template reproduces Prawn's spacing model (block spacing zero, explicit bottom margins, half-leading per paragraph, line gaps, `keep()` for blocks asciidoctor-pdf keeps together); read spec §11 before changing spacing and run `cargo test -p adocfoundry-cli --test pdf_regression` afterwards. Typst is pinned at 0.15.1.
- **`adoc-antora`** — `antora.yml` parsing (`serde-saphyr`), the playbook (`playbook.rs`: attributes, sources, `site.title`, `site.start_page` with its range, resolved by `AntoraCatalog::resolve_start_page`; found at the first root with one, else beside the first component version's `antora.yml`), `AntoraCatalog`, `parse_resource_id` for `version@component:module:family$path`, `AntoraResolver`. Resolution follows Antora 3.2 rules; the docs for those rules are linked from the design doc, not re-derived.
- **`adoc-index`** — `WorkspaceIndex` with replacement-based updates and direct map lookups, including reverse maps from the file name an xref names and from a fragment to the references (`xrefs_naming`, `references_with_fragment`), which `adoc-lang` resolves to find references. Every table is keyed by file or holds the file's one shared `Arc<Path>`, so replacing or removing a file visits only what it contributed (`AnchorLocation` and `ReferenceLocation` are views borrowed from the index); keep it so. A file indexed from disk (`index_file`, `replace_from_disk`, the full index) keeps its parse but not its text: read it with `FileEntry::text`, which reads the file back and returns `None` once it no longer holds the text parsed; only `replace` (an open page's parse, sharing its `Arc<str>` text with the engine) keeps the text. Never read an indexed `document.text` directly. An open page's entry can be built off the index as a `PreparedFile` (the parse, anchors with section ids, symbols and words, include targets) and filed with `insert_prepared`, which, prepared against the index's `shared_path` for the file, visits only the keys whose targets, symbol names or includes changed and returns the replaced parts as `Retired`, to be freed elsewhere. `workspace_diagnostics` resolves each file a page's xrefs name once per page (`Lookups`). Never add a feature that scans every document. `normalize_path` is lexical and never canonicalises, so unsaved files work.
- **`adoc-lang`** — editor-agnostic language features operating on byte offsets: definition, hover, completion, diagnostics, document and workspace symbols, attribute resolution, references and anchor renames (`references.rs`). This is the former `adoc-ls/src/handlers` and the non-LSP parts of its `state.rs`. Both `adoc-ls` and `adoc-engine` call it; neither re-implements it.
- **`adoc-math`** — STEM notation: AsciiMath (`asciimath-parser`, converted in-house) and LaTeX (`mitex`) to Typst maths markup, and `is_safe`, which refuses any markup holding code (`#`) or a name outside Typst's maths scope and `HELPERS`. Only checked markup (`TypstMath`) ever reaches Typst's `eval`; whoever evaluates it defines `HELPERS` in its scope.
- **`adoc-spell`** — spell checking with no AsciiDoc knowledge: `spellbook` (only ever named here, checked by `cargo xtask layers`), the bundled SCOWL `en_GB`/`en_US` dictionaries and a folder of others (`Dictionaries`), the words of a run of text worth checking (`words`, `OBJECT`), and word lists (`WordList`). The engine's `src/spelling.rs` reads prose from the visual model and checks open pages on a worker.
- **`adoc-graph`** — general graph code with no AsciiDoc knowledge and no internal dependencies: `GraphKey` (a file or an unresolved target), `EdgeKind`, `NodeKind`, `GraphNode`, `GraphEdge`, `GraphSnapshot` (built by `GraphSnapshot::build`, which filters with `GraphFilter` and merges links of one kind between two nodes), `LinkStore` (each link owned by the file whose text made it, a navigation file owning its tree's links; `set_links`, `set_owned_links`, `remove`, `linking_to`, `neighbourhood`, `shortest_path`, a breadth-first search that is stable on ties, giving `PathStep`s that `GraphSnapshot::along` turns into a snapshot; its reverse maps are hashed, as paths compare slowly) `Layout` (seeded, deterministic force-directed layout, Barnes–Hut above 500 nodes, `f32` only and no trigonometry, with its own `Point`; `set_grouping` adds a pull to each group's centre and a push between groups), groups (`group.rs`: `GroupBy`, `Groups`, `group_name`, `Other` outside Antora, `GraphSnapshot::collapse` drawing a group as one `GraphKey::Group` node with its links merged), mind maps (`tree.rs`: `MindMap::build` from a root, a navigation file's following navigation links only, a page's every link both ways to a depth, one parent per node by link rank; `positions` left to right or radial with polynomial sines; the view feeds them to `Layout::set_targets`, which eases nodes there instead of moving them by force) and `GraphSnapshot::restrict`; `LastChanged` on `GraphNode::last_changed` and `ColourBy::Age` through `Palette` (`Palette::of`, `colour`), which every drawing colours with, the node palette and sizes every drawing shares (`style.rs`: `ColourBy`, which the engine's settings name `GraphColour`, `colour_groups`, `node_colour`, `node_radius`) and `to_svg`/`to_svg_laid_out` (the graph as a standalone SVG, titles escaped and never a path, the same bytes for the same layout), which the app's Export Graph (rasterised to PNG by `image_decode::svg_to_png`), `adocfoundry-cli graph --format svg` and the MCP `link_graph` tool draw with. `cargo bench -p adoc-graph` holds one step for 2,000 nodes to 8 ms. The engine's `src/graph.rs` keeps the graph current: `adoc_lang::graph::links_from` resolves one file, the first build runs on the index worker, `graph_file_changed` marks a file wherever the index changes and `update_due_graph` (in `pump`) resolves it again, with the files naming one that came or went, skipping a file whose link inputs are unchanged; only a change to the catalog's shape (`graph_catalog_changed`) builds it all again, on a worker. Front ends read `Engine::graph`, `graph_path` (searched among what a scope and filter show), `nav_places`, `neighbours`, `new_page_for` and `new_partial_for` (the file a ghost's xrefs or includes expect, from `adoc_lang::graph::missing_page` and `missing_include`, made with `page.new` or `page.new_partial`) and write links with `link_edit` (`src/links.rs`, reusing the resource-id writing of `search.rs`), and redraw on `EngineEvent::GraphChanged`; the app draws it in `src/graph_view.rs` (`GraphView`, in `WindowKind::Graph` and `SidebarTab::Graph`).
- **`adoc-audit`** — the documentation quality audit's model, pure and synchronous (no threads, settings files, writes, subprocesses or network): stable rule IDs and the registry (`RuleId`, `RULES`, `FindingCode`, which is a `quality.*` rule or an existing `DiagnosticCode` aggregated with its own severity and message, never restated as a rule), the report (`AuditBuilder` collects findings, `Skip`s and `Gap`s in any order and `finish` applies the `Policy` and sorts; `AuditReport` is immutable, serialisable, schema-versioned by `SCHEMA_VERSION`, with root-relative `/` paths and no absolute path), completeness (`Completeness` is about coverage, with stable `GapReason`s; a skipped dynamic construct never makes a report partial) and the policy (rule severities, validated `Exclusion`s by resource ID with a reason, `fail_on`, `require_complete`, and `AuditReport::verdict`, the CI table of the Quality PRD §5.4). `audit(&AuditInput, scope)` (`src/workspace.rs`; the input is the `WorkspaceState`, the roots and a reader for navigation files, so the crate does no IO of its own) gives the builder every in-scope file's existing diagnostics (`adoc_lang::diagnostics`, the `antora.yml` files included), a navigation file's unresolved entries as its own `adoc.unresolved-xref-file` (the trees' `nav-unresolved`, which restates them, is left out), the per-version `NavCoverage`, and the rules: `navigation.rs` (`unlisted-page`: a published `.adoc` page no navigation file of its own component version reaches, the start page listed; a navigation with an `include::`, an `{attribute}` target or an unreadable file turns its unlisted pages and dynamic entries into skips) and `content.rs` (`missing-title` on published pages, skipped when an include before the first section may supply it; `missing-alt` on block image macros of pages and partials with no text written at all; the parser records no inline images). It depends on `adoc-core`, `adoc-antora`, `adoc-index` and `adoc-lang`. The engine reads `[quality]` into `Settings::quality` and re-exports the crate as `adoc_engine::audit`; front ends never name it (`ENGINE_ONLY` in `xtask/src/layers.rs`). An audit is made of parts that never depend on the scope (`audit_file`, `audit_version`: `FileAudit`, `VersionAudit`), which `assemble` puts together for a scope; `audit` computes the parts in scope and assembles them, and the engine keeps them, so the CLI's audit and the app's always agree. `to_sarif` writes SARIF 2.1.0 (excluded findings as suppressed results, gaps as tool execution notifications, completeness and provider states run properties), with 1-based character regions from a caller-given `Region` lookup, since only the caller reads files. Optional providers (`providers.rs`: `ProviderId`, `PROVIDERS` with `Needs` and the tracking issue: `compatibility` #104, `external-links` #86, `page-age` #289, `vale` #85) are off until `[quality] providers` enables them (`Policy::enable_provider`); none is implemented, and their work must never run in this crate (`ADOC_AUDIT_FORBIDDEN_PATHS` in `xtask/src/layers.rs`, test `audit_is_offline`): whoever runs one reports `AuditBuilder::provider_ran`/`provider_unavailable`, and `finish` gives every provider a `ProviderStatus` (`AuditReport::providers`), an enabled one that did not run being unavailable and a `provider-unavailable` gap.
- **`adoc-impact`** — the documentation impact analysis's model (Impact PRD), pure and synchronous like `adoc-audit` (the same forbidden paths in `xtask/src/layers.rs`; in `ENGINE_ONLY`, re-exported as `adoc_engine::impact`), depending on `adoc-core`, `adoc-antora`, `adoc-index` and `adoc-lang`. A `DependencySnapshot` is one side of a comparison, a `WorkspaceState` at one revision, borrowed (the live workspace) or owned (a revision built from Git objects); every question goes through the index's reverse maps and `adoc-lang` (`includes_of`, `references_to`, `references_to_anchor`, `reference_target_path`, section ids, `graph::links_from` for navigation entries), never a scan or a second resolver. `analyse(changes, base, head, publications, limits)` gives an `ImpactReport` (`SCHEMA_VERSION`, root-relative paths, sorted): render impacts through the include closure (cycles and depth bounded), reference-integrity reviews for removed or moved targets (from base; `broken`, `resolved_by_alias`, `resolved_by_change`) and removed anchors, never for prose changes; navigation compared per component version between base and head; publications whose selection holds an affected page (`potential` when it names content head lacks). Every impact records its `evidence` side, `via` path and `source` span. Gaps: `no-base-revision`, `asset-consumers-not-analysed` (images are not traced), `not-in-catalog`, `outside-every-root`. Fixture `tests/fixtures/impact`. The engine's `src/impact_analysis.rs` runs it: `Engine::analyse_impact(&ChangeSource, Limits)` with `GitRefs { base, head }` (both snapshots from Git objects: `adoc_git::Repository::resolve_revision`, `tree_files`, `text_at`, `tree_changes` with renames, then `adoc_antora::discover_antora_files`, the disk discovery's rules over a file list, and the same parser; the working tree and live index never read; cached by tree id in `ImpactCache`), `WorkingTree` (`HEAD`'s snapshot against the live workspace, unsaved buffers included) and `Paths` (no base; works without the `git` feature) and `Removal` (Inspect Impact: the live workspace against a copy with the files taken out through `remove_document` and `remove_source`, as a staged move does). An explicit comparison reads Git whatever `[git] enabled` says. `analyse_impact` and the app's worker share one `compute` over inputs taken from the engine; `src/impact_inspection.rs` keeps the app's one analysis (`inspect_impact` on a worker, `impact_inspection`, `impact_stale` by workspace revision, `impact_place`, `impact_trail`, the report's `via` as graph `PathStep`s asked of the link store), and the snapshot resolves a reference only to a file its side holds. `src/deletion.rs` is Delete File (#100): `file.delete` moves any file of the roots (never a folder, a link or one reached through a linked folder) into `<state_dir>/deleted/<millis>-<pid>-<n>/file`, after any save of it in flight, closing its tab and telling the index, catalog, graph and Files view as the watcher would; undo history is per page and a deleted page has none, so `file.undo_delete` puts back the session's latest deletion (refused while a file is at its path), reopening it if it had a tab; earlier sessions' are swept after `[history] keep_days`; without a state folder nothing is deleted (`can_delete_files`, `CommandContext::Deletion`/`DeletedFile`).
- **`adoc-engine`** — the only entry point front ends use. Its features `typst` (PDF export and the STEM provider) and `git` (`adoc-git`) are default for the crate but off in `[workspace.dependencies]`, so each front end names the ones it wants; without `git` the engine behaves as with `[git] enabled = false` (`src/git_off.rs`), and without `typst` the export commands are not registered. Owns the workspace (roots, catalog, index), open documents, the command registry, undo history, settings and the file watcher, and publishes `EngineEvent`s. A file the watcher reports in a module's family folders is catalogued or forgotten on its own (`catalog_file_changed` in `src/workspace.rs`, a page with its `page-aliases`), never by reading its component again, and an open page keeps its entry as it keeps its index entry. `[workspace] ignore` is the one list of folders the index, Antora discovery and the watcher skip (`adoc_core::DEFAULT_IGNORED_DIRECTORIES` by default); the index worker places the watches as it walks, one per folder on Linux (`WatchMode::Folders`) and one per root elsewhere, never following links, and an unreadable folder is reported and left out rather than failing the index. Every user-visible action is a `Command` with a stable `CommandId`; the UI, CLI and future MCP server invoke commands, never engine internals. `Engine::next_due` is the earliest deadline of every step of `pump`, which `has_pending` reads, so a new step in `pump` needs its deadline there and a test in `tests/wake.rs`; every worker message goes through `WorkerSender`, which, like the watcher's callback, calls the waker a front end gave `set_waker`. Every worker counted in `workers_running` is started with `worker::spawn` (`src/worker.rs`), which turns a panic into the failure its job reports (or `WorkerMessage::Crashed`), so nothing waits for a worker that has gone, and the writer runs each job under `worker::guarded`; start new workers through it, never with a bare `thread::spawn`. Each document has an `EditorMode`; while it is shown visually the engine keeps a `VisualDocument` (model and view tree from one parse, `src/visual.rs`). Visual commands take `CommandArgs::Visual` (a selection in source offsets and the document version it belongs to) and apply model steps as ordinary edits in the document's one undo history. A change from elsewhere makes the model stale: source typing rebuilds it after `MODEL_SETTLE`, any other command that made it stale before `invoke` returns; only the active page's model is rebuilt so, and a background page's waits until it is shown (`set_active`). `restore_session` builds no model (`set_editor_mode_later`): the active page's is built on the next `pump`, the rest when shown, and diagnostics are refreshed once after the last tab; the app restores only after the window's first frame (`after_first_frame` in `workspace_view.rs`). `Engine::git()` holds each root's repository, file status and the hunks of open documents (`src/git.rs`); discovery, status and diffs run on workers, hunks recompute `GIT_SETTLE` after typing (diffing against each document's text in `HEAD`, kept until `HEAD`'s commit moves, in one job per working tree), and the watcher also watches `.git/HEAD`, `index`, `packed-refs` and `refs/`. Request flow: a keystroke edits the editor buffer → `Engine::apply_edit` updates the document and publishes `EngineEvent::DocumentChanged` → views re-render from engine state. A typed edit is indexed once typing pauses for `INDEX_SETTLE`: `src/index_settle.rs` parses the page and prepares its index entry on a worker, and `pump` files it and diagnoses only while the page is at the version parsed; any non-typing command indexes what is pending, or still on the worker, at once. Preview flow: while the preview is visible the engine requests its target (the pinned document, else the active one) → `PREVIEW_SETTLE` (100 ms) after the last change to the page or any file it includes, a worker parses a snapshot through `adoc-dom` → `pump` builds the view tree on the engine thread (resolution needs the catalog and index) → diagrams come from the cache or render on a worker → `EngineEvent::PreviewReady` → views read `rendered_preview(id)`. A result is dropped when a newer job started or an input changed after it began.

## Conventions that must be preserved

- Layering is absolute: no upward dependencies, no UI types below `adocfoundry`, no LSP types below `adoc-ls`, no external parser crates outside `adoc-dom`, and no HTTP client reachable from any crate but `adocfoundry` (checked over the resolved graph by `cargo xtask layers`). `hyper` and `hyper-util` are allowed in `adoc-mcp` too (`NETWORK_SERVER_ALLOWED`), as long as its own build turns on none of their `client` features.
- Byte offsets everywhere (`SourceRange`). Line/column conversion happens at the edge (`adoc-ls` for LSP, the editor view for the caret) using `LineIndex`.
- Diagnostics stay conservative: prefer no diagnostic over a false positive, warnings over errors for unresolved references, and no diagnostics at all for dynamic constructs (`include::{attr}/x.adoc[]`).
- Incomplete AsciiDoc is normal input. Parsers, resolvers and handlers must not panic on half-typed syntax; add a regression test for every panic fixed.
- Every mutation of a document goes through a `Command` and is recorded in undo history. No view writes to a buffer directly.
- `unsafe_code = "forbid"` workspace-wide; avoid global mutable state; `anyhow` only in binaries, typed errors in libraries.
- Edition 2021 (matching the migrated crates); the toolchain is pinned in `rust-toolchain.toml`, and `rust-version` in `[workspace.package]` names the same release (checked by `packaging/test_toolchain.py`); move both together. `[profile.release]` uses thin LTO and strips symbols, and keeps `panic = "unwind"`, which the parsers' and workers' panic guards need. Crates take dependency versions from `[workspace.dependencies]`, never their own.
- All external dependencies are pinned exactly (`=1.0.229` style) and new ones must pass `cargo deny` (MIT, Apache-2.0, BSD-2/3, MPL-2.0, Unlicense, Zlib, OFL-1.1 for fonts; GPL and LGPL are denied).
- `vendor/evalexpr` is a home-grown Apache-2.0 stand-in, patched in through `[patch.crates-io]`, for the AGPL `evalexpr` that acdc-parser pulls in (see `vendor/README.md`). Do not remove the patch while acdc-parser still depends on it.
- `vendor/comemo` is comemo 0.5.1 with two changes that free the memory of evicted caches (gigabytes after a book export, which the app would otherwise keep), patched in the same way. Keep it at the comemo version Typst uses, and drop it once a release frees evicted memory (see `vendor/README.md`).
- Keep the UI framework a one-crate swap (egui/eframe was the fallback had the GPUI spike failed): nothing below `adocfoundry` may know which framework is in use.
- **Never** depend on Zed's `editor`, `text`, `rope`, `multi_buffer`, `language` or `project` crates: they are GPL-3.0. The permitted GPUI crates are `gpui`/`gpui-pre`, `gpui-component`, `gpui-base` and their platform crates (Apache-2.0).
- No Node.js, no JVM, no Ruby required at runtime. External tools (`asciidoctor`, `dot`, `plantuml`, `mmdc`) are optional and discovered, never assumed.
- Use `Path`/`PathBuf` for filesystem work and `adoc_index::normalize_path`; do not canonicalise paths that may not exist. Antora resource IDs always use `/`.
- Do not clone remote Antora repositories or execute project scripts.
- Settings are TOML, read through `adoc-engine::Settings`; the UI never reads the settings file itself.

## Testing

Unit tests live in `#[cfg(test)] mod tests` next to the code. Integration tests: `crates/adoc-engine/tests/` drives the engine headlessly through commands; `crates/adocfoundry-cli/tests/cli.rs` drives the binary via `CARGO_BIN_EXE_adocfoundry-cli`; `crates/adoc-ls/tests/stdio.rs` drives the language server through an initialise/shutdown lifecycle.

Shared fixtures are in `tests/fixtures/`, grouped by scenario (`simple/`, `includes/`, `xrefs/`, `antora-single-component/`, `antora-multi-component/`, `antora-versions/`, and `render/` for the fidelity harness), reached with `Path::new(env!("CARGO_MANIFEST_DIR")).join("../../tests/fixtures/...")` — never absolute developer-machine paths. A test that opens a fixture in place turns Git off (`Settings::with_git_opt_in()`), since the fixtures lie inside the developer's checkout. Keep fixtures small and readable; add one alongside every resolver, parser, engine or command behaviour change.

Tests that spawn a real process must take the crate-private `spawn_guard()` mutex in `adoc-render` (the `ETXTBSY` workaround). Do not remove the guard or add unguarded spawning tests.

A pull request is done when: `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`, `cargo deny check` and `cargo xtask layers` all pass, `README.md` reflects any visible change, and the phase spec's acceptance test for the work package has a test with that name.

## Working rules for Claude Code

- Work one work package at a time, in the order the phase spec gives; each package leaves the workspace compiling and green.
- Read the relevant section of the phase spec and the crate's existing code before writing. The spec gives trait signatures; implement them as written and raise a question in the PR description if a signature cannot work, rather than silently changing it.
- Prefer extending an existing crate over adding a new one; a new crate needs a line in the ladder above and in the layering check.
- When a dependency is needed, check `Cargo.lock` for one already in the tree before adding another, pin it exactly, and run `cargo deny check`.
- Do not refactor crates outside the package you are working on unless the spec says the package includes that refactor.
- If the spike or a package shows the spec is wrong, update the spec in the same PR and say so in the description.
- Commit messages: short imperative (`Add cross-component resolution to adoc-antora`). One package per PR, titled `WP <phase>.<n>: <package name>`; the PR description lists the spec section, tests added and the commands run.
